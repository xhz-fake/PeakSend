# Day14-变更细节及详细逻辑链路说明

## 1. Day14 这一阶段要解决的，不只是“项目里用了 Redis”

如果只从技术名词看，`PeakSend` 里其实早就已经有 Redis 了：

- 店铺营业状态已经直接放在 Redis
- 用户端菜品和套餐查询已经用了 Spring Cache

所以 Day14 如果只是说：

- “我又做了一次 Redis”

那这一天的价值会很弱。

更准确的说法应该是：

- Day14 要把项目里原本分散、半成型的缓存能力，升级成一个更像高并发读场景优化专题的版本

也就是说，这一天真正要练的不是：

- 会不会写 `@Cacheable`

而是下面这几件工程能力：

- 哪些接口适合缓存
- 缓存 key 应该按什么查询维度设计
- 管理端写操作后，用户端为什么不能继续读旧缓存
- TTL 为什么重要
- 为什么要防缓存雪崩、缓存穿透
- Redis 挂掉时，系统至少应该怎么兜底

一句话总结：

- Day14 的目标，是把 Redis 从“项目里出现过”，升级成“可以讲热点读优化、缓存一致性和基础高并发认知”的能力块。

## 2. Day14 和以前 Day7 的商品缓存，边界有什么不同

这个问题一定要先讲透，不然后面最容易误以为：

- Day14 只是把 Day7 重做一遍

其实不是。

Day7 更像课程阶段的缓存入门，它解决的是：

- 用户端菜品和套餐第一次查库、第二次命中缓存
- 管理端修改后如何删缓存

而 Day14 是升级版项目里的再工程化，它的视角更高一层：

- 不再只盯“一个接口有没有缓存”
- 而是把缓存当成一类后端性能优化能力来看

所以 Day14 真正新增的视角有四个：

### 2.1 从“会缓存”转向“会选缓存场景”

不是所有接口都值得缓存。

Day14 更强调优先挑：

- 高频读
- 低写入频率
- 查询结果可重复复用
- 对一致性要求是“最终一致即可”的接口

像分类列表、菜品列表、套餐列表、营业状态，就是典型场景。

### 2.2 从“会写注解”转向“会设计 key 和失效策略”

缓存真正难的地方从来不是 `@Cacheable` 本身，而是：

- key 怎么设计
- 缓存粒度是什么
- 写操作后删哪个 key
- 为什么有时删单个 key 不够，要删整组缓存

### 2.3 从“能跑”转向“能解释高并发常见问题”

Day14 开始，项目要能承载下面这些常见面试问题：

- 缓存穿透
- 缓存雪崩
- 缓存一致性
- Redis 异常时的降级思路

不一定今天一次做完全部高级方案，但至少要有第一版设计落点。

### 2.4 从“写完代码”转向“拿到量化证据”

如果 Day14 最后没有这些东西，这一天价值会打折：

- 缓存前后接口响应时间对比
- Redis key 命中证据
- MySQL 压力下降证据

所以 Day14 不是单纯功能开发，而是第一次把“代码 + 验证 + 指标”绑在一起。

## 3. Day14 当前第一刀为什么先落在分类缓存

Day14 当前第一刀没有先去上报表缓存，也没有直接谈复杂的穿透方案，而是先补：

- 用户端分类缓存
- 管理端分类缓存失效

这样做不是保守，而是有明确的教学和工程原因。

### 3.1 分类接口更适合先吃透缓存基本功

分类接口本身很适合做第一刀，因为它：

- 查询参数少
- key 设计简单
- 返回结构清晰
- 和菜品/套餐显示关系紧密

这意味着我们可以先把下面这条最核心链路练扎实：

- 用户端查分类
- 第一次查库
- 第二次命中缓存
- 管理端改分类
- 用户端下次重新查库

### 3.2 分类缓存能帮助我们真正理解“按查询维度设计 key”

用户端分类接口是：

- `/user/category/list?type=1`
- `/user/category/list?type=2`

所以缓存 key 的设计必须跟查询维度一致。

也就是说，缓存不是按：

- `categoryId`

来存，而是按：

- `type`

来区分分类列表结果。

这次实际采用的是：

- `categoryCache::1`
- `categoryCache::2`
- 当 `type` 为空时，用 `categoryCache::all`

这一步非常重要，因为它会把你对缓存 key 的理解从“随便拼个字符串”推进到：

- key 必须跟接口查询语义一致

### 3.3 分类变更非常适合讲“为什么先删缓存而不是更缓存”

分类会发生的写操作包括：

- 新增分类
- 修改分类
- 删除分类
- 启用/禁用分类

一旦发生这些操作，用户端看到的分类列表就可能变化。

这时工程上最稳的第一版策略，不是去精确更新 Redis 里的旧值，而是：

- 写成功后直接删掉相关分类缓存

为什么？

因为分类可能不只是改名字，还可能：

- 改状态
- 改排序
- 改类型

如果分类从 `type=1` 改到 `type=2`，那它同时影响：

- 原来 `type=1` 这组缓存
- 现在 `type=2` 这组缓存

这时“精确更新某一个 key”很容易漏删。

所以 Day14 第一版先采用：

- `@CacheEvict(allEntries = true)`

优先保证正确性，再谈精细化。

## 4. Day14 当前已落地的第一批改动

这次第一批代码改动集中在两个入口。

### 4.1 用户端分类缓存入口

文件：

- [user/CategoryController.java](file:///D:/ProgramFiles/CodeProjects/PeakSend/peaksend-backend/sky-server/src/main/java/com/sky/controller/user/CategoryController.java)

当前做法：

- 在分类列表查询接口上增加：
  - `@Cacheable(cacheNames = "categoryCache", key = "#type == null ? 'all' : #type")`

它的含义是：

1. 请求进来后，Spring Cache 会先看 Redis 里有没有对应 key
2. 如果有，就直接返回缓存结果
3. 如果没有，才真正进入方法体执行 `categoryService.list(type)`
4. 方法返回后，Spring Cache 自动把结果写入 Redis

这也意味着一个很重要的观察点：

- 如果缓存命中了，Controller 里的业务日志通常不会再打印

这后面会直接用来做 Day14 的命中验证。

### 4.2 管理端分类缓存失效入口

文件：

- [admin/CategoryController.java](file:///D:/ProgramFiles/CodeProjects/PeakSend/peaksend-backend/sky-server/src/main/java/com/sky/controller/admin/CategoryController.java)

当前做法：

- 在下面 4 个写接口上增加：
  - `@CacheEvict(cacheNames = "categoryCache", allEntries = true)`

对应操作包括：

- 新增分类
- 修改分类
- 删除分类
- 启用/禁用分类

它真正完成的是：

- 只要管理端某个分类写操作成功，当前 `categoryCache` 整组缓存就会被清掉
- 用户端下一次再访问分类接口时，就必须重新回库并重建缓存

这就是典型的：

- `Cache Aside`
- 也就是“读时回填，写时删缓存”

## 5. Day14 目前这条分类缓存链到底怎么走

为了让你后面能真正自己讲出来，我们把这条链按请求顺序拆一遍。

### 5.1 用户端第一次查分类

假设请求是：

- `GET /user/category/list?type=1`

请求进来后：

1. Spring Cache 先检查 Redis 中是否存在：
   - `categoryCache::1`
2. 如果不存在，进入 Controller 方法体
3. Controller 调用 `categoryService.list(1)`
4. Service 组装查询条件：
   - `type=1`
   - `status=ENABLE`
5. Mapper 去查数据库
6. 返回 `Result<List<Category>>`
7. Spring Cache 自动把这个结果写入 Redis

### 5.2 用户端第二次再查同样的分类

请求还是：

- `GET /user/category/list?type=1`

这一次：

1. Spring Cache 先检查 Redis
2. 发现已经有：
   - `categoryCache::1`
3. 直接返回缓存值
4. Controller 方法体不再真正执行业务查询
5. 数据库也不会再被访问

这就是缓存命中的最本质效果：

- 不是“查完数据库再顺手去看一下 Redis”
- 而是在方法执行之前就已经决定了这次是否还需要访问数据库

### 5.3 管理端修改分类后会发生什么

假设管理端执行：

- 修改分类名称
- 启用 / 禁用分类
- 删除分类

只要对应接口执行成功：

1. `@CacheEvict` 会把 `categoryCache` 整组清掉
2. Redis 中原有分类列表缓存被删除
3. 用户端下一次再查分类时，就不可能再命中旧值
4. 系统只能重新回库查最新数据
5. 再把最新结果重新写入缓存

这条链路非常值得背下来，因为它本质上就是：

- 查询提速靠缓存
- 一致性靠写后删缓存

## 6. Day14 后续真正补了什么，最后又收到了哪里

前面分类缓存和地址簿空值缓存落地之后，Day14 没有继续发散去追更多“听起来高级”的概念，而是继续补了两类真正有简历价值的能力：

- 报表类热点查询结果缓存
- 一轮能拿得出手的量化验证

也就是说，Day14 最后不是停在：

- “我又多写了几个 `@Cacheable`”

而是收到了一个更完整的缓存工程化版本：

- 高频读列表缓存
- 写后删缓存保证一致性
- 空值缓存挡住明显穿透
- 结果级缓存优化高成本统计查询
- Redis key / TTL / 日志 / MySQL 增量四类证据联动验证

下面把这几块补齐后的意义讲透。

### 6.1 TTL

如果缓存没有明确 TTL，容易出现两个问题：

- 旧数据长期驻留
- 热点 key 生命周期不可控

这里已经补完了 RedisCacheManager 统一 TTL 配置，并且不是所有缓存一个时间，而是按场景分档：

- 分类缓存：`20m`
- 菜品缓存：`30m`
- 套餐缓存：`35m`
- 地址簿空值缓存：`2m`
- 报表结果缓存：单独配置较短 TTL

这样做的意义是：

- 热点读列表和统计结果都能被缓存
- 但不会让所有 key 在同一时刻集中失效
- 空值缓存也不会长期滞留

### 6.2 雪崩基础防护边界

如果一批 key 都在同一个固定 TTL 到期，就容易在热点时段同时失效。

这就是缓存雪崩最基础的触发条件之一。

Day14 这里没有继续内卷到更复杂的 per-key 随机扰动系统，而是先明确收在：

- 不同缓存使用不同 TTL
- 让热点 key 至少具备错峰过期意识

为什么先收在这里？

因为当前 Day14 的目标是：

- 先把可实现、可验证、可讲的缓存工程主线打通

而不是今天为了一个名词，再把整套缓存基础设施做成更重的版本。

更细的随机过期扰动，会留到后续增强项，不再阻塞 Day14 收口。

### 6.3 穿透防护第一版

Day14 这一天至少要让项目能开始承载这个问题：

- 如果一直请求一个不存在的数据怎么办？

第一版不一定上布隆过滤器，但可以先考虑：

- 空值缓存
- 较短 TTL

这一块最后的明确落点是：

- 在用户端地址簿按 id 查询上，给不存在地址的查询结果做了短 TTL 空值缓存

这里要特别注意一个容易误解的点：

- 我们缓存的不是“Java 方法直接返回了 null”
- 而是 Controller 最终返回的整个：
  - `Result.success(null)`

也就是说：

1. Service 查不到地址时，返回 `null`
2. Controller 再把它包成：
   - `Result<AddressBook>`
3. Spring Cache 缓存的是整个返回对象
4. 所以“查不到”的结果也能短暂进入 Redis

当前 key 设计为：

- `当前用户id:地址id`

例如：

- `addressBookByIdCache::4:999999`

这样做的目的不是写得花，而是避免不同用户查询同一个地址 id 时互相串缓存。

TTL 当前先配成：

- `2m`

这里故意配短，是因为第一版的目标不是长期缓存空结果，而是：

- 挡住短时间内重复请求同一个不存在 id 时的回库压力

这样至少能把“明显的穿透场景”挡住一部分。

而且这一轮我们不是只停留在代码层，而是真正跑了运行态验证：

1. 先确认 Redis 中没有：
   - `addressBookByIdCache::*`
2. 请求不存在的地址：
   - `GET /user/addressBook/999999`
3. 首次返回：
   - `{"code":1,"msg":null,"data":null}`
4. Redis 中出现：
   - `addressBookByIdCache::4:999999`
5. 在 TTL 还没过期时再次请求
6. 后端只剩 JWT 校验日志
7. `AddressBookController` 日志和 SQL 消失

这说明：

- “查不到”的结果确实已经命中缓存
- 我们挡住的不是抽象概念，而是短时间内对同一个不存在 id 的重复回库

### 6.4 报表结果缓存

如果 Day14 只停在分类缓存和空值缓存，它依然更像“会缓存接口列表”。

真正把这一天往后端优化题上再推一层的，是：

- 管理端报表结果缓存

落点选的是：

- `GET /admin/report/turnoverStatistics`

它和分类列表的区别在于：

- 分类列表更像“重复查同一份列表”
- 营业额统计更像“重复算同一份统计结果”

而 `ReportServiceImpl` 本身就是典型的高成本查询：

1. 从 `begin` 到 `end`
2. 一天一天循环
3. 每一天都查一次数据库
4. 最后再把每天结果拼成 `TurnoverReportVO`

所以这里最值得缓存的，不是原始表数据，而是：

- 指定时间区间最终算出来的统计结果

当前 key 设计为：

- `turnoverReportCache::begin:end`

例如：

- `turnoverReportCache::2026-08-01:2026-08-14`

这类设计非常适合面试表达，因为它天然就是：

- 输入是时间区间
- 输出是统计结果
- key 直接和查询语义绑定

### 6.5 Redis 异常兜底

真正工程化的系统不会假设 Redis 永远正常。

所以后面至少要讲清楚：

- Redis 不可用时，是否还能回退数据库
- 哪些接口即便缓存失效，业务也不该直接 500

这部分会直接决定 Day14 能不能讲出“系统稳定性意识”。

## 7. Day14 这一轮完整链路到底验证了什么

这一轮最后实际跑通的，不再只是“分类缓存能不能命中”，而是已经形成了一条比较完整的 Day14 证据链。

### 7.1 分类缓存闭环

这一轮我们亲手验证了：

1. Redis 中先删掉：
   - `categoryCache::1`
2. 再确认 TTL 为：
   - `-2`
3. 第一次请求：
   - `GET /user/category/list?type=1`
4. 响应时间：
   - `0.037384s`
5. Redis 中重新出现：
   - `categoryCache::1`
6. 二次同请求响应时间降到：
   - `0.019104s`
7. 管理端修改分类后：
   - `categoryCache::1` 变成 `-2`
8. 用户端再次请求后：
   - 读到最新分类名称
   - Redis TTL 重新变成正数

这说明：

- 首次请求会查库并回填缓存
- 二次请求会命中缓存
- 管理端写操作会真正触发写后删缓存
- 下次读请求会重新查库并重建缓存

### 7.2 空值缓存闭环

这一轮我们也验证了：

1. 先确认 Redis 中没有：
   - `addressBookByIdCache::*`
2. 首次请求不存在地址：
   - `GET /user/addressBook/999999`
3. 返回：
   - `{"code":1,"msg":null,"data":null}`
4. Redis 中出现：
   - `addressBookByIdCache::4:999999`
5. 如果中间等太久，超过 `2m` TTL，请求会重新回库
6. 在 TTL 未过期时再次请求
7. Controller 日志和 SQL 消失

这说明：

- 空值缓存确实已经生效
- TTL 也确实在动态生效
- “没命中”不一定是代码错了，也可能只是缓存已经过期

### 7.3 报表结果缓存闭环

这一轮最有价值的新验证，是报表接口：

- `GET /admin/report/turnoverStatistics`

我们实际拿到了两组数据。

第一组老区间：

- 首次：
  - `0.707692s`
- 二次：
  - `0.030966s`

第二组新区间：

- 首次：
  - `0.076508s`
- 二次：
  - `0.015217s`

并且 Redis 中能看到：

- `turnoverReportCache::2026-08-01:2026-08-14`
- `turnoverReportCache::2026-08-02:2026-08-13`

数据库侧还补了 `MySQL Questions` 增量趋势：

- 基线：
  - `22`
- 第一次新区间请求后：
  - `43`
- 第二次同新区间请求后：
  - `46`

这里要特别强调一个工程表达：

- `Questions` 不是业务 SQL 的精确计数器
- 它是 MySQL 全局累计值
- 所以我们看的是：
  - 第一次之后增量明显更大
  - 第二次之后增量明显更小

这已经足够支撑：

- 报表结果缓存降低了重复统计查询的数据库压力
