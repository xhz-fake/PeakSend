# PeakSend 12 天陪跑总地图

## 1. 我们这 12 天到底在做什么

这 12 天不是单纯把一个课程项目敲完，而是围绕 `PeakSend` 这份简历项目，系统训练以下四项核心能力：

- 能看懂并分析一个中后台项目的业务结构
- 能把原型图、接口文档、数据库和代码实现串起来
- 能独立完成接口开发、接口调试、前后端联调和常见问题排查
- 能把项目中的设计思路讲清楚，转化为实习和秋招面试中的表达素材

因此，我们后面的节奏会固定为：

- 先明确当天业务目标
- 再拆接口、数据库、类结构和关键流程
- 然后完成代码
- 再用 APIFox 和页面验证
- 最后输出当天的复盘文档

## 2. 项目的整体技术画像

后端技术主线：

- Spring Boot
- MyBatis
- MySQL
- Druid
- PageHelper
- JWT
- Knife4j / Swagger
- APIFox
- Nginx
- Redis
- WebSocket
- 定时任务
- POI Excel 导出

工程结构主线：

- `sky-common`：常量、异常、工具类、统一组件
- `sky-pojo`：DTO、Entity、VO、POJO
- `sky-server`：Controller、Service、Mapper、配置、拦截器、业务实现

业务主线：

- 管理端：员工、分类、菜品、套餐、店铺营业、订单处理、统计报表、工作台
- 用户端：登录、浏览商品、购物车、下单、历史订单、地址簿、催单

## 7. 最终目标

项目完成时，你不只会拥有一份代码，而会同时拥有：

- 一份完整可运行的简历项目
- 一套从需求到实现的后端开发方法
- 一批可复用的调试经验与排错思路
- 一套可以用于实习和秋招的项目表达素材

## 8. 从目前对话中沉淀出的高价值原则

- 进度不以“看了几小节”为核心指标，而以“是否讲得清楚一个完整业务链路”为核心指标
- 视频课程提供主线，但真正决定你能否拿这个项目去面试的，是你是否理解设计理由、排错方法和工程取舍
- 每做完一个功能，都必须补齐三件事：接口调通、页面联调、文档复盘
- 项目中的每一个技术点，都要尽量回答三个问题：它解决什么问题、为什么放在这里、如果出错该怎么排查

## 9. 已经暴露出的常见问题类型

- Git 仓库层面：子目录重复初始化仓库，导致根仓库无法正确追踪代码
- Maven / IDEA 层面：模块名、父工程名、JDK 版本、Lombok 版本不一致，导致编译异常或 UI 显示异常
- 环境层面：后端端口、Nginx 端口、MySQL 实例、项目配置文件理解混乱
- 接口层面：请求方式错误、`@RequestBody` 缺失、token 未携带、Swagger 文档与静态接口文档混淆
- 数据库层面：连错实例、密码格式问题、修改了错误字段、只改表数据但没验证接口链路

## 10. 我们后续固定使用的排错顺序

后面遇到问题，优先按这个顺序排查：

1. 先确认请求有没有真正打到后端
2. 再确认请求路径、请求方式、请求体和请求头是否正确
3. 再看 Controller 是否正确接收参数
4. 再看 Service 的业务逻辑有没有执行到
5. 再看 Mapper / SQL 是否正确命中数据库
6. 最后才考虑前端页面和缓存等外围因素

这样做的好处是：不会一出错就慌，也不会盲目怀疑所有东西。

## 11. Day12 之后的升级版路线

前面的 `Day1 ~ Day12` 负责把课程版 `PeakSend` 做成一份完整、可运行、可复盘、可讲述的业务项目。

但如果目标进一步升级为：

- 拿这份项目去冲中小厂实习
- 尽量减少再做第二个业务项目的重复投入
- 在现有业务骨架上继续补工程化、异步化和微服务能力

那么 `Day12` 之后就不应该直接散掉，而应该进入升级版路线。

### 为什么升级版路线要单独规划

原因不是原项目不够好，而是：

- 原项目更偏“课程业务闭环”
- 求职展示还需要进一步补上：

  - Docker
  - 更有业务落点的 Redis 使用
  - RocketMQ
  - 微服务拆分
  - 日志链路与部署能力

因此，`Day12` 之后的目标不再是“继续堆小功能”，而是：

- 把 `PeakSend` 从课程项目演进成更适合简历展示的升级版主项目

### 升级版路线的几个硬原则

- 不为技术而技术，每加一层技术都要能解释它解决了什么业务或工程问题
- 一次只推进一个最小闭环，不能一口气“上微服务全家桶”
- 每阶段都要有代码、验证、文档、复盘，不允许只留概念
- 当前管理端前端源码不完整，因此升级版默认优先推进后端和系统层能力

### 对当前项目的整体认识

从现在开始，`PeakSend` 应同时有两层定位：

- 第一层：`Day1 ~ Day12` 的课程版项目，用来完成业务主链和基础工程能力
- 第二层：`Day13 ~ Day20` 的升级版项目，用来补强容器化、异步化、微服务和可观测性

两者不是互相替代，而是前后衔接。
