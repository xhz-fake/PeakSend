## 2. 项目一句话介绍

### 2.1 项目介绍

这是一个围绕本地生活配送场景构建的商配平台项目，基础版已经完整覆盖了管理端和用户端两条主链。业务上参考了外卖/商家后台系统的典型场景，核心包括：

- 管理端：员工、分类、菜品、套餐、店铺营业、订单处理、统计报表、工作台

- 运营侧：WebSocket 来单提醒、报表统计、工作台、运营数据导出

技术上主要基于：

- Spring Boot
- Spring MVC
- MyBatis
- MySQL
- Redis
- JWT
- AOP
- WebSocket
- 定时任务
- POI Excel 导出
- Maven 多模块工程

可以这样说：

## 3. 项目整体架构怎么说

### 3.1 高频问题：你的项目是怎么分层的？

#### 简洁回答

我的项目采用的是比较典型的分层设计，主要分为：

- Controller 层：负责接收请求和返回响应
- Service 层：负责核心业务逻辑、事务控制和规则判断
- Mapper 层：负责和数据库交互

这种设计的好处是职责清晰，便于维护，也方便后期扩展。

#### 延伸说明

如果面试官继续问，可以补一句：

- 比如菜品管理里，Controller 只负责接参数和调 Service，真正的一对多保存、删除前校验、事务控制，都是在 Service 层完成的。

### 3.2 高频问题：你的项目为什么要拆成 common、pojo、server 三个模块？

#### 简洁回答

我这个项目是 Maven 多模块工程，主要分成：

- common：放公共工具类、常量、枚举、上下文等通用能力
- pojo：放 DTO、Entity、VO 这些数据对象
- server：放 Controller、Service、Mapper、配置类这些真正的业务代码

这样拆分的好处是：

- 公共能力和业务能力分离
- 数据对象集中管理
- 结构更清晰，也更接近真实项目的组织方式

## 4. DTO、Entity、VO 怎么说

### 4.1 高频问题：DTO、Entity、VO 分别是干什么的？

#### 简洁回答

- DTO 面向请求，主要用来接收前端传来的参数
- Entity 面向数据库，通常和表结构比较接近
- VO 面向响应，主要用来返回给前端展示

#### 好背版本

- DTO：接请求
- Entity：落数据库
- VO：做响应

#### 项目例子

在菜品管理里：

- `DishDTO` 用来接前端新增或修改菜品时提交的数据
- `Dish` 对应数据库中的 `dish` 表
- `DishVO` 用来返回菜品详情或分页展示结果，因为前端除了菜品本身，还需要分类名、口味等展示字段

## 5. Spring MVC 和请求链怎么说

### 5.1 高频问题：前端请求到后端之后，整个链路是怎么走的？

#### 简洁回答

前端点击按钮后，会由前端的 JavaScript 发起 HTTP 请求，请求先到 Tomcat，再交给 Spring MVC。Spring MVC 会根据请求路径和请求方式找到对应的 Controller 方法，并完成参数绑定。然后 Controller 调用 Service，Service 再调用 Mapper 和数据库交互。最后 Controller 返回 Java 对象，Spring MVC 再把它转换成 JSON 响应给前端。

#### 更顺口版本

- 前端发请求
- Tomcat 接住
- Spring MVC 分发到 Controller
- Controller 调 Service
- Service 调 Mapper
- Mapper 执行 SQL
- 结果再被 Spring MVC 转成 JSON 返回前端

### 5.2 高频问题：Spring MVC 在你的项目里主要做了什么？

#### 简洁回答

Spring MVC 在我这个项目里主要负责四件事：

- 路由分发：根据 URL 和请求方式找到对应 Controller
- 参数绑定：把 JSON、路径参数、查询参数转成 Java 参数或对象
- 执行拦截器：比如 JWT 登录校验
- 响应转换：把 Java 对象序列化成 JSON 返回给前端

### 5.3 高频问题：`@RequestBody`、`@PathVariable`、`@RequestParam` 有什么区别？

#### 简洁回答

- `@RequestBody`：从请求体里接 JSON
- `@PathVariable`：从 URL 路径里取参数
- `@RequestParam`：从查询参数里取值

#### 项目例子

- 新增菜品时用 `@RequestBody DishDTO`
- 根据 id 查询详情时用 `@PathVariable Long id`
- 批量删除菜品时用 `@RequestParam List<Long> ids`

## 6. JWT 和登录校验怎么说

### 6.1 高频问题：你项目里的登录和权限校验是怎么做的？

#### 简洁回答

项目登录成功后，后端会生成 JWT 返回给前端。前端后续访问受保护接口时，会把 token 放到请求头里。后端通过拦截器统一校验 token，校验通过后再放行请求，同时把当前登录用户 id 保存到 `BaseContext`，方便后续业务代码使用。

#### 项目亮点补充

- 我们后面做公共字段自动填充时，就是通过 `BaseContext` 拿当前登录用户 id，然后自动给 `createUser` 和 `updateUser` 赋值的。

## 7. AOP 和公共字段自动填充怎么说

### 7.1 高频问题：你项目里 AOP 用在了什么地方？

#### 简洁回答

我在项目里用 AOP 做了公共字段自动填充。因为很多表在新增和修改时都要重复设置 `createTime`、`updateTime`、`createUser`、`updateUser`，如果把这些逻辑都写在 Service 里，会有很多重复代码。所以我通过自定义注解、切面和反射，在 Mapper 方法执行前统一完成这些字段的赋值。

### 7.2 高频问题：公共字段自动填充的实现思路是什么？

#### 简洁回答

实现思路是：

- 先自定义一个 `@AutoFill` 注解，标记哪些 Mapper 方法需要自动填充
- 再定义一个切面，拦截这些打了注解的方法
- 从注解里判断当前是新增还是修改
- 再结合 `BaseContext` 中保存的当前用户 id
- 通过反射调用实体类的 setter，自动设置公共字段

### 7.3 高频问题：为什么这里要用反射？

#### 简洁回答

因为切面拿到的参数是一个通用的 `Object`，它事先并不知道具体是 `Employee`、`Category` 还是 `Dish`。但这些实体类都约定好了同名的 setter 方法，所以可以通过反射在运行时动态找到这些方法并统一调用，这样一套逻辑就能复用到多个实体上。

#### 好背版本

- 不知道具体实体是谁
- 但知道它应该有哪些 setter
- 所以用反射统一处理

## 8. MyBatis 和动态 SQL 怎么说

### 8.1 高频问题：`#{}` 是什么？

#### 简洁回答

`#{}` 是 MyBatis 的参数占位写法，不是原生 MySQL 语法。它的作用是从 Java 方法传进来的参数中取值，然后在执行 SQL 时填进去。

#### 项目例子

比如：

```xml
status = #{status}
```

如果传进来的对象里 `status = 1`，那么执行 SQL 时就会把这个值填进去。

### 8.2 高频问题：什么是动态 SQL？

#### 简洁回答

动态 SQL 的核心思想是：

- 传了什么条件，就拼什么 SQL
- 没传的条件，就不拼

在我的项目里，菜品分页查询和动态更新都用了动态 SQL。比如修改菜品时，只有不为空的字段才会被更新，这样可以避免把原有字段误更新成 `null`。

### 8.3 高频问题：`<if>`、`<where>`、`<set>`、`<foreach>` 分别有什么用？

#### 简洁回答

- `<if>`：条件成立才拼接 SQL
- `<where>`：自动处理 where 和多余的 and/or
- `<set>`：自动处理 update 的 set 和多余逗号
- `<foreach>`：循环集合，常用于 `in (...)`

## 9. 菜品管理的一对多设计怎么说

### 9.1 高频问题：为什么菜品管理不是单表操作？

#### 简洁回答

因为菜品和口味是典型的一对多关系：

- 一条菜品对应一条 `dish` 主表记录
- 一条菜品可以对应多条 `dish_flavor` 子表记录

所以新增、修改、删除菜品时，不能只操作主表，还要联动处理口味表。

### 9.2 高频问题：为什么新增菜品时要先插主表，再插子表？

#### 简洁回答

因为子表 `dish_flavor` 里有 `dish_id` 字段，它要依赖主表 `dish` 的主键 id。只有先插主表，拿到生成的菜品 id，后面才能把这个 id 赋给每一条口味数据，再批量插入口味表。

### 9.3 高频问题：为什么修改菜品口味时选择“先删旧的，再插新的”？

#### 简洁回答

因为前端编辑口味时，可能会出现新增、删除、修改、顺序变化等多种情况。如果后端逐条判断差异，逻辑会比较复杂。考虑到子表数据量不大，所以采用“先删旧口味，再插入新口味”的方式更简单、更稳，也更容易维护。

### 9.4 高频问题：为什么删除菜品时不能只删主表？

#### 简洁回答

因为如果只删 `dish` 主表，不删 `dish_flavor` 子表，就会留下没有归属的口味记录，也就是孤儿数据。这种数据会污染数据库，也会给后续业务带来风险，所以删除时必须主表和子表一起处理。

## 10. 事务怎么说

### 10.1 高频问题：你的项目里事务用在了哪些场景？

#### 简洁回答

我在菜品新增、菜品修改、批量删除等涉及多步数据库操作的场景用了事务。因为这些业务往往不是只改一张表，而是需要联动多张表。如果中间某一步失败，就要整体回滚，避免出现半截数据。

### 10.2 高频问题：为什么 `saveWithFlavor()` 和 `updateWithFlavor()` 要加 `@Transactional`？

#### 简洁回答

因为这两个方法都涉及多步操作：

- 新增菜品时要先插 `dish`，再插 `dish_flavor`
- 修改菜品时要先更新主表，再删旧口味，再插新口味

如果没有事务，一旦中间出错，数据库就可能留下不完整数据。所以要用事务保证要么全成功，要么全失败。

#### 好背版本

- 多步操作
- 多表联动
- 不能接受半截成功
- 所以要加事务

## 11. 文件上传和本地图片方案怎么说

### 11.1 高频问题：你的项目里图片上传是怎么做的？

#### 简洁回答

我这个项目一开始课程思路是走云端对象存储，但在当前阶段我把它改成了本地上传方案。前端上传图片时，请求会打到 `POST /admin/common/upload`，后端用 `MultipartFile` 接收文件，给图片生成 UUID 文件名后保存到本地 `uploads` 目录，再把图片访问 URL 返回给前端。前端后续把这个 URL 作为菜品的 `image` 字段提交保存到数据库。

### 11.2 高频问题：为什么图片上传这里不用 `@RequestBody`？

#### 简洁回答

因为上传文件时，请求格式通常是 `multipart/form-data`，不是普通的 JSON 请求体，所以这里需要使用 `MultipartFile` 来接收文件，而不是 `@RequestBody`。

### 11.3 高频问题：为什么浏览器能直接访问 `/uploads/xxx.jpg`？

#### 简洁回答

因为我在 `WebMvcConfiguration` 里做了静态资源映射，把 `/uploads/**` 这个访问路径映射到了本地磁盘目录 `uploads`。这样浏览器访问这个 URL 时，Spring MVC 会直接去对应目录下找到文件并返回给浏览器。

### 11.4 高频问题：为什么上传图片成功不等于菜品保存成功？

#### 简洁回答

因为这是两次不同的请求：

- 第一次是上传文件，后端返回图片 URL
- 第二次是新增或修改菜品，把这个图片 URL 连同其他菜品信息一起保存进数据库

所以如果图片上传成功了，但菜品保存接口没有成功执行，数据库中的图片地址仍然不会更新。

## 12. 分页、查询、状态修改这些常见接口怎么说

### 12.1 高频问题：菜品分页查询你是怎么做的？

#### 简洁回答

我用了 PageHelper 做分页，Controller 接收分页参数后交给 Service，Service 中先调用 `PageHelper.startPage()` 开启分页，再调用 Mapper 查询。SQL 里通过动态条件支持按名称、分类、状态筛选，同时关联分类表查出 `categoryName`，最后统一封装成 `PageResult` 返回前端。

### 12.2 高频问题：为什么分页查询返回的是 VO，不是 Entity？

#### 简洁回答

因为分页页面不仅需要菜品本身的字段，还需要像 `categoryName` 这种展示字段，而这些字段并不完全属于数据库主表实体。所以更适合用 VO 来组织返回结果。

### 12.3 高频问题：起售/停售接口你是怎么实现的？

#### 简洁回答

我用了一个比较轻量的做法，只构造一个带 `id` 和 `status` 的 `Dish` 对象，然后调用动态更新 SQL。因为 SQL 里只会更新不为空的字段，所以可以只改状态，同时结合自动填充机制自动更新 `updateTime` 和 `updateUser`。

## 13. 删除前校验怎么说

### 13.1 高频问题：为什么删除菜品前还要做校验？

#### 简洁回答

因为数据库能删，不代表业务允许删。在我的项目里，删除菜品前会先判断两件事：

- 菜品当前是否处于起售状态
- 菜品是否已经被套餐关联

只有都满足条件时，才允许真正删除。这样更符合真实项目的业务规则。

#### 好背版本

- 先判断能不能删
- 再决定删不删
- 不是数据库能删就直接删

## 16. 套餐管理怎么说

### 16.1 高频问题：套餐管理和菜品管理最大的区别是什么？

#### 简洁回答

菜品管理主要是一条主表 `dish` 和它的口味子表 `dish_flavor` 的关系，而套餐管理更像是一个组合业务：

- 套餐本身有主表 `setmeal`
- 套餐和菜品之间还有关系表 `setmeal_dish`

所以套餐管理的重点不只是 CRUD，还包括：

- 主表和关系表联动保存
- 启售前业务校验
- 删除前业务校验
- 详情查询时的多表组装

### 16.2 高频问题：新增套餐你是怎么做的？

#### 简洁回答

新增套餐时，我不是只插一张 `setmeal` 表，而是分三步做：

- 先把前端传来的 `SetmealDTO` 转成 `Setmeal`
- 先插入套餐主表，拿到生成的套餐 id
- 再给每一条 `setmealDishes` 补上 `setmealId`，批量插入 `setmeal_dish`

整个过程加了事务，保证要么一起成功，要么一起回滚。

#### 好背版本

- 先插主表
- 拿到套餐 id
- 再插关系表
- 用事务保证一致性

### 16.3 高频问题：套餐启售为什么不能直接改状态？

#### 简洁回答

因为套餐能不能启售，不只取决于它自己，还取决于它里面的菜品状态。我的实现是：

- 先查这个套餐关联了哪些菜
- 再查这些菜当前是不是启售
- 只要有一道菜还在停售
- 就拒绝启售整个套餐

这样做是为了保证前台用户看到的套餐是可用的，不会出现“套餐启售了，但里面有菜其实不能卖”的情况。

### 16.4 高频问题：你项目里套餐启售失败的提示是什么？

#### 简洁回答

如果套餐里包含未启售菜品，我会抛业务异常，提示：

- `套餐内包含未启售菜品，无法启售`

这说明我这里不是单纯改一个状态字段，而是先做了业务规则判断。

### 16.5 高频问题：为什么删除套餐前也要做校验？

#### 简洁回答

因为数据库能删，不代表业务允许删。在我的项目里：

- 起售中的套餐不能删除

所以删除前会先查套餐状态：

- 如果是起售中，直接拦住
- 如果已经停售，才允许继续删除

#### 好背版本

- 先判断能不能删
- 起售中的套餐不让删
- 停售后才能真正删除

### 16.6 高频问题：为什么删除套餐时不能只删 `setmeal` 主表？

#### 简洁回答

因为套餐和菜品之间还有关系表 `setmeal_dish`。如果只删主表，不删关系表，就会留下没有归属的关联数据，形成脏数据。所以删除套餐时我做的是：

- 先删 `setmeal`
- 再删 `setmeal_dish`

这两个动作放在同一个事务里处理。

### 16.7 高频问题：套餐详情查询为什么返回的是一个大对象？

#### 简洁回答

因为前端编辑套餐时，不只是要看到套餐主信息，还要看到这个套餐里包含哪些菜、每道菜几份。所以详情查询不是只查一张表，而是：

- 先查 `setmeal` 主表
- 再查 `setmeal_dish` 关系表
- 最后把它们组装成一个完整的 `SetmealVO`

这样前端拿到一次响应，就能直接做表单回显。

### 16.8 高频问题：套餐修改为什么采用“删旧关系、插新关系”？

#### 简洁回答

因为套餐关联菜品在前端编辑时，可能会同时发生：

- 菜品新增
- 菜品删除
- 份数变化
- 顺序变化

如果后端逐条对比旧数据和新数据，逻辑会比较复杂。所以我采用了更稳的做法：

- 先更新套餐主表
- 再删除原来的 `setmeal_dish`
- 再把前端这次传来的新关系全部重新插入

这和我前面做菜品口味修改时的思路是一致的。

### 16.9 高频问题：套餐管理这一块你觉得最能体现项目含金量的点是什么？

#### 简洁回答

我觉得套餐管理最能体现项目含金量的地方在于，它已经不是简单的单表 CRUD 了，而是把几个真实项目里很常见的能力放到了一起：

- 主表和关系表联动保存
- 启售前业务校验
- 删除前业务校验
- 详情查询时的多表组装
- 修改时的事务式关系重建

所以这一块很适合在面试里体现我对业务规则和数据一致性的理解。

### 16.10 一个适合面试的套餐管理总结说法

可以这样说：

- 我在套餐管理模块里，不只是完成了新增、分页、起售停售、删除、详情、修改这些接口，更重要的是把套餐和菜品之间的关系表设计、启售前校验、删除前校验、详情组装和事务更新这几类真实业务问题都跑通了。这个模块让我真正练到了“多表联动 + 业务规则 + 事务一致性”这三个点。

## 17. 店铺营业状态和 Redis 怎么说

### 17.1 高频问题：为什么店铺营业状态这里用了 Redis，而不是 MySQL？

#### 简洁回答

因为店铺营业状态本质上只是一个很轻量的全局共享状态，比如：

- `1`：营业中
- `0`：打烊中

它会被管理端和用户端反复读取，所以我把它放在 Redis 里，用一个简单的 key-value 来存储。这样读写更轻量，也更适合这种配置型状态场景。

### 17.2 高频问题：Day5 这一块的业务链路是怎么走的？

#### 简洁回答

我在管理端提供了两个接口：

- 查询店铺营业状态
- 修改店铺营业状态

在用户端提供了一个接口：

- 查询店铺营业状态

管理端修改状态时，会把 `SHOP_STATUS` 写入 Redis；管理端和用户端查询状态时，读的也是 Redis 里的同一个 key。所以这块本质上是管理端和用户端共享同一份状态源。

#### 好背版本

- 管理端写 Redis
- 管理端读 Redis
- 用户端也读 Redis
- 三者共享同一个 `SHOP_STATUS`

### 17.3 高频问题：店铺营业状态这一块最能体现什么能力？

#### 简洁回答

我觉得这块最能体现的是，我开始不只是做数据库 CRUD，而是在项目里真正接入了 Redis，并把一个全局配置状态从管理端传递到用户端。它虽然接口不多，但很能体现我对状态型业务、中间件接入和前后端联动的理解。

### 17.4 一个适合面试的 Day5 总结说法

可以这样说：

- 在店铺营业状态这个模块里，我没有继续走传统数据库 CRUD 的思路，而是把一个全局共享状态放进 Redis。管理端负责修改和查询营业状态，用户端负责查询，同一份 `SHOP_STATUS` 被多个端共同读取。这一块让我第一次把 Redis 真正接进项目，也练到了状态型业务和中间件联调。

## 18. 用户端登录和鉴权怎么说

### 18.1 高频问题：你们小程序登录后，后端怎么识别当前用户是谁？

#### 简洁回答

小程序先通过 `uni.login()` 从微信拿到一个临时 `code`，前端把这个 `code` 发给后端。后端再拿 `code + appid + secret` 去调微信接口换取 `openid`，然后用 `openid` 查询本地 `user` 表，查不到就自动注册。登录成功后，后端会把本地 `user.id` 放进 JWT 返回给前端。前端后续请求带着 token，后端拦截器统一解析 token，取出 `userId` 后放进 `BaseContext`，这样后面的购物车和订单等业务就能识别当前用户。

#### 好背版本

- 前端拿 `code`
- 后端换 `openid`
- 用 `openid` 找本地 `user`
- 把本地 `user.id` 放进 token
- 拦截器再从 token 里解析出当前用户

### 18.2 高频问题：为什么 token 里放的是 userId，而不是 code 或 openid？

#### 简洁回答

因为 `code` 只是一次性临时登录凭证，不能长期使用；`openid` 虽然稳定，但业务系统后续更适合围绕本地 `user` 表主键来做关联。像购物车、地址、订单这些业务表，最终都是和本地 `user.id` 关联的，所以登录成功后我会把本地 `user.id` 放进 token，后续统一按这个 id 识别用户。

#### 好背版本

- `code` 太临时
- `openid` 属于微信体系
- 本地业务最终按 `user.id` 关联
- 所以 token 里放本地 `userId`

### 18.3 高频问题：用户端拦截器为什么会自动执行？

#### 简洁回答

因为我在 `WebMvcConfiguration` 里把 `JwtTokenUserInterceptor` 注册给了 Spring MVC，并配置了它要拦截的路径。项目启动时只是完成规则注册，真正收到匹配 `/user/**` 的请求时，Spring MVC 会自动回调这个拦截器的 `preHandle()` 方法。也就是说，这属于框架生命周期中的自动回调，不需要业务代码手动去调用。

#### 好背版本

- 启动时注册规则
- 请求到来时自动匹配
- 命中后 Spring MVC 自动调用 `preHandle()`

### 18.4 高频问题：为什么业务代码不让前端直接传 userId？

#### 简洁回答

因为前端参数是不可信的，如果允许前端自己传 `userId`，用户就可以伪造身份去查看甚至修改别人的购物车、订单等数据。所以我的做法是让前端只传 token，后端拦截器自行解析 token 拿到可信的 `userId`，再通过 `BaseContext` 在本次请求处理中共享给业务代码使用。

#### 好背版本

- 前端参数可伪造
- `userId` 不能信前端
- 必须后端自己解析 token 来确认身份

## 19. 用户端购物车怎么说

### 19.1 高频问题：购物车为什么不能只按 dishId 判重？

#### 简洁回答

因为购物车里的“同一项”不只是同一道菜，还要看是谁点的、选了什么口味。我的实现里，购物车判重至少基于：

- `userId`
- `dishId` 或 `setmealId`
- `dishFlavor`

比如同一个用户点了同一道菜，但一次选微辣、一次选不辣，这两条应该在购物车里分开显示，不能简单合并成数量加一。

#### 好背版本

- 不是只看菜品
- 还要看当前用户
- 还要看口味/规格

### 19.2 高频问题：购物车加购的核心逻辑是什么？

#### 简洁回答

我在加购时不是直接插一条记录，而是先把前端传来的菜品、套餐和口味信息转换成查询条件，再补上当前登录用户 `userId`，去购物车表里查有没有同一项。如果查到了，就只把数量加一；如果没查到，才去菜品表或套餐表补齐名称、图片、价格这些字段，然后新增一条购物车记录。

#### 好背版本

- 先查重
- 查到就 `update +1`
- 查不到再补齐信息并 `insert`

### 19.3 高频问题：购物车减购为什么不是一直 number - 1？

#### 简洁回答

因为当购物车里某一项数量只剩 `1` 时，再减一次就不应该保留一条 `number = 0` 的记录了。这样既不符合业务展示，也会留下脏数据。所以我的处理是：

- 如果数量大于 `1`，就执行数量减一
- 如果数量等于 `1`，就直接删除这条购物车记录

#### 好背版本

- 大于 `1`：`update -1`
- 等于 `1`：直接 `delete`
- 不保留 `number = 0` 的脏数据

## 21. Day7 商品缓存怎么说

### 21.1 高频问题：Day7 这一块你到底做了什么？

#### 简洁回答

Day7 我主要完成的是用户端商品缓存。具体来说，我把用户端菜品列表和套餐列表都接入了 Spring Cache + Redis：第一次按分类查询时会走数据库，后续相同分类请求会直接命中 Redis；管理端在新增、修改、删除、起售停售商品时，再通过 `@CacheEvict` 清理对应缓存，保证用户端下一次访问拿到的是最新数据。

#### 好背版本

- 用户端查商品先走缓存
- 首次查库，二次命中
- 管理端变更后清缓存
- 下次访问重新回库

### 21.2 高频问题：你们缓存的到底是什么？

#### 简洁回答

我们缓存的不是单个菜品对象，也不是整张商品表，而是“某个分类下的整份列表查询结果”。比如用户端请求 `/user/dish/list?categoryId=16`，缓存里的就是分类 `16` 下所有起售菜品及其口味的完整返回结果；套餐也是一样，缓存的是某个套餐分类下的列表结果。

#### 好背版本

- 缓存的不是单个对象
- 缓存的是“分类列表查询结果”
- 前端点哪个分类，就缓存哪个分类那一屏的数据

### 21.3 高频问题：为什么缓存 key 选择 categoryId，而不是 dishId 或 setmealId？

#### 简洁回答

因为这两个用户端接口本身就是“按分类查列表”，前端传给后端的核心查询条件就是 `categoryId`。缓存 key 设计应该跟查询维度保持一致，所以菜品列表按 `categoryId` 缓存成 `dishCache::categoryId`，套餐列表按 `categoryId` 缓存成 `setmealCache::categoryId`。如果用 `dishId` 或 `setmealId`，就和接口的查询粒度不一致了。

#### 好背版本

- 前端按什么条件查
- 缓存就优先按什么条件存
- 这里前端按分类查
- 所以缓存 key 也按分类 id 设计

### 21.4 高频问题：为什么缓存里天然只有起售中的菜品和套餐？

#### 简洁回答

因为用户端查询数据库时，就已经在条件里加了 `status = ENABLE`。也就是说，返回给前端的结果本身就只包含起售中的数据，而 Spring Cache 缓存的就是这个查询结果，所以缓存里天然也只会出现起售中的菜品和套餐，而不是先查全部再从缓存里做二次筛选。

#### 好背版本

- 先按起售状态查库
- 再把查询结果缓存起来
- 不是缓存全部再过滤

### 21.5 高频问题：为什么第二次请求时只有 JWT 日志，没有 Controller 日志和 SQL？

#### 简洁回答

因为 JWT 拦截器和缓存发生在请求链的不同层。请求进来后，Spring MVC 仍然会先执行用户端 JWT 拦截器做身份校验；但校验通过后，`@Cacheable` 已经在方法入口外层判断到 Redis 里有缓存了，所以 Controller 方法体不会继续执行，自然也就不会再打印业务日志和 SQL。

#### 好背版本

- JWT 先校验身份
- 缓存再决定要不要进方法体
- 命中缓存时 Controller 和 SQL 都不会再执行

### 21.6 高频问题：为什么管理端只改了一个菜品，却要清整个 dishCache？

#### 简洁回答

因为用户端缓存的粒度不是单个菜品，而是“某个分类下的一整份列表结果”。一个菜品状态、名称、排序或展示内容变化，都可能影响这个分类下的列表展示，所以我这里先采用 `@CacheEvict(allEntries = true)` 清整组缓存的策略。这样实现更简单，也更能优先保证一致性。

#### 好背版本

- 缓存粒度是分类列表
- 改一个菜也会影响整份列表
- 所以先清整组缓存
- 先保证一致性，再谈更细粒度优化

### 21.7 高频问题：菜品缓存和套餐缓存最大的区别是什么？

#### 简洁回答

两者本质上是同一个“按分类缓存列表”的模板，最大区别在首次查询复杂度。菜品列表查询除了查 `dish` 主表，还要把 `dish_flavor` 一起带出来，所以首次查库更重；套餐列表当前主要查的是 `setmeal` 主表列表，相对更轻。除此之外，两者的缓存命中、缓存失效、管理端清缓存思路都基本一致。

#### 好背版本

- 两者模板一样
- 都是按分类缓存列表
- 菜品查询更重，因为还要带口味
- 套餐列表相对更轻

### 21.8 一个适合面试的 Day7 总结说法

可以这样说：

- Day7 这一块我把 Redis 从“只存全局状态”升级到了“缓存高频读业务结果”。我在用户端菜品和套餐分类查询上接了 Spring Cache，第一次请求会查数据库，第二次相同分类请求直接命中 Redis；管理端对菜品和套餐做新增、修改、启停售时，再通过 `@CacheEvict` 清理缓存，保证用户端下次访问重新回库并重建缓存。这一阶段让我真正理解了缓存 key 设计、缓存命中、缓存失效和数据一致性。

## 22. Day14 Redis 工程化缓存怎么说

### 22.1 高频问题：Day14 这一块你到底做了什么？

#### 简洁回答

Day14 我不是重新把 Redis 接一遍，而是把项目里原本分散的缓存能力做了一次工程化升级。具体包括四块：第一，补齐了用户端分类列表缓存和管理端分类写后删缓存的完整闭环；第二，把 TTL、序列化和缓存异常兜底统一收口到 Redis 配置层；第三，在用户端地址簿按 id 查询上补了一版空值缓存，对不存在数据做短 TTL 防穿透；第四，在管理端营业额统计上补了按时间区间划分的结果级缓存，用来优化重复统计查询。这样项目就不只是“用了 Redis”，而是开始能讲缓存命中、一致性、穿透防护、结果级优化和运行态验证。

#### 好背版本

- 分类列表：首次查库，二次命中
- 管理端改分类：写后删缓存
- TTL / 序列化 / 兜底统一收口
- 地址簿补了空值缓存第一版
- 报表接口补了结果级缓存

### 22.2 高频问题：你怎么证明分类缓存真的命中了？

#### 简洁回答

我不是只看接口返回时间，而是带着证据链去验证。先手动清掉 `categoryCache::1`，确认 Redis 里没有这个 key；第一次请求 `/user/category/list?type=1` 后，Redis 里出现 `categoryCache::1` 且 TTL 大约 20 分钟；第二次再请求同样接口时，后端日志里不再出现分类查询日志和 SQL。也就是说，这次请求只经过 JWT 校验，后面的 Controller 方法体和数据库查询都没有再执行，这才是命中缓存最硬的证据。

#### 好背版本

- 先删缓存
- 第一次请求后 Redis 出现 key
- 第二次请求时 Controller 和 SQL 消失
- 这才叫真正命中缓存

### 22.3 高频问题：为什么你说不能只看耗时判断缓存命中？

#### 简洁回答

因为单次耗时会受很多因素影响，比如 JVM 冷启动、数据库连接池状态、网络波动、Redis key 是否刚好过期。Day14 这一轮我们就真实遇到了这种情况：空值缓存第二次请求因为已经超过 2 分钟 TTL，所以虽然 Redis 里之前有过 key，但请求还是重新回库了。如果只看时间，很容易误判。所以我更看重两类硬证据：第一，Redis key 和 TTL 是否按预期变化；第二，后端日志里 Controller 方法体和 SQL 是否真正消失。

#### 好背版本

- 时间会受很多环境因素影响
- TTL 过期也会让请求重新回库
- 真正硬的证据是 key / TTL 和日志 / SQL

### 22.4 高频问题：你们 Day14 的缓存穿透第一版是怎么做的？

#### 简洁回答

我先没有上布隆过滤器，而是选择了一个更适合当前项目、也更容易验证的第一版方案：空值缓存。落点放在用户端地址簿按 id 查询上。如果请求的是一个根本不存在的地址 id，Service 层会返回 `null`，但 Controller 最终返回的是 `Result.success(null)`。我把这个整个返回对象作为缓存值短暂写入 Redis，key 设计为 `userId:id`，TTL 设成 2 分钟。这样短时间内对同一个不存在地址 id 的重复请求，会直接命中 Redis，不再反复打数据库。

#### 好背版本

- 不存在地址也短暂缓存
- 缓存的是整个 `Result.success(null)`
- key 按 `userId:id`
- TTL 先设 2 分钟

### 22.5 高频问题：为什么空值缓存也要配短 TTL？

#### 简洁回答

因为第一版的目标只是挡住短时间内重复请求不存在数据时的回库压力，而不是把空结果长期保存在 Redis 里。TTL 太长会导致真实数据后来被补上时，缓存里的空结果还在；TTL 适当缩短，则可以在“减少穿透压力”和“避免空结果滞留太久”之间做一个更稳的平衡。所以我这里先把地址簿空值缓存的 TTL 设成 2 分钟。

#### 好背版本

- 目标是短时间挡穿透
- 不是长期缓存空结果
- TTL 太长会让空结果滞留
- 所以第一版先用 2 分钟

### 22.6 高频问题：你们为什么还做了报表结果缓存？

#### 简洁回答

因为报表接口和普通列表接口不一样，它往往不是“查一份现成数据”，而是“按时间区间做一轮统计计算”。像营业额统计这个接口，本身会从 `begin` 到 `end` 一天一天循环查库，再把每天的结果拼成 `TurnoverReportVO`。如果同一个时间区间被反复查询，每次都重新统计其实很浪费，所以我在这里补了结果级缓存，key 按 `begin:end` 设计。这样同一个时间区间的重复查询，就可以直接返回 Redis 里的统计结果。

#### 好背版本

- 报表接口重在“重复统计”
- 不是简单查一份列表
- 所以缓存的是“时间区间对应的统计结果”
- key 按 `begin:end`

### 22.7 高频问题：你怎么证明报表结果缓存真的生效了？

#### 简洁回答

我用的是一条比“只看快没快”更完整的证据链。先确认 Redis 里没有对应的 `turnoverReportCache` key，再第一次请求某个时间区间的营业额统计；请求之后 Redis 里会出现像 `turnoverReportCache::2026-08-01:2026-08-14` 这样的 key 和 TTL。然后我对同一时间区间再查一次，响应时间会明显下降，比如本地 Docker 真实链路下有一组数据是 `0.707692s -> 0.030966s`。另外我还补看了 MySQL `Questions` 的增量趋势：第一次新区间请求后从 `22` 升到 `43`，第二次同区间请求后只升到 `46`。这说明第二次请求已经不再重复走那轮按天统计主路径了。

#### 好背版本

- 先看 Redis 里没 key
- 第一次请求后出现 `turnoverReportCache::begin:end`
- 第二次同区间明显更快
- `Questions` 增量也明显变小

### 22.8 高频问题：为什么你说报表缓存比普通列表缓存更像后端优化题？

#### 简洁回答

因为普通列表缓存更多是在减少重复读同一份数据，而报表缓存优化的是“重复计算同一份结果”。营业额统计这类接口真正重的地方不在某一次单表查询，而在于它会按天循环、多次查库、最后再拼装结果对象。所以我这里缓存的不是原始表数据，而是“指定时间区间最终算出来的统计结果”。这种表达更贴近后端优化题里的思路：先识别高成本路径，再用缓存去减少重复计算。

#### 好背版本

- 列表缓存：减少重复读
- 报表缓存：减少重复算
- 我缓存的是“统计结果”，不是原始表
- 所以更像真实后端优化题

### 22.9 一个适合面试的 Day14 总结说法

可以这样说：

- Day14 这一块我把项目里的 Redis 从“已有缓存注解”升级成了更完整的工程化缓存能力。我先补齐了用户端分类列表的缓存命中链和管理端分类写后删缓存的一致性链路，再把 TTL、序列化和缓存异常兜底统一收口到 Redis 配置层。之后又在用户端地址簿按 id 查询上补了一版空值缓存，用短 TTL 缓存不存在数据的查询结果，降低相同无效请求短时间内反复回库的概率。最后我又给管理端营业额统计补了按时间区间划分的结果级缓存，把同区间重复查询从约 `708ms` 优化到约 `31ms`，并结合 Redis key、TTL、后端日志和 MySQL `Questions` 增量去验证缓存命中和数据库压力下降趋势。所以 Day14 真正沉淀下来的不是“会用 Redis”，而是缓存命中、一致性、穿透防护、结果级优化和证据化验证思路。

## 23. Spring Bean 和依赖注入怎么说

### 23.1 高频问题：Spring Bean 是什么？

#### 简洁回答

Spring Bean 本质上就是“交给 Spring 容器统一创建、统一管理、统一分发的对象”。在我的项目里，Controller、Service、拦截器、配置类这些对象都属于 Bean。正因为它们被 Spring 管起来了，项目里才可以通过 `@Autowired` 把不同层的对象自动注入到一起使用。

#### 好背版本

- Bean 就是被 Spring 托管的对象
- Spring 负责创建、管理、注入
- Controller、Service、拦截器、配置类都可以是 Bean

### 23.2 高频问题：`@RestController`、`@Service`、`@Component` 和 Bean 有什么关系？

#### 简洁回答

这些注解本质上都在告诉 Spring：“这个类交给你来管理”。区别只是语义层次不同：`@RestController` 主要用于控制层并表示返回 JSON，`@Service` 主要用于业务层，`@Component` 是更通用的组件标记。它们共同的结果都是让类变成 Spring Bean。

#### 好背版本

- 本质都和 Bean 注册有关
- `@RestController` 管控制层
- `@Service` 管业务层
- `@Component` 是通用版

### 23.3 高频问题：如果 Service 没加 `@Service` 会怎样？

#### 简洁回答

如果 Service 类没有加 `@Service`，Spring 容器就不会创建这个 Service Bean。这样 Controller 里通过 `@Autowired` 注入时就找不到对应对象，应用通常会在启动阶段直接报依赖注入失败，导致 Controller 和 Service 之间的调用链断掉。

#### 好背版本

- 不加 `@Service`
- Spring 不会创建 Service Bean
- `@Autowired` 注入失败
- 应用启动就可能报错

### 23.4 高频问题：为什么项目里 admin 和 user 下都能有同名 Controller？

#### 简洁回答

同名 Controller 在不同包下，Java 层面靠全限定类名区分，不会冲突；路由层面再通过 `/admin/**` 和 `/user/**` 的请求前缀隔开。真正需要注意的是 Spring Bean 命名冲突，所以像用户端 `DishController` 这类重名控制器，可以显式指定 Bean 名，比如 `@RestController("userDishController")`，从而避免和管理端默认 Bean 名撞上。

#### 好背版本

- Java 靠包名区分类
- 路由靠 `/admin` 和 `/user` 区分
- Bean 层如果重名，显式指定 Bean 名即可

### 24.7 高频问题：为什么提交订单不能简单理解成“插一条订单记录”？

#### 简洁回答

因为提交订单本质上是在把购物车里的临时数据转成正式订单数据。它至少包含四类动作：先根据登录态确定当前用户，再校验购物车和地址是否合法，然后写订单主表和订单明细表，最后清空购物车。所以它不是单表新增，而是一条完整的业务链。

#### 好背版本

- 先确定当前用户
- 再校验购物车和地址
- 再写订单主表和明细表
- 最后清空购物车
- 本质是把临时购物车数据转成正式订单数据

### 24.8 高频问题：为什么订单要拆成 `orders` 和 `order_detail` 两张表？

#### 简洁回答

因为订单主信息和商品明细天然不是同一种数据结构。订单号、用户、地址、状态、总金额这些是一张订单固定只有一份的数据，适合放在 `orders` 主表；而一张订单里买了什么、每样几份、什么口味，这部分条数是不固定的，天然是一对多关系，所以要单独放在 `order_detail` 里。拆开之后结构更清晰，也更符合后续详情、历史订单、再来一单这些查询和回填场景。

#### 好背版本

- `orders` 存固定的一份订单整体信息
- `order_detail` 存不固定的多条商品明细
- 一张订单对多条明细，天然就是一对多

### 24.9 高频问题：为什么订单里还要保存地址、手机号、收货人，而不是只存 `addressBookId`？

#### 简洁回答

因为地址簿会变化，但历史订单不能跟着变。订单里保存的是下单当时的收货信息快照，如果后面用户修改了地址簿，老订单依然应该保留下单时的地址、手机号和收货人。否则历史订单数据就会被污染。

#### 好背版本

- 地址簿会变
- 订单不能跟着变
- 订单要保留下单当时的收货信息快照

### 24.10 高频问题：为什么购物车当前更适合放 MySQL，而不是 Redis？

#### 简洁回答

因为购物车属于用户私有的强业务数据，不只是高频读结果，它后面还要参与正式下单，所以优先要保证持久化和数据一致性。像商品列表这种读多写少、丢了还能从数据库重建的数据更适合 Redis；购物车如果只放 Redis，会额外引入数据丢失风险和 Redis 与 MySQL 同步复杂度，对当前项目来说属于过度设计。

#### 好背版本

- 商品列表适合 Redis，因为高频读、可重建
- 购物车更像正式业务数据，优先放 MySQL
- 只放 Redis 会增加稳定性和一致性风险

### 24.11 高频问题：为什么支付要拆成 `payment()` 和 `paySuccess()` 两段？

#### 简洁回答

因为调起支付不等于支付成功。用户点击支付后，中间还可能出现取消支付、支付失败、网络超时、重复点击等情况，所以系统必须把“开始支付”和“确认支付成功后的状态更新”拆开。`payment()` 负责校验订单能不能支付、记录支付方式并返回支付参数；`paySuccess()` 才是真正把订单从待付款改成已支付后的统一状态流转入口。

#### 好背版本

- 调起支付不等于支付成功
- `payment()` 负责开始支付
- `paySuccess()` 负责支付成功后的状态更新
- 这样业务状态才不会乱

### 24.12 高频问题：什么叫幂等性？为什么支付场景特别需要它？

#### 简洁回答

幂等性指的是同一个操作执行一次和执行多次，最终结果应该一致，不应该因为重复执行产生额外副作用。支付场景特别容易出现前端重复点击、网络重试、第三方支付重复回调、后端补偿重放等情况，所以支付成功逻辑必须做幂等保护。比如当前项目里，如果订单已经是“已支付 + 待接单”，就直接返回，不再重复更新状态。

#### 好背版本

- 幂等性就是同一操作多次执行，结果仍一致
- 支付最怕重复点击、重复回调、网络重试
- 所以支付成功逻辑必须防重复处理

### 24.13 高频问题：真实微信支付里，为什么订单最终是否成功不能只信前端？

#### 简洁回答

因为前端不是最终可信方。前端可能被篡改、断网、关闭页面，或者只拿到了局部结果。真实微信支付里，更可靠的方式是以后端收到支付平台异步回调为准。也就是说，前端负责发起支付和拉起支付面板，后端则以后续回调通知来确认最终支付成功并更新订单状态。

#### 好背版本

- 前端只负责发起支付
- 前端不是最终可信方
- 真正可靠的是支付平台对后端的异步回调

### 24.14 高频问题：什么叫异步？什么叫回调接口？

#### 简洁回答

异步可以理解成“我先把事情发出去，不站在原地等最终结果，结果到了再处理”。回调接口则是“我先留一个通知入口，等对方处理完，再主动回来告诉我结果”。在微信支付里，用户发起支付后，微信不会把最终结果同步锁死在当前请求里，而是由微信服务器在支付完成后，主动请求我们后端预留的回调接口，把支付结果通知回来。

#### 好背版本

- 异步：先发出去，结果稍后处理
- 回调接口：提前留个入口，让对方处理完回来通知我
- 微信支付成功后，微信服务器会回调后端

### 24.15 高频问题：为什么支付链更适合用 `orderNumber/outTradeNo`，而不是 `orderId`？

#### 简洁回答

因为 `orderId` 更像系统内部数据库主键，只适合内部表关联；而 `orderNumber/outTradeNo` 是对外业务单号，适合传给第三方支付平台，也适合在回调时跨系统定位订单。微信并不知道你数据库里的自增主键是多少，它只认你下单时传给它的商户订单号。

#### 好背版本

- `orderId` 是内部主键
- `orderNumber/outTradeNo` 是对外业务单号
- 支付平台只认业务单号，不认数据库自增 id

### 24.16 高频问题：你项目里真实微信支付的主流程是什么？

#### 简洁回答

真实微信支付里，前端先把订单号交给后端 `payment()`，后端校验订单后，根据订单号、支付金额和当前用户的 `openid` 向微信下单，拿到前端拉起支付所需参数后再返回给小程序。前端调用 `uni.requestPayment(...)` 让用户确认支付。支付完成后，微信服务器通过异步回调通知我们的后端接口，后端根据回调里的 `out_trade_no` 找到订单，再统一执行 `paySuccess()` 更新订单状态。

#### 好背版本

- 后端先向微信下单
- 前端拉起微信支付面板
- 微信支付完成后回调后端
- 后端再更新订单状态

### 24.17 高频问题：真实商户环境拿不到时，你是怎么保证支付模块还有项目价值的？

#### 简洁回答

### 24.18 高频问题：Day8 你遇到过哪些最值得讲的问题？

## 25. Day10 WebSocket 实时提醒怎么说

### 25.1 高频问题：Day10 这一块你到底做了什么？

#### 简洁回答

Day10 我围绕订单域打通了一条实时提醒闭环。具体来说，用户在小程序里发起催单后，请求先进入后端订单业务层，后端会先校验当前用户、订单归属和订单状态，确认这次催单合法后，再组装一条 JSON 消息，并通过 WebSocket 广播给当前在线的管理端页面。管理端收到提醒后，不只是弹一个通知，还能继续查询订单详情并执行接单、派送、完成等处理动作。

#### 好背版本

- 用户端发起催单
- 后端先校验订单是否合法
- 再组装消息并通过 WebSocket 广播
- 管理端实时收到提醒
- 提醒后还能继续处理订单

### 25.2 高频问题：为什么这里要用 WebSocket，而不是普通 HTTP？

#### 简洁回答

因为这个场景需要服务端主动把消息推给管理端。如果只用普通 HTTP，管理端只能不停轮询后端问“有没有新提醒”，这样实时性差，请求也更浪费。WebSocket 建立长连接后，后端一旦有催单或来单消息，就可以直接推给当前在线的管理端页面。

#### 好背版本

- 这个场景要后端主动推消息
- 轮询也能做，但不够实时、还更浪费
- WebSocket 更适合做管理端实时提醒

### 25.3 高频问题：WebSocket 在你项目里的作用到底是什么？

#### 简洁回答

WebSocket 在我这个项目里，主要承担的是管理端实时提醒通道。管理端页面打开时会先建立 WebSocket 连接，后端把这条连接登记进在线连接表；用户催单后，后端把提醒消息广播给这些在线连接，于是管理端页面就能第一时间收到消息、弹提醒、播放提示音，并进入订单处理链。

#### 好背版本

- 页面先连 WebSocket
- 后端维护在线连接表
- 用户催单后广播提醒消息
- 管理端第一时间收到并继续处理订单

### 25.4 高频问题：WebSocket 底层是 TCP 还是 UDP？

#### 简洁回答

WebSocket 底层建立在 TCP 之上，不是 UDP。它的实时性主要来自长连接和服务端主动推送，而它的稳定性主要依赖 TCP 的可靠传输能力。

#### 好背版本

- WebSocket 用的是 TCP
- 实时感来自长连接和主动推送
- 稳定性主要靠 TCP

### 25.5 高频问题：`SESSION_MAP` 里保存的是什么？

#### 简洁回答

`SESSION_MAP` 存的不是管理员账号对象，而是 `sid -> Session` 的映射关系，也就是“客户端标识”对应的“WebSocket 连接对象”。后端后面广播消息时，真正依赖的是这些在线连接，而不是直接按账号对象推送。

#### 好背版本

- 不是存管理员账号
- 是存 `sid -> Session`
- 本质是在线连接表

### 25.6 高频问题：为什么 `sendToAllClient()` 发消息前还要检查连接状态？

#### 简洁回答

因为在线连接表里理论上保存的是当前可用连接，但实际网络环境里，某些连接可能已经断开、失效或者状态不同步。如果不先检查连接是否为空、是否还打开，就可能往一条已经失效的连接发消息，这样既没意义，也可能报错、浪费资源。所以广播前先校验连接状态，并顺手清理失效连接，会更稳。

#### 好背版本

- 先确认连接还活着
- 失效连接就清掉
- 避免无意义发送和广播报错

### 25.7 高频问题：为什么 `reminder()` 不是一上来就发 WebSocket？

#### 简洁回答

因为实时提醒也必须受业务规则约束。后端不能只因为前端点了催单按钮，就直接广播消息，而是要先确认当前用户是谁、订单是否存在、是否属于当前用户、当前状态是否允许催单。只有这些都通过，这次催单才是合法业务动作，后面才有资格被转换成一条实时提醒消息。

#### 好背版本

- 先判断这次催单合不合法
- 合法了才组装消息并广播
- 不是按钮一按就直接推送

### 25.8 高频问题：为什么 Day10 不能只做到“会弹提醒”？

#### 简洁回答

因为提醒本身不是业务终点，它只是订单处理链的入口。如果管理端只能看到提醒，却不能继续查看订单详情、执行接单、派送、完成等动作，那这条链最多只是“通知链”，还不是完整业务闭环。Day10 真正有价值的地方，是把“实时提醒”和“订单状态流转”接在了一起。

#### 好背版本

- 提醒不是终点
- 提醒后还得能处理订单
- 否则只是通知链，不是完整闭环

### 25.9 高频问题：为什么 `confirm()`、`delivery()`、`complete()` 都要先校验状态？

#### 简洁回答

因为订单状态流转必须受业务规则约束，不能任意跳状态。比如只有待接单的订单才能接单，只有已接单的订单才能进入派送中，只有派送中的订单才能完成。如果不做状态校验，就可能出现已取消订单还能派送、已完成订单再接单这类错误，整个订单链就会乱掉。

#### 好背版本

- 每个动作都只能发生在正确阶段
- 接单、派送、完成要一步一步走
- 不校验状态，订单流转就会乱

### 25.10 高频问题：Day10 这一块最值得讲的排障案例是什么？

#### 简洁回答

最值得讲的是：手工 `new WebSocket(...)` 能连通，但管理端页面自动连接却失败。这个现象说明后端 WebSocket 端点并不是完全坏的，问题更可能出在管理端前端自动连接逻辑。后来通过读取运行中的静态 bundle 和 sourcemap，最终定位到自动连接地址写错，修成根据当前页面 `location.host` 动态拼接后，管理端才真正恢复自动收提醒。同时浏览器缓存还会制造“明明改了、第一次打开还是旧效果”的假象，所以后来又沉淀出 `Ctrl + F5` 强刷这个重要经验。

#### 好背版本

- 手工连得通，不代表页面自动连接就对
- 最后定位到前端运行包里的 WebSocket 地址写错
- 修完后还要警惕浏览器缓存带来的假象

### 25.11 一个适合面试的 Day10 总结说法

可以这样说：

- Day10 这一块，我不是只接了一个 WebSocket，而是围绕订单域打通了一条实时提醒闭环。用户在小程序里发起催单后，后端会先校验当前用户身份、订单归属和订单状态，确认这次催单合法后，再组装成 JSON 消息，并通过 WebSocket 广播给当前在线的管理端页面。管理端收到提醒后，不只是弹一个通知，还能继续进入订单详情页并执行接单、派送、完成等处理动作。所以这一块最终形成的是“实时通知 + 订单状态流转”的完整业务闭环，而不是单纯的前端弹窗效果。

## 26. Day11 数据统计与图形报表怎么说

### 26.1 高频问题：Day11 这一块你到底做了什么？

#### 简洁回答

Day11 我主要完成的是管理端报表统计模块。具体来说，我围绕时间区间统计补齐了 4 个接口：

- 营业额统计
- 用户统计
- 订单统计
- 商品销量 Top10

这些接口后面都完成了 APIFox 验证，前端图表页也已经能正常显示，所以这一块最终不是只把 SQL 查出来，而是把统计结果真正接成了可展示的图表能力。

#### 好背版本

- 补了 4 个报表接口
- 做了时间区间统计和聚合查询
- 接口调通了
- 管理端图表也真正显示出来了

### 26.2 高频问题：为什么我会说 Day11 的难点不在 Controller？

#### 简洁回答

因为 Controller 在这一块里主要只是接 `begin/end` 参数、调用 Service、返回结果。真正复杂的是 Service 层要按报表口径拆时间区间、逐天统计、计算派生指标，再把结果组装成前端图表接口需要的结构。所以 Day11 的核心难点不在“写出 4 个接口”，而在“把统计结果加工成图表数据”。

#### 好背版本

- Controller 只负责接参数和返回结果
- 真正复杂的是 Service 层的数据加工
- 报表的难点在口径和结构，不在接口壳子

### 26.3 高频问题：Day11 的核心分层该怎么说？

#### 简洁回答

这块我会分成三层来讲：

- Controller：暴露 4 个报表接口
- Service：负责按报表口径组装数据
- Mapper：负责底层聚合查询

比如 `countByMap()`、`sumByMap()` 和 Top10 的联表聚合，Mapper 只负责查基础结果；而像按天循环、订单完成率计算、`dateList/turnoverList` 这些图表结构拼装，都放在 Service 层完成。

#### 好背版本

- Mapper 查基础统计
- Service 按业务口径加工
- Controller 对外提供接口

### 26.4 高频问题：为什么前三个统计接口都要按天循环？

#### 简洁回答

因为营业额、用户统计和订单统计这三类图表，本质上都是趋势图。前端不是只想知道整个区间的一个总数，而是想知道“每一天分别是多少”，这样才能画折线图或趋势图。所以后端必须把 `begin ~ end` 拆成一天一天，每天单独统计一次，再把结果拼成列表返回。

#### 好背版本

- 前三个接口要的是趋势图
- 趋势图需要每天一份数据
- 所以后端必须按天循环统计

### 26.5 高频问题：为什么要把“一天”转换成完整时间区间？

#### 简洁回答

因为数据库里像 `order_time`、`create_time` 这类字段存的是带时分秒的 `LocalDateTime`，不是纯日期。前端传过来的 `2026-06-02` 只是一个自然语言意义上的“某一天”，但数据库真正能比较的是具体时刻。所以后端要把一天翻译成：

- 开始时刻 `2026-06-02 00:00:00`
- 结束时刻 `2026-06-02 23:59:59.999999999`

这样才能把当天所有数据完整框进去。

#### 好背版本

- 数据库存的是具体时刻，不是模糊的一天
- 所以要把一天翻译成起点时刻和终点时刻

### 26.6 高频问题：用户统计这一块最值得讲什么？

#### 简洁回答

用户统计这块最值得讲的是，同一天里其实要查两种口径：

- 当天新增用户数
- 截止当天的累计总用户数

所以它不是简单 `count(*)` 一次就完了，而是通过动态条件查询同一个 Mapper 方法，分别统计“区间内新增”和“截止累计”。这个点很能体现我对报表口径的理解。

#### 好背版本

- 同一天要查新增和累计两种口径
- 难点不在 count，而在知道这次 count 的业务含义

### 26.7 高频问题：订单统计这一块最值钱的点是什么？

#### 简洁回答

订单统计最值钱的点在于，它除了查每天总订单数和每天有效订单数，还要在 Service 层进一步算出整个时间区间的订单完成率。也就是说，Mapper 负责基础计数，Service 负责把这些基础结果加工成业务指标。这一点非常适合体现“SQL 查询”和“业务指标计算”之间的分工。

#### 好背版本

- 先查总订单数和有效订单数
- 再在 Service 层算完成率
- Mapper 查基础数据，Service 算业务指标

### 26.8 高频问题：为什么 Top10 不用按天循环？

#### 简洁回答

因为 Top10 要解决的不是趋势问题，而是排行问题。前三个接口要的是“每天各是多少”，所以要按天拆；Top10 要的是“整个时间段里哪些商品卖得最多”，所以直接对整个区间做一次联表聚合、分组求和、排序取前 10 就够了。

- Top10 是排行图

这次 Day11 很真实的一点是，调试过程中不只有业务代码问题，还混进了环境问题，比如 Redis 没启动、token 过期、Druid 清理长时间空闲连接等。后来我学到的一点是，联调排错一定要先分层：先判断是认证问题、环境问题还是当前业务链的问题，不能看到日志报错就直接认为是新写的报表代码炸了。

## 28. Day15 限量套餐活动怎么说

### 28.1 高频问题：Day15 这一块你到底做了什么？

#### 简洁回答

Day15 我主要补了一条“限量套餐活动”的高并发资源竞争链路。具体来说，我新增了活动管理和用户抢购这两端能力：管理端可以创建、启停和查看活动，用户端可以在小程序看到活动、发起抢购和查看自己的抢购记录。技术上核心是用 Redis 预热活动状态和库存，再用 Lua 脚本一次性完成活动时间、状态、库存和一人一单的原子校验，最后再把成功结果持久化到 MySQL。

#### 好背版本

- 做了限量套餐活动
- 管理端能创建和启停
- 小程序能看到活动并抢购
- 核心技术是 Redis + Lua 原子校验 + MySQL 落库

### 28.2 高频问题：为什么这块不能只靠数据库来做？

#### 简洁回答

因为限量抢购是典型的热点竞争场景，如果把活动状态判断、库存校验、重复抢购校验和库存扣减都直接压到数据库，数据库会承受很集中的竞争压力，而且多段逻辑拆开做时还会有并发窗口。所以我把这些高频判断前移到 Redis，通过 Lua 脚本在 Redis 内一次执行完，再把结果落到数据库。

#### 好背版本

- 不能把所有竞争都压给数据库
- 数据库压力会很集中
- 多段逻辑拆开还会有并发窗口
- 所以先在 Redis 里原子抢资格

### 28.3 高频问题：为什么 Lua 比 Java 里多次调用 Redis 更稳？

#### 简洁回答

因为如果在 Java 里先查库存、再查用户资格、再扣库存、再写用户状态，这几个 Redis 操作之间会有窗口期；而 Lua 脚本是在 Redis 内部一次执行完这些动作，对 Redis 来说是原子的，更适合这种高并发热点竞争场景。

#### 好背版本

- Java 里多次调 Redis 会有窗口期
- Lua 在 Redis 内一次执行完
- 原子性更强，更适合抢购场景

### 28.4 高频问题：一人一单是怎么做的？

#### 简洁回答

我做了双层保护。第一层是在 Redis 里用 Set 记录当前活动已经抢购成功的用户，Lua 脚本先判断当前用户是不是已经在这个集合里；第二层是在数据库抢购记录表上加 `activity_id + user_id` 唯一约束，作为最终落库兜底。这样既能前置拦截热点重复请求，也能避免极端情况下出现重复成功记录。

#### 好背版本

- Redis Set 先拦一遍
- 数据库唯一约束再兜一遍
- 前者负责高并发拦截，后者负责最终落库保险

### 28.5 高频问题：如果 Redis 先扣成功了，但数据库落库失败怎么办？

#### 简洁回答

这个场景我专门做了回补。因为 Lua 脚本成功后，Redis 里的库存已经减了，用户也被记进已抢购集合了；如果后面的数据库更新库存或插抢购记录失败，系统会把 Redis 库存加回去，并把这个用户从已抢购集合里移除，避免 Redis 和 MySQL 状态不一致。

#### 好背版本

- Redis 成功不等于整条业务真正成功
- MySQL 失败时要回补 Redis
- 把库存加回去，再把用户移出已抢集合

## 29. Day16 RocketMQ 削峰异步化 + 延迟关单怎么说

### 29.1 高频问题：Day16 这一块你到底做了什么？

#### 简洁回答

Day16 我主要把项目里的两条典型交易链接到了 `RocketMQ` 上。第一条是把 Day15 的限量套餐抢购链从“Redis 抢资格 + MySQL 同步落库”升级成了“Redis 抢资格 + MQ 异步落库”；第二条是给订单域补了延迟消息，实现超时未支付自动关单。这样项目就不只是用了 Redis，而是进一步具备了“削峰异步”和“延迟处理”这两类更像真实交易系统的能力。

#### 好背版本

- 抢购链接了 MQ，改成异步落库
- 订单链接了延迟消息，支持超时自动关单
- Day16 的核心就是削峰异步 + 延迟处理

### 29.2 高频问题：为什么抢购链要从同步落库改成异步落库？

#### 简洁回答

因为抢购场景真正最重要的是先快速完成资格判定，而不是把所有数据库写操作都堆在接口主链上。Day15 已经把高并发资格校验前移到了 Redis，但如果抢购成功后还要同步扣活动表库存、插抢购记录，那么高峰时段数据库压力还是会继续压在接口响应时间上。所以 Day16 的做法是：Redis 先抢资格，成功后立即发送消息，数据库副作用交给消费端异步完成。

#### 好背版本

- 抢购主链应该先抢资格、快返回
- 不该把所有写库动作都压在接口主链上
- 所以改成 Redis 抢资格 + MQ 异步落库

### 29.3 高频问题：Day16 抢购异步链的完整执行顺序是什么？

#### 简洁回答

顺序可以概括成四步：

- 用户请求抢购
- Redis + Lua 原子判断活动状态、库存和一人一单，并先预扣资格
- 如果成功，生产者发送抢购落库消息，接口立即返回
- 消费端收到消息后，再异步扣 MySQL 活动库存并插入抢购记录

也就是说，主链路只保留 Redis 抢资格和 MQ 投递，数据库持久化被移到了消费端。

#### 好背版本

- Redis 先抢资格
- MQ 再接住后半段
- 消费端异步落 MySQL

### 29.4 高频问题：为什么你会强调“offset 前进不等于业务成功”？

#### 简洁回答

因为我在 Day16 真实踩到过这个坑。第一次联调时，RocketMQ topic 里有消息，consumer progress 也前进了，但 MySQL 库存和抢购记录都没变化，业务成功日志也没有。这个现象说明：位点前进只能证明框架层消息流转发生过，不能证明你的事务逻辑真的成功了。后来我把最终判断标准改成“三侧证据闭环”：

- 数据库有没有变化
- 业务成功日志有没有出现
- Redis / DB / 日志能不能对得上

#### 好背版本

- offset 动了，只能说明消息流转过
- 真正业务成功还得看 DB 和业务日志
- Day16 这个坑我是真踩过

### 29.5 高频问题：为什么后来要把消费逻辑拆进独立 Service？

#### 简洁回答

因为 Day16 两条 MQ 链第一次失败时，问题都出在“listener 看起来收到了消息，但业务副作用没有稳定落地”。所以我最后把职责拆成了两层：

- listener 只负责接消息和打接收日志
- 真正带事务的业务逻辑放进独立 Service

这样一来，消息接收和事务落库的职责就分开了，排障路径和日志也都更清楚。

#### 好背版本

- listener 负责收消息
- service 负责真正落业务
- 这样职责更清楚，事务也更稳

### 29.6 高频问题：抢购异步消费侧怎么做幂等？

#### 简洁回答

我在消费抢购落库消息时，先按 `activityId + userId` 去查抢购记录表。如果这条记录已经存在，就直接跳过，不再重复扣库存和插记录。这样可以防止 RocketMQ 重试或重复消费时再次产生副作用。

#### 好背版本

- 先查这名用户在这个活动里是不是已经成功过
- 有记录就直接跳过
- 防止重复消费导致重复落库

### 29.7 高频问题：延迟关单为什么适合用 MQ 延迟消息，而不是一直靠定时任务扫表？

#### 简洁回答

因为超时关单这种问题天然就是“现在先不处理，等未来某个时间点再处理”。如果一直靠定时任务扫表，精度会受扫描间隔影响，而且会产生很多无效数据库扫描。MQ 延迟消息更适合这种场景：订单创建时就预约一条未来消息，到点后再消费并处理，这样更接近“精准触发”。

#### 好背版本

- 定时任务是一直扫
- 延迟消息是提前预约，到点再处理
- 对超时关单这种场景更自然

### 29.8 高频问题：延迟关单为什么还要在消费端二次校验订单状态？

#### 简洁回答

因为从订单创建到延迟消息真正到达，这中间存在时间差，订单状态可能已经变了。比如用户可能已经付款，或者订单已经被其他流程取消。所以消费端不能到点就无脑取消，而是必须先重新查订单，确认它仍然是“待付款 + 未支付”，只有这种情况下才真正执行自动取消。这样才能避免误关单。

#### 好背版本

- 延迟消息到的时候，订单状态可能已经变了
- 所以不能到点就直接取消
- 必须先查当前状态，再决定要不要关单

### 29.9 高频问题：Day16 这一块最值得讲的验证证据是什么？

#### 简洁回答

我拿到的是两条真实链路都跑通后的证据。抢购异步链里，用户抢购成功后 Redis 先把库存从 `2` 变成 `1`，随后 MySQL 活动库存也从 `2` 变成 `1`，抢购记录表新增一条记录，同时日志里能看到“发送成功 -> 收到消息 -> 消费成功”的完整闭环。延迟关单链里，订单提交后先是待付款，等待十几秒后自动变成已取消，并写入“支付超时，系统自动取消”的原因和取消时间。

#### 好背版本

- 抢购链：Redis 先变，MySQL 后变，日志闭环完整
- 关单链：先待付款，约 `10s` 后自动变已取消
- 这不是理论设计，是我真实跑通过的

### 29.11 Day16 额外高价值存档：`onMessage(...)` 为什么会自动执行

这个点不是最终话术成品，但非常值得存档，后面单独整理正式话术时大概率会用到。

要点：

- `FlashSaleOrderCreateConsumer.onMessage(...)`
- `OrderDelayCloseConsumer.onMessage(...)`

都不是业务代码手动调用的。

真正的执行机制是：

1. Spring 启动时先把 consumer 注册成 Bean
2. `@RocketMQMessageListener` 告诉 RocketMQ Spring 组件：
   - 监听哪个 topic
   - 使用哪个 consumerGroup
3. RocketMQ 创建监听容器
4. topic 来消息后，由监听容器自动回调 `onMessage(...)`

这个点适合后续整理成：

- “为什么这个方法没人显式调用也会执行”
- “RocketMQListener 和 Spring Bean / 容器回调是什么关系”

### 29.12 Day16 额外高价值存档：幂等到底该怎么讲

这个点要单独存，因为它非常容易在面试里被追问。

高价值表述素材：

- 幂等不是“绝对不让重复来”
- 幂等是“即使重复来，最终副作用也不能重复发生”
- MQ 场景下，consumer 必须默认消息可能重试、重投或重复消费

结合项目最适合讲的例子：

- 抢购异步落库链里，如果没有幂等，重复消费一次就可能：
  - 多扣一次 MySQL 活动库存
  - 多插一条抢购记录

当前项目里的幂等抓手是：

- `activityId + userId`

落点文件：

- [FlashSaleAsyncPersistenceService.java](file:///D:/ProgramFiles/CodeProjects/PeakSend/peaksend-backend/sky-server/src/main/java/com/sky/service/FlashSaleAsyncPersistenceService.java)

关键逻辑：

- 先查这名用户在该活动里是否已有成功订单
- 如果已有，就直接跳过，不再重复扣库存、重复插单

延迟关单链里对应的高价值素材：

- 它不完全是“查是否已有记录”式幂等
- 更像“状态幂等保护”
- 只有订单当前仍是“待付款 + 未支付”才允许关单
- 如果订单已支付或已流转，重复消息来了也会直接跳过

后面整理正式话术时可以抽成：

- 幂等定义
- 为什么 MQ 场景必须做幂等
- 抢购链的幂等怎么设计
- 延迟关单链的状态幂等怎么设计

### 29.14 Day16 额外高价值存档：重启后暴露出的两个运行态问题

这两个点都很值钱，后面正式整理话术时未必全部展开，但现在必须先存下来。

#### 1）nginx 握着旧 backend IP，导致 502

现象：

- backend 容器已经正常启动
- 管理端接口却返回 `502`

最终定位：

- nginx upstream 仍在往旧 backend 容器 IP 转发

处理：

- 重启 nginx，让它重新解析 `backend`

价值：

- 说明容器化环境里的问题，不一定来自后端代码
- 网关/运行态组件也可能握着旧解析结果

#### 2）Redis 活动缓存重启后丢失，但请求可自动触发回源重建

现象：

- `flashsale:activity:5` 和用户集合 key 在 Redis 中消失

后续验证：

- 再次请求活动后，没有报“活动不存在”
- 而是正确返回“活动已结束”
- 再查 Redis，相关 key 已被重建

价值：

- 说明 `ensureActivityCacheLoaded(activityId)` 这条兜底逻辑真实生效
- 当前系统具备“缓存丢失后自动恢复”的运行态韧性
- 这类问题也应该被归档进全局文档，因为它已经不只是某个接口 bug，而是部署态和缓存韧性的真实证据

### 30.2 高频问题：为什么 Day17 不是一上来就拆 order / product，而是先上 Nacos + Gateway？

因为微服务不是把包拆散就结束了。

如果没有：

- 注册发现
- 统一入口
- 容器里的稳定寻址方式

那你后面拆出来的服务，只会立刻遇到两个问题：

- 请求到底先进谁
- 服务之间到底怎么找彼此

所以 Day17 先做的是：

这个点在面试里很值钱，因为它说明你理解的是：

- 微服务是先建设基础设施，再逐步拆业务

而不是：

- 先拆出几个模块名，看起来像微服务就算了

### 30.3 高频问题：Nacos 和 Gateway 分别解决什么问题？

`Nacos` 解决的是：

- 服务在哪

也就是：

- `sky-server` 启动后去 Nacos 报到
- `gateway` 要找 `sky-server` 时，不写死 IP，而是去 Nacos 查服务名

所以 Nacos 更像：

- 服务通讯录
- 地址簿

`Gateway` 解决的是：

- 请求先进谁统一处理

也就是：

- 管理端 `/api/**`
- 用户端 `/user/**`
- WebSocket `/ws/**`

都先收口到 `gateway`

然后再由 `gateway` 决定：

- 该转给哪个服务
- 转发前路径要不要改写

所以 Gateway 更像：

- Java 微服务体系里的统一入口

一句话区分：

- `Nacos` 负责“找人”
- `Gateway` 负责“带路”

### 30.4 高频问题：Day17 一次真实请求到底是怎么走的？

拿这条请求举例：

- `http://localhost:8081/api/flashSaleSetmealActivity/list`

完整链路是：

1. 浏览器先把请求打到 `nginx`
2. `nginx` 识别这是 `/api/**` 路径
3. `nginx` 把请求转发给 `gateway`
4. `gateway` 命中 `admin-route`
5. `gateway` 把路径从：
   - `/api/flashSaleSetmealActivity/list`
   - 改写成
   - `/admin/flashSaleSetmealActivity/list`
6. `gateway` 去 `Nacos` 查：
   - `sky-server` 在哪
7. 找到后把请求转给 `sky-server`
8. `sky-server` 进入鉴权与业务处理逻辑

这条链最值得讲的地方不是“多了一跳”，而是：

- 外层入口和内部路由分层了
- 服务地址不再靠写死 IP
- 旧的 `/admin/**` 后端接口没有被推翻，而是通过网关层兼容改写接了进来

### 30.5 Day17 额外高价值存档：为什么返回 `401` 反而说明链路通了？

Day17 当前阶段的代表性验证之一是：

- 访问 `http://localhost:8081/api/flashSaleSetmealActivity/list`
- 返回的是 `401`

这个结果很容易被误判成：

- 请求失败了

但在基础设施验证阶段，它反而是好证据。

原因是：

- 如果链路没通，更常见看到的是：
  - `502`
  - `404`
  - 连接失败
- 现在返回 `401`
  - 说明请求已经穿过：
    - `nginx`
    - `gateway`
    - 最后进入了 backend 鉴权层

所以这类结果更适合后面整理成一句工程表达：

- Day17 基础设施链路已经真实贯通，当前外部请求可以稳定进入后端鉴权层。

### 30.8 Day17 额外高价值存档：Nacos 和 ZooKeeper 像在哪，不像在哪？
