## 3. 项目整体架构怎么说

### 3.1 高频问题：你的项目是怎么分层的？

#### 简洁回答

我的项目采用的是比较典型的分层设计，主要分为：

- Controller 层：负责接收请求和返回响应
- Service 层：负责核心业务逻辑、事务控制和规则判断
- Mapper 层：负责和数据库交互

这种设计的好处是职责清晰，便于维护，也方便后期扩展。

#### 延伸说明

如果面试官继续问，可以补一句：

- 比如菜品管理里，Controller 只负责接参数和调 Service，真正的一对多保存、删除前校验、事务控制，都是在 Service 层完成的。

### 3.2 高频问题：你的项目为什么要拆成 common、pojo、server 三个模块？

#### 简洁回答

我这个项目是 Maven 多模块工程，主要分成：

- common：放公共工具类、常量、枚举、上下文等通用能力
- pojo：放 DTO、Entity、VO 这些数据对象
- server：放 Controller、Service、Mapper、配置类这些真正的业务代码

这样拆分的好处是：

- 公共能力和业务能力分离
- 数据对象集中管理
- 结构更清晰，也更接近真实项目的组织方式

## 4. DTO、Entity、VO 怎么说

### 4.1 高频问题：DTO、Entity、VO 分别是干什么的？

#### 简洁回答

- DTO 面向请求，主要用来接收前端传来的参数
- Entity 面向数据库，通常和表结构比较接近
- VO 面向响应，主要用来返回给前端展示

#### 好背版本

- DTO：接请求
- Entity：落数据库
- VO：做响应

#### 项目例子

在菜品管理里：

- `DishDTO` 用来接前端新增或修改菜品时提交的数据
- `Dish` 对应数据库中的 `dish` 表
- `DishVO` 用来返回菜品详情或分页展示结果，因为前端除了菜品本身，还需要分类名、口味等展示字段

## 5. Spring MVC 和请求链怎么说

### 5.1 高频问题：前端请求到后端之后，整个链路是怎么走的？

#### 简洁回答

前端点击按钮后，会由前端的 JavaScript 发起 HTTP 请求，请求先到 Tomcat，再交给 Spring MVC。Spring MVC 会根据请求路径和请求方式找到对应的 Controller 方法，并完成参数绑定。然后 Controller 调用 Service，Service 再调用 Mapper 和数据库交互。最后 Controller 返回 Java 对象，Spring MVC 再把它转换成 JSON 响应给前端。

#### 更顺口版本

- 前端发请求
- Tomcat 接住
- Spring MVC 分发到 Controller
- Controller 调 Service
- Service 调 Mapper
- Mapper 执行 SQL
- 结果再被 Spring MVC 转成 JSON 返回前端

### 5.2 高频问题：Spring MVC 在你的项目里主要做了什么？

#### 简洁回答

Spring MVC 在我这个项目里主要负责四件事：

- 路由分发：根据 URL 和请求方式找到对应 Controller
- 参数绑定：把 JSON、路径参数、查询参数转成 Java 参数或对象
- 执行拦截器：比如 JWT 登录校验
- 响应转换：把 Java 对象序列化成 JSON 返回给前端

### 5.3 高频问题：`@RequestBody`、`@PathVariable`、`@RequestParam` 有什么区别？

#### 简洁回答

- `@RequestBody`：从请求体里接 JSON
- `@PathVariable`：从 URL 路径里取参数
- `@RequestParam`：从查询参数里取值

#### 项目例子

- 新增菜品时用 `@RequestBody DishDTO`
- 根据 id 查询详情时用 `@PathVariable Long id`
- 批量删除菜品时用 `@RequestParam List<Long> ids`

## 6. JWT 和登录校验怎么说

### 6.1 高频问题：你项目里的登录和权限校验是怎么做的？

#### 简洁回答

项目登录成功后，后端会生成 JWT 返回给前端。前端后续访问受保护接口时，会把 token 放到请求头里。后端通过拦截器统一校验 token，校验通过后再放行请求，同时把当前登录用户 id 保存到 `BaseContext`，方便后续业务代码使用。

#### 项目亮点补充

- 我们后面做公共字段自动填充时，就是通过 `BaseContext` 拿当前登录用户 id，然后自动给 `createUser` 和 `updateUser` 赋值的。

## 7. AOP 和公共字段自动填充怎么说

### 7.1 高频问题：你项目里 AOP 用在了什么地方？

#### 简洁回答

我在项目里用 AOP 做了公共字段自动填充。因为很多表在新增和修改时都要重复设置 `createTime`、`updateTime`、`createUser`、`updateUser`，如果把这些逻辑都写在 Service 里，会有很多重复代码。所以我通过自定义注解、切面和反射，在 Mapper 方法执行前统一完成这些字段的赋值。

### 7.2 高频问题：公共字段自动填充的实现思路是什么？

#### 简洁回答

实现思路是：

- 先自定义一个 `@AutoFill` 注解，标记哪些 Mapper 方法需要自动填充
- 再定义一个切面，拦截这些打了注解的方法
- 从注解里判断当前是新增还是修改
- 再结合 `BaseContext` 中保存的当前用户 id
- 通过反射调用实体类的 setter，自动设置公共字段

### 7.3 高频问题：为什么这里要用反射？

#### 简洁回答

因为切面拿到的参数是一个通用的 `Object`，它事先并不知道具体是 `Employee`、`Category` 还是 `Dish`。但这些实体类都约定好了同名的 setter 方法，所以可以通过反射在运行时动态找到这些方法并统一调用，这样一套逻辑就能复用到多个实体上。

#### 好背版本

- 不知道具体实体是谁
- 但知道它应该有哪些 setter
- 所以用反射统一处理

## 8. MyBatis 和动态 SQL 怎么说

### 8.1 高频问题：`#{}` 是什么？

#### 简洁回答

`#{}` 是 MyBatis 的参数占位写法，不是原生 MySQL 语法。它的作用是从 Java 方法传进来的参数中取值，然后在执行 SQL 时填进去。

#### 项目例子

比如：

```xml
status = #{status}
```

如果传进来的对象里 `status = 1`，那么执行 SQL 时就会把这个值填进去。

### 8.2 高频问题：什么是动态 SQL？

#### 简洁回答

动态 SQL 的核心思想是：

- 传了什么条件，就拼什么 SQL
- 没传的条件，就不拼

在我的项目里，菜品分页查询和动态更新都用了动态 SQL。比如修改菜品时，只有不为空的字段才会被更新，这样可以避免把原有字段误更新成 `null`。

### 8.3 高频问题：`<if>`、`<where>`、`<set>`、`<foreach>` 分别有什么用？

#### 简洁回答

- `<if>`：条件成立才拼接 SQL
- `<where>`：自动处理 where 和多余的 and/or
- `<set>`：自动处理 update 的 set 和多余逗号
- `<foreach>`：循环集合，常用于 `in (...)`

## 9. 菜品管理的一对多设计怎么说

### 9.1 高频问题：为什么菜品管理不是单表操作？

#### 简洁回答

因为菜品和口味是典型的一对多关系：

- 一条菜品对应一条 `dish` 主表记录
- 一条菜品可以对应多条 `dish_flavor` 子表记录

所以新增、修改、删除菜品时，不能只操作主表，还要联动处理口味表。

### 9.2 高频问题：为什么新增菜品时要先插主表，再插子表？

#### 简洁回答

因为子表 `dish_flavor` 里有 `dish_id` 字段，它要依赖主表 `dish` 的主键 id。只有先插主表，拿到生成的菜品 id，后面才能把这个 id 赋给每一条口味数据，再批量插入口味表。

### 9.3 高频问题：为什么修改菜品口味时选择“先删旧的，再插新的”？

#### 简洁回答

因为前端编辑口味时，可能会出现新增、删除、修改、顺序变化等多种情况。如果后端逐条判断差异，逻辑会比较复杂。考虑到子表数据量不大，所以采用“先删旧口味，再插入新口味”的方式更简单、更稳，也更容易维护。

### 9.4 高频问题：为什么删除菜品时不能只删主表？

#### 简洁回答

因为如果只删 `dish` 主表，不删 `dish_flavor` 子表，就会留下没有归属的口味记录，也就是孤儿数据。这种数据会污染数据库，也会给后续业务带来风险，所以删除时必须主表和子表一起处理。

## 10. 事务怎么说

### 10.1 高频问题：你的项目里事务用在了哪些场景？

#### 简洁回答

我在菜品新增、菜品修改、批量删除等涉及多步数据库操作的场景用了事务。因为这些业务往往不是只改一张表，而是需要联动多张表。如果中间某一步失败，就要整体回滚，避免出现半截数据。

### 10.2 高频问题：为什么 `saveWithFlavor()` 和 `updateWithFlavor()` 要加 `@Transactional`？

#### 简洁回答

因为这两个方法都涉及多步操作：

- 新增菜品时要先插 `dish`，再插 `dish_flavor`
- 修改菜品时要先更新主表，再删旧口味，再插新口味

如果没有事务，一旦中间出错，数据库就可能留下不完整数据。所以要用事务保证要么全成功，要么全失败。

#### 好背版本

- 多步操作
- 多表联动
- 不能接受半截成功
- 所以要加事务

## 11. 文件上传和本地图片方案怎么说

### 11.1 高频问题：你的项目里图片上传是怎么做的？

#### 简洁回答

我这个项目一开始课程思路是走云端对象存储，但在当前阶段我把它改成了本地上传方案。前端上传图片时，请求会打到 `POST /admin/common/upload`，后端用 `MultipartFile` 接收文件，给图片生成 UUID 文件名后保存到本地 `uploads` 目录，再把图片访问 URL 返回给前端。前端后续把这个 URL 作为菜品的 `image` 字段提交保存到数据库。

### 11.2 高频问题：为什么图片上传这里不用 `@RequestBody`？

#### 简洁回答

因为上传文件时，请求格式通常是 `multipart/form-data`，不是普通的 JSON 请求体，所以这里需要使用 `MultipartFile` 来接收文件，而不是 `@RequestBody`。

### 11.3 高频问题：为什么浏览器能直接访问 `/uploads/xxx.jpg`？

#### 简洁回答

因为我在 `WebMvcConfiguration` 里做了静态资源映射，把 `/uploads/**` 这个访问路径映射到了本地磁盘目录 `uploads`。这样浏览器访问这个 URL 时，Spring MVC 会直接去对应目录下找到文件并返回给浏览器。

### 11.4 高频问题：为什么上传图片成功不等于菜品保存成功？

#### 简洁回答

因为这是两次不同的请求：

- 第一次是上传文件，后端返回图片 URL
- 第二次是新增或修改菜品，把这个图片 URL 连同其他菜品信息一起保存进数据库

所以如果图片上传成功了，但菜品保存接口没有成功执行，数据库中的图片地址仍然不会更新。

## 12. 分页、查询、状态修改这些常见接口怎么说

### 12.1 高频问题：菜品分页查询你是怎么做的？

#### 简洁回答

我用了 PageHelper 做分页，Controller 接收分页参数后交给 Service，Service 中先调用 `PageHelper.startPage()` 开启分页，再调用 Mapper 查询。SQL 里通过动态条件支持按名称、分类、状态筛选，同时关联分类表查出 `categoryName`，最后统一封装成 `PageResult` 返回前端。

### 12.2 高频问题：为什么分页查询返回的是 VO，不是 Entity？

#### 简洁回答

因为分页页面不仅需要菜品本身的字段，还需要像 `categoryName` 这种展示字段，而这些字段并不完全属于数据库主表实体。所以更适合用 VO 来组织返回结果。

### 12.3 高频问题：起售/停售接口你是怎么实现的？

#### 简洁回答

我用了一个比较轻量的做法，只构造一个带 `id` 和 `status` 的 `Dish` 对象，然后调用动态更新 SQL。因为 SQL 里只会更新不为空的字段，所以可以只改状态，同时结合自动填充机制自动更新 `updateTime` 和 `updateUser`。

## 13. 删除前校验怎么说

### 13.1 高频问题：为什么删除菜品前还要做校验？

#### 简洁回答

因为数据库能删，不代表业务允许删。在我的项目里，删除菜品前会先判断两件事：

- 菜品当前是否处于起售状态
- 菜品是否已经被套餐关联

只有都满足条件时，才允许真正删除。这样更符合真实项目的业务规则。

#### 好背版本

- 先判断能不能删
- 再决定删不删
- 不是数据库能删就直接删

## 16. 套餐管理怎么说

### 16.1 高频问题：套餐管理和菜品管理最大的区别是什么？

#### 简洁回答

菜品管理主要是一条主表 `dish` 和它的口味子表 `dish_flavor` 的关系，而套餐管理更像是一个组合业务：

- 套餐本身有主表 `setmeal`
- 套餐和菜品之间还有关系表 `setmeal_dish`

所以套餐管理的重点不只是 CRUD，还包括：

- 主表和关系表联动保存
- 启售前业务校验
- 删除前业务校验
- 详情查询时的多表组装

### 16.2 高频问题：新增套餐你是怎么做的？

#### 简洁回答

新增套餐时，我不是只插一张 `setmeal` 表，而是分三步做：

- 先把前端传来的 `SetmealDTO` 转成 `Setmeal`
- 先插入套餐主表，拿到生成的套餐 id
- 再给每一条 `setmealDishes` 补上 `setmealId`，批量插入 `setmeal_dish`

整个过程加了事务，保证要么一起成功，要么一起回滚。

#### 好背版本

- 先插主表
- 拿到套餐 id
- 再插关系表
- 用事务保证一致性

### 16.3 高频问题：套餐启售为什么不能直接改状态？

#### 简洁回答

因为套餐能不能启售，不只取决于它自己，还取决于它里面的菜品状态。我的实现是：

- 先查这个套餐关联了哪些菜
- 再查这些菜当前是不是启售
- 只要有一道菜还在停售
- 就拒绝启售整个套餐

这样做是为了保证前台用户看到的套餐是可用的，不会出现“套餐启售了，但里面有菜其实不能卖”的情况。

### 16.4 高频问题：你项目里套餐启售失败的提示是什么？

#### 简洁回答

如果套餐里包含未启售菜品，我会抛业务异常，提示：

- `套餐内包含未启售菜品，无法启售`

这说明我这里不是单纯改一个状态字段，而是先做了业务规则判断。

### 16.5 高频问题：为什么删除套餐前也要做校验？

#### 简洁回答

因为数据库能删，不代表业务允许删。在我的项目里：

- 起售中的套餐不能删除

所以删除前会先查套餐状态：

- 如果是起售中，直接拦住
- 如果已经停售，才允许继续删除

#### 好背版本

- 先判断能不能删
- 起售中的套餐不让删
- 停售后才能真正删除

### 16.6 高频问题：为什么删除套餐时不能只删 `setmeal` 主表？

#### 简洁回答

因为套餐和菜品之间还有关系表 `setmeal_dish`。如果只删主表，不删关系表，就会留下没有归属的关联数据，形成脏数据。所以删除套餐时我做的是：

- 先删 `setmeal`
- 再删 `setmeal_dish`

这两个动作放在同一个事务里处理。

### 16.7 高频问题：套餐详情查询为什么返回的是一个大对象？

#### 简洁回答

因为前端编辑套餐时，不只是要看到套餐主信息，还要看到这个套餐里包含哪些菜、每道菜几份。所以详情查询不是只查一张表，而是：

- 先查 `setmeal` 主表
- 再查 `setmeal_dish` 关系表
- 最后把它们组装成一个完整的 `SetmealVO`

这样前端拿到一次响应，就能直接做表单回显。

### 16.8 高频问题：套餐修改为什么采用“删旧关系、插新关系”？

#### 简洁回答

因为套餐关联菜品在前端编辑时，可能会同时发生：

- 菜品新增
- 菜品删除
- 份数变化
- 顺序变化

如果后端逐条对比旧数据和新数据，逻辑会比较复杂。所以我采用了更稳的做法：

- 先更新套餐主表
- 再删除原来的 `setmeal_dish`
- 再把前端这次传来的新关系全部重新插入

这和我前面做菜品口味修改时的思路是一致的。

### 16.9 高频问题：套餐管理这一块你觉得最能体现项目含金量的点是什么？

#### 简洁回答

我觉得套餐管理最能体现项目含金量的地方在于，它已经不是简单的单表 CRUD 了，而是把几个真实项目里很常见的能力放到了一起：

- 主表和关系表联动保存
- 启售前业务校验
- 删除前业务校验
- 详情查询时的多表组装
- 修改时的事务式关系重建

所以这一块很适合在面试里体现我对业务规则和数据一致性的理解。

### 16.10 一个适合面试的套餐管理总结说法

可以这样说：

- 我在套餐管理模块里，不只是完成了新增、分页、起售停售、删除、详情、修改这些接口，更重要的是把套餐和菜品之间的关系表设计、启售前校验、删除前校验、详情组装和事务更新这几类真实业务问题都跑通了。这个模块让我真正练到了“多表联动 + 业务规则 + 事务一致性”这三个点。
