## 3. 项目整体架构怎么说

### 3.1 高频问题：你的项目是怎么分层的？

#### 简洁回答

我的项目采用的是比较典型的分层设计，主要分为：

- Controller 层：负责接收请求和返回响应
- Service 层：负责核心业务逻辑、事务控制和规则判断
- Mapper 层：负责和数据库交互

这种设计的好处是职责清晰，便于维护，也方便后期扩展。

#### 延伸说明

如果面试官继续问，可以补一句：

- 比如菜品管理里，Controller 只负责接参数和调 Service，真正的一对多保存、删除前校验、事务控制，都是在 Service 层完成的。

### 3.2 高频问题：你的项目为什么要拆成 common、pojo、server 三个模块？

#### 简洁回答

我这个项目是 Maven 多模块工程，主要分成：

- common：放公共工具类、常量、枚举、上下文等通用能力
- pojo：放 DTO、Entity、VO 这些数据对象
- server：放 Controller、Service、Mapper、配置类这些真正的业务代码

这样拆分的好处是：

- 公共能力和业务能力分离
- 数据对象集中管理
- 结构更清晰，也更接近真实项目的组织方式

## 4. DTO、Entity、VO 怎么说

### 4.1 高频问题：DTO、Entity、VO 分别是干什么的？

#### 简洁回答

- DTO 面向请求，主要用来接收前端传来的参数
- Entity 面向数据库，通常和表结构比较接近
- VO 面向响应，主要用来返回给前端展示

#### 好背版本

- DTO：接请求
- Entity：落数据库
- VO：做响应

#### 项目例子

在菜品管理里：

- `DishDTO` 用来接前端新增或修改菜品时提交的数据
- `Dish` 对应数据库中的 `dish` 表
- `DishVO` 用来返回菜品详情或分页展示结果，因为前端除了菜品本身，还需要分类名、口味等展示字段

## 5. Spring MVC 和请求链怎么说

### 5.1 高频问题：前端请求到后端之后，整个链路是怎么走的？

#### 简洁回答

前端点击按钮后，会由前端的 JavaScript 发起 HTTP 请求，请求先到 Tomcat，再交给 Spring MVC。Spring MVC 会根据请求路径和请求方式找到对应的 Controller 方法，并完成参数绑定。然后 Controller 调用 Service，Service 再调用 Mapper 和数据库交互。最后 Controller 返回 Java 对象，Spring MVC 再把它转换成 JSON 响应给前端。

#### 更顺口版本

- 前端发请求
- Tomcat 接住
- Spring MVC 分发到 Controller
- Controller 调 Service
- Service 调 Mapper
- Mapper 执行 SQL
- 结果再被 Spring MVC 转成 JSON 返回前端

### 5.2 高频问题：Spring MVC 在你的项目里主要做了什么？

#### 简洁回答

Spring MVC 在我这个项目里主要负责四件事：

- 路由分发：根据 URL 和请求方式找到对应 Controller
- 参数绑定：把 JSON、路径参数、查询参数转成 Java 参数或对象
- 执行拦截器：比如 JWT 登录校验
- 响应转换：把 Java 对象序列化成 JSON 返回给前端

### 5.3 高频问题：`@RequestBody`、`@PathVariable`、`@RequestParam` 有什么区别？

#### 简洁回答

- `@RequestBody`：从请求体里接 JSON
- `@PathVariable`：从 URL 路径里取参数
- `@RequestParam`：从查询参数里取值

#### 项目例子

- 新增菜品时用 `@RequestBody DishDTO`
- 根据 id 查询详情时用 `@PathVariable Long id`
- 批量删除菜品时用 `@RequestParam List<Long> ids`

## 6. JWT 和登录校验怎么说

### 6.1 高频问题：你项目里的登录和权限校验是怎么做的？

#### 简洁回答

项目登录成功后，后端会生成 JWT 返回给前端。前端后续访问受保护接口时，会把 token 放到请求头里。后端通过拦截器统一校验 token，校验通过后再放行请求，同时把当前登录用户 id 保存到 `BaseContext`，方便后续业务代码使用。

#### 项目亮点补充

- 我们后面做公共字段自动填充时，就是通过 `BaseContext` 拿当前登录用户 id，然后自动给 `createUser` 和 `updateUser` 赋值的。

## 7. AOP 和公共字段自动填充怎么说

### 7.1 高频问题：你项目里 AOP 用在了什么地方？

#### 简洁回答

我在项目里用 AOP 做了公共字段自动填充。因为很多表在新增和修改时都要重复设置 `createTime`、`updateTime`、`createUser`、`updateUser`，如果把这些逻辑都写在 Service 里，会有很多重复代码。所以我通过自定义注解、切面和反射，在 Mapper 方法执行前统一完成这些字段的赋值。

### 7.2 高频问题：公共字段自动填充的实现思路是什么？

#### 简洁回答

实现思路是：

- 先自定义一个 `@AutoFill` 注解，标记哪些 Mapper 方法需要自动填充
- 再定义一个切面，拦截这些打了注解的方法
- 从注解里判断当前是新增还是修改
- 再结合 `BaseContext` 中保存的当前用户 id
- 通过反射调用实体类的 setter，自动设置公共字段

### 7.3 高频问题：为什么这里要用反射？

#### 简洁回答

因为切面拿到的参数是一个通用的 `Object`，它事先并不知道具体是 `Employee`、`Category` 还是 `Dish`。但这些实体类都约定好了同名的 setter 方法，所以可以通过反射在运行时动态找到这些方法并统一调用，这样一套逻辑就能复用到多个实体上。

#### 好背版本

- 不知道具体实体是谁
- 但知道它应该有哪些 setter
- 所以用反射统一处理

## 8. MyBatis 和动态 SQL 怎么说

### 8.1 高频问题：`#{}` 是什么？

#### 简洁回答

`#{}` 是 MyBatis 的参数占位写法，不是原生 MySQL 语法。它的作用是从 Java 方法传进来的参数中取值，然后在执行 SQL 时填进去。

#### 项目例子

比如：

```xml
status = #{status}
```

如果传进来的对象里 `status = 1`，那么执行 SQL 时就会把这个值填进去。

### 8.2 高频问题：什么是动态 SQL？

#### 简洁回答

动态 SQL 的核心思想是：

- 传了什么条件，就拼什么 SQL
- 没传的条件，就不拼

在我的项目里，菜品分页查询和动态更新都用了动态 SQL。比如修改菜品时，只有不为空的字段才会被更新，这样可以避免把原有字段误更新成 `null`。

### 8.3 高频问题：`<if>`、`<where>`、`<set>`、`<foreach>` 分别有什么用？

#### 简洁回答

- `<if>`：条件成立才拼接 SQL
- `<where>`：自动处理 where 和多余的 and/or
- `<set>`：自动处理 update 的 set 和多余逗号
- `<foreach>`：循环集合，常用于 `in (...)`

## 9. 菜品管理的一对多设计怎么说

### 9.1 高频问题：为什么菜品管理不是单表操作？

#### 简洁回答

因为菜品和口味是典型的一对多关系：

- 一条菜品对应一条 `dish` 主表记录
- 一条菜品可以对应多条 `dish_flavor` 子表记录

所以新增、修改、删除菜品时，不能只操作主表，还要联动处理口味表。

### 9.2 高频问题：为什么新增菜品时要先插主表，再插子表？

#### 简洁回答

因为子表 `dish_flavor` 里有 `dish_id` 字段，它要依赖主表 `dish` 的主键 id。只有先插主表，拿到生成的菜品 id，后面才能把这个 id 赋给每一条口味数据，再批量插入口味表。

### 9.3 高频问题：为什么修改菜品口味时选择“先删旧的，再插新的”？

#### 简洁回答

因为前端编辑口味时，可能会出现新增、删除、修改、顺序变化等多种情况。如果后端逐条判断差异，逻辑会比较复杂。考虑到子表数据量不大，所以采用“先删旧口味，再插入新口味”的方式更简单、更稳，也更容易维护。

### 9.4 高频问题：为什么删除菜品时不能只删主表？

#### 简洁回答

因为如果只删 `dish` 主表，不删 `dish_flavor` 子表，就会留下没有归属的口味记录，也就是孤儿数据。这种数据会污染数据库，也会给后续业务带来风险，所以删除时必须主表和子表一起处理。

## 10. 事务怎么说

### 10.1 高频问题：你的项目里事务用在了哪些场景？

#### 简洁回答

我在菜品新增、菜品修改、批量删除等涉及多步数据库操作的场景用了事务。因为这些业务往往不是只改一张表，而是需要联动多张表。如果中间某一步失败，就要整体回滚，避免出现半截数据。

### 10.2 高频问题：为什么 `saveWithFlavor()` 和 `updateWithFlavor()` 要加 `@Transactional`？

#### 简洁回答

因为这两个方法都涉及多步操作：

- 新增菜品时要先插 `dish`，再插 `dish_flavor`
- 修改菜品时要先更新主表，再删旧口味，再插新口味

如果没有事务，一旦中间出错，数据库就可能留下不完整数据。所以要用事务保证要么全成功，要么全失败。

#### 好背版本

- 多步操作
- 多表联动
- 不能接受半截成功
- 所以要加事务

## 11. 文件上传和本地图片方案怎么说

### 11.1 高频问题：你的项目里图片上传是怎么做的？

#### 简洁回答

我这个项目一开始课程思路是走云端对象存储，但在当前阶段我把它改成了本地上传方案。前端上传图片时，请求会打到 `POST /admin/common/upload`，后端用 `MultipartFile` 接收文件，给图片生成 UUID 文件名后保存到本地 `uploads` 目录，再把图片访问 URL 返回给前端。前端后续把这个 URL 作为菜品的 `image` 字段提交保存到数据库。

### 11.2 高频问题：为什么图片上传这里不用 `@RequestBody`？

#### 简洁回答

因为上传文件时，请求格式通常是 `multipart/form-data`，不是普通的 JSON 请求体，所以这里需要使用 `MultipartFile` 来接收文件，而不是 `@RequestBody`。

### 11.3 高频问题：为什么浏览器能直接访问 `/uploads/xxx.jpg`？

#### 简洁回答

因为我在 `WebMvcConfiguration` 里做了静态资源映射，把 `/uploads/**` 这个访问路径映射到了本地磁盘目录 `uploads`。这样浏览器访问这个 URL 时，Spring MVC 会直接去对应目录下找到文件并返回给浏览器。

### 11.4 高频问题：为什么上传图片成功不等于菜品保存成功？

#### 简洁回答

因为这是两次不同的请求：

- 第一次是上传文件，后端返回图片 URL
- 第二次是新增或修改菜品，把这个图片 URL 连同其他菜品信息一起保存进数据库

所以如果图片上传成功了，但菜品保存接口没有成功执行，数据库中的图片地址仍然不会更新。

## 12. 分页、查询、状态修改这些常见接口怎么说

### 12.1 高频问题：菜品分页查询你是怎么做的？

#### 简洁回答

我用了 PageHelper 做分页，Controller 接收分页参数后交给 Service，Service 中先调用 `PageHelper.startPage()` 开启分页，再调用 Mapper 查询。SQL 里通过动态条件支持按名称、分类、状态筛选，同时关联分类表查出 `categoryName`，最后统一封装成 `PageResult` 返回前端。

### 12.2 高频问题：为什么分页查询返回的是 VO，不是 Entity？

#### 简洁回答

因为分页页面不仅需要菜品本身的字段，还需要像 `categoryName` 这种展示字段，而这些字段并不完全属于数据库主表实体。所以更适合用 VO 来组织返回结果。

### 12.3 高频问题：起售/停售接口你是怎么实现的？

#### 简洁回答

我用了一个比较轻量的做法，只构造一个带 `id` 和 `status` 的 `Dish` 对象，然后调用动态更新 SQL。因为 SQL 里只会更新不为空的字段，所以可以只改状态，同时结合自动填充机制自动更新 `updateTime` 和 `updateUser`。

## 13. 删除前校验怎么说

### 13.1 高频问题：为什么删除菜品前还要做校验？

#### 简洁回答

因为数据库能删，不代表业务允许删。在我的项目里，删除菜品前会先判断两件事：

- 菜品当前是否处于起售状态
- 菜品是否已经被套餐关联

只有都满足条件时，才允许真正删除。这样更符合真实项目的业务规则。

#### 好背版本

- 先判断能不能删
- 再决定删不删
- 不是数据库能删就直接删

## 16. 套餐管理怎么说

### 16.1 高频问题：套餐管理和菜品管理最大的区别是什么？

#### 简洁回答

菜品管理主要是一条主表 `dish` 和它的口味子表 `dish_flavor` 的关系，而套餐管理更像是一个组合业务：

- 套餐本身有主表 `setmeal`
- 套餐和菜品之间还有关系表 `setmeal_dish`

所以套餐管理的重点不只是 CRUD，还包括：

- 主表和关系表联动保存
- 启售前业务校验
- 删除前业务校验
- 详情查询时的多表组装

### 16.2 高频问题：新增套餐你是怎么做的？

#### 简洁回答

新增套餐时，我不是只插一张 `setmeal` 表，而是分三步做：

- 先把前端传来的 `SetmealDTO` 转成 `Setmeal`
- 先插入套餐主表，拿到生成的套餐 id
- 再给每一条 `setmealDishes` 补上 `setmealId`，批量插入 `setmeal_dish`

整个过程加了事务，保证要么一起成功，要么一起回滚。

#### 好背版本

- 先插主表
- 拿到套餐 id
- 再插关系表
- 用事务保证一致性

### 16.3 高频问题：套餐启售为什么不能直接改状态？

#### 简洁回答

因为套餐能不能启售，不只取决于它自己，还取决于它里面的菜品状态。我的实现是：

- 先查这个套餐关联了哪些菜
- 再查这些菜当前是不是启售
- 只要有一道菜还在停售
- 就拒绝启售整个套餐

这样做是为了保证前台用户看到的套餐是可用的，不会出现“套餐启售了，但里面有菜其实不能卖”的情况。

### 16.4 高频问题：你项目里套餐启售失败的提示是什么？

#### 简洁回答

如果套餐里包含未启售菜品，我会抛业务异常，提示：

- `套餐内包含未启售菜品，无法启售`

这说明我这里不是单纯改一个状态字段，而是先做了业务规则判断。

### 16.5 高频问题：为什么删除套餐前也要做校验？

#### 简洁回答

因为数据库能删，不代表业务允许删。在我的项目里：

- 起售中的套餐不能删除

所以删除前会先查套餐状态：

- 如果是起售中，直接拦住
- 如果已经停售，才允许继续删除

#### 好背版本

- 先判断能不能删
- 起售中的套餐不让删
- 停售后才能真正删除

### 16.6 高频问题：为什么删除套餐时不能只删 `setmeal` 主表？

#### 简洁回答

因为套餐和菜品之间还有关系表 `setmeal_dish`。如果只删主表，不删关系表，就会留下没有归属的关联数据，形成脏数据。所以删除套餐时我做的是：

- 先删 `setmeal`
- 再删 `setmeal_dish`

这两个动作放在同一个事务里处理。

### 16.7 高频问题：套餐详情查询为什么返回的是一个大对象？

#### 简洁回答

因为前端编辑套餐时，不只是要看到套餐主信息，还要看到这个套餐里包含哪些菜、每道菜几份。所以详情查询不是只查一张表，而是：

- 先查 `setmeal` 主表
- 再查 `setmeal_dish` 关系表
- 最后把它们组装成一个完整的 `SetmealVO`

这样前端拿到一次响应，就能直接做表单回显。

### 16.8 高频问题：套餐修改为什么采用“删旧关系、插新关系”？

#### 简洁回答

因为套餐关联菜品在前端编辑时，可能会同时发生：

- 菜品新增
- 菜品删除
- 份数变化
- 顺序变化

如果后端逐条对比旧数据和新数据，逻辑会比较复杂。所以我采用了更稳的做法：

- 先更新套餐主表
- 再删除原来的 `setmeal_dish`
- 再把前端这次传来的新关系全部重新插入

这和我前面做菜品口味修改时的思路是一致的。

### 16.9 高频问题：套餐管理这一块你觉得最能体现项目含金量的点是什么？

#### 简洁回答

我觉得套餐管理最能体现项目含金量的地方在于，它已经不是简单的单表 CRUD 了，而是把几个真实项目里很常见的能力放到了一起：

- 主表和关系表联动保存
- 启售前业务校验
- 删除前业务校验
- 详情查询时的多表组装
- 修改时的事务式关系重建

所以这一块很适合在面试里体现我对业务规则和数据一致性的理解。

### 16.10 一个适合面试的套餐管理总结说法

可以这样说：

## 17. 店铺营业状态和 Redis 怎么说

### 17.1 高频问题：为什么店铺营业状态这里用了 Redis，而不是 MySQL？

#### 简洁回答

因为店铺营业状态本质上只是一个很轻量的全局共享状态，比如：

- `1`：营业中
- `0`：打烊中

它会被管理端和用户端反复读取，所以我把它放在 Redis 里，用一个简单的 key-value 来存储。这样读写更轻量，也更适合这种配置型状态场景。

### 17.2 高频问题：Day5 这一块的业务链路是怎么走的？

#### 简洁回答

我在管理端提供了两个接口：

- 查询店铺营业状态
- 修改店铺营业状态

在用户端提供了一个接口：

- 查询店铺营业状态

管理端修改状态时，会把 `SHOP_STATUS` 写入 Redis；管理端和用户端查询状态时，读的也是 Redis 里的同一个 key。所以这块本质上是管理端和用户端共享同一份状态源。

#### 好背版本

- 管理端写 Redis
- 管理端读 Redis
- 用户端也读 Redis
- 三者共享同一个 `SHOP_STATUS`

### 17.3 高频问题：店铺营业状态这一块最能体现什么能力？

#### 简洁回答

我觉得这块最能体现的是，我开始不只是做数据库 CRUD，而是在项目里真正接入了 Redis，并把一个全局配置状态从管理端传递到用户端。它虽然接口不多，但很能体现我对状态型业务、中间件接入和前后端联动的理解。

### 17.4 一个适合面试的 Day5 总结说法

可以这样说：

- 在店铺营业状态这个模块里，我没有继续走传统数据库 CRUD 的思路，而是把一个全局共享状态放进 Redis。管理端负责修改和查询营业状态，用户端负责查询，同一份 `SHOP_STATUS` 被多个端共同读取。这一块让我第一次把 Redis 真正接进项目，也练到了状态型业务和中间件联调。

## 18. 用户端登录和鉴权怎么说

### 18.1 高频问题：你们小程序登录后，后端怎么识别当前用户是谁？

#### 简洁回答

小程序先通过 `uni.login()` 从微信拿到一个临时 `code`，前端把这个 `code` 发给后端。后端再拿 `code + appid + secret` 去调微信接口换取 `openid`，然后用 `openid` 查询本地 `user` 表，查不到就自动注册。登录成功后，后端会把本地 `user.id` 放进 JWT 返回给前端。前端后续请求带着 token，后端拦截器统一解析 token，取出 `userId` 后放进 `BaseContext`，这样后面的购物车和订单等业务就能识别当前用户。

#### 好背版本

- 前端拿 `code`
- 后端换 `openid`
- 用 `openid` 找本地 `user`
- 把本地 `user.id` 放进 token
- 拦截器再从 token 里解析出当前用户

### 18.2 高频问题：为什么 token 里放的是 userId，而不是 code 或 openid？

#### 简洁回答

因为 `code` 只是一次性临时登录凭证，不能长期使用；`openid` 虽然稳定，但业务系统后续更适合围绕本地 `user` 表主键来做关联。像购物车、地址、订单这些业务表，最终都是和本地 `user.id` 关联的，所以登录成功后我会把本地 `user.id` 放进 token，后续统一按这个 id 识别用户。

#### 好背版本

- `code` 太临时
- `openid` 属于微信体系
- 本地业务最终按 `user.id` 关联
- 所以 token 里放本地 `userId`

### 18.3 高频问题：用户端拦截器为什么会自动执行？

#### 简洁回答

因为我在 `WebMvcConfiguration` 里把 `JwtTokenUserInterceptor` 注册给了 Spring MVC，并配置了它要拦截的路径。项目启动时只是完成规则注册，真正收到匹配 `/user/**` 的请求时，Spring MVC 会自动回调这个拦截器的 `preHandle()` 方法。也就是说，这属于框架生命周期中的自动回调，不需要业务代码手动去调用。

#### 好背版本

- 启动时注册规则
- 请求到来时自动匹配
- 命中后 Spring MVC 自动调用 `preHandle()`

### 18.4 高频问题：为什么业务代码不让前端直接传 userId？

#### 简洁回答

因为前端参数是不可信的，如果允许前端自己传 `userId`，用户就可以伪造身份去查看甚至修改别人的购物车、订单等数据。所以我的做法是让前端只传 token，后端拦截器自行解析 token 拿到可信的 `userId`，再通过 `BaseContext` 在本次请求处理中共享给业务代码使用。

#### 好背版本

- 前端参数可伪造
- `userId` 不能信前端
- 必须后端自己解析 token 来确认身份

## 19. 用户端购物车怎么说

### 19.1 高频问题：购物车为什么不能只按 dishId 判重？

#### 简洁回答

因为购物车里的“同一项”不只是同一道菜，还要看是谁点的、选了什么口味。我的实现里，购物车判重至少基于：

- `userId`
- `dishId` 或 `setmealId`
- `dishFlavor`

比如同一个用户点了同一道菜，但一次选微辣、一次选不辣，这两条应该在购物车里分开显示，不能简单合并成数量加一。

#### 好背版本

- 不是只看菜品
- 还要看当前用户
- 还要看口味/规格

### 19.2 高频问题：购物车加购的核心逻辑是什么？

#### 简洁回答

我在加购时不是直接插一条记录，而是先把前端传来的菜品、套餐和口味信息转换成查询条件，再补上当前登录用户 `userId`，去购物车表里查有没有同一项。如果查到了，就只把数量加一；如果没查到，才去菜品表或套餐表补齐名称、图片、价格这些字段，然后新增一条购物车记录。

#### 好背版本

- 先查重
- 查到就 `update +1`
- 查不到再补齐信息并 `insert`

### 19.3 高频问题：购物车减购为什么不是一直 number - 1？

#### 简洁回答

因为当购物车里某一项数量只剩 `1` 时，再减一次就不应该保留一条 `number = 0` 的记录了。这样既不符合业务展示，也会留下脏数据。所以我的处理是：

- 如果数量大于 `1`，就执行数量减一
- 如果数量等于 `1`，就直接删除这条购物车记录

#### 好背版本

- 大于 `1`：`update -1`
- 等于 `1`：直接 `delete`
- 不保留 `number = 0` 的脏数据

## 21. Day7 商品缓存怎么说

### 21.1 高频问题：Day7 这一块你到底做了什么？

#### 简洁回答

Day7 我主要完成的是用户端商品缓存。具体来说，我把用户端菜品列表和套餐列表都接入了 Spring Cache + Redis：第一次按分类查询时会走数据库，后续相同分类请求会直接命中 Redis；管理端在新增、修改、删除、起售停售商品时，再通过 `@CacheEvict` 清理对应缓存，保证用户端下一次访问拿到的是最新数据。

#### 好背版本

- 用户端查商品先走缓存
- 首次查库，二次命中
- 管理端变更后清缓存
- 下次访问重新回库

### 21.2 高频问题：你们缓存的到底是什么？

#### 简洁回答

我们缓存的不是单个菜品对象，也不是整张商品表，而是“某个分类下的整份列表查询结果”。比如用户端请求 `/user/dish/list?categoryId=16`，缓存里的就是分类 `16` 下所有起售菜品及其口味的完整返回结果；套餐也是一样，缓存的是某个套餐分类下的列表结果。

#### 好背版本

- 缓存的不是单个对象
- 缓存的是“分类列表查询结果”
- 前端点哪个分类，就缓存哪个分类那一屏的数据

### 21.3 高频问题：为什么缓存 key 选择 categoryId，而不是 dishId 或 setmealId？

#### 简洁回答

因为这两个用户端接口本身就是“按分类查列表”，前端传给后端的核心查询条件就是 `categoryId`。缓存 key 设计应该跟查询维度保持一致，所以菜品列表按 `categoryId` 缓存成 `dishCache::categoryId`，套餐列表按 `categoryId` 缓存成 `setmealCache::categoryId`。如果用 `dishId` 或 `setmealId`，就和接口的查询粒度不一致了。

#### 好背版本

- 前端按什么条件查
- 缓存就优先按什么条件存
- 这里前端按分类查
- 所以缓存 key 也按分类 id 设计

### 21.4 高频问题：为什么缓存里天然只有起售中的菜品和套餐？

#### 简洁回答

因为用户端查询数据库时，就已经在条件里加了 `status = ENABLE`。也就是说，返回给前端的结果本身就只包含起售中的数据，而 Spring Cache 缓存的就是这个查询结果，所以缓存里天然也只会出现起售中的菜品和套餐，而不是先查全部再从缓存里做二次筛选。

#### 好背版本

- 先按起售状态查库
- 再把查询结果缓存起来
- 不是缓存全部再过滤

### 21.5 高频问题：为什么第二次请求时只有 JWT 日志，没有 Controller 日志和 SQL？

#### 简洁回答

因为 JWT 拦截器和缓存发生在请求链的不同层。请求进来后，Spring MVC 仍然会先执行用户端 JWT 拦截器做身份校验；但校验通过后，`@Cacheable` 已经在方法入口外层判断到 Redis 里有缓存了，所以 Controller 方法体不会继续执行，自然也就不会再打印业务日志和 SQL。

#### 好背版本

- JWT 先校验身份
- 缓存再决定要不要进方法体
- 命中缓存时 Controller 和 SQL 都不会再执行

### 21.6 高频问题：为什么管理端只改了一个菜品，却要清整个 dishCache？

#### 简洁回答

因为用户端缓存的粒度不是单个菜品，而是“某个分类下的一整份列表结果”。一个菜品状态、名称、排序或展示内容变化，都可能影响这个分类下的列表展示，所以我这里先采用 `@CacheEvict(allEntries = true)` 清整组缓存的策略。这样实现更简单，也更能优先保证一致性。

#### 好背版本

- 缓存粒度是分类列表
- 改一个菜也会影响整份列表
- 所以先清整组缓存
- 先保证一致性，再谈更细粒度优化

### 21.7 高频问题：菜品缓存和套餐缓存最大的区别是什么？

#### 简洁回答

两者本质上是同一个“按分类缓存列表”的模板，最大区别在首次查询复杂度。菜品列表查询除了查 `dish` 主表，还要把 `dish_flavor` 一起带出来，所以首次查库更重；套餐列表当前主要查的是 `setmeal` 主表列表，相对更轻。除此之外，两者的缓存命中、缓存失效、管理端清缓存思路都基本一致。

#### 好背版本

- 两者模板一样
- 都是按分类缓存列表
- 菜品查询更重，因为还要带口味
- 套餐列表相对更轻

### 21.8 一个适合面试的 Day7 总结说法

可以这样说：

- Day7 这一块我把 Redis 从“只存全局状态”升级到了“缓存高频读业务结果”。我在用户端菜品和套餐分类查询上接了 Spring Cache，第一次请求会查数据库，第二次相同分类请求直接命中 Redis；管理端对菜品和套餐做新增、修改、启停售时，再通过 `@CacheEvict` 清理缓存，保证用户端下次访问重新回库并重建缓存。这一阶段让我真正理解了缓存 key 设计、缓存命中、缓存失效和数据一致性。

## 22. Spring Bean 和依赖注入怎么说

### 22.1 高频问题：Spring Bean 是什么？

#### 简洁回答

Spring Bean 本质上就是“交给 Spring 容器统一创建、统一管理、统一分发的对象”。在我的项目里，Controller、Service、拦截器、配置类这些对象都属于 Bean。正因为它们被 Spring 管起来了，项目里才可以通过 `@Autowired` 把不同层的对象自动注入到一起使用。

#### 好背版本

- Bean 就是被 Spring 托管的对象
- Spring 负责创建、管理、注入
- Controller、Service、拦截器、配置类都可以是 Bean

### 22.2 高频问题：`@RestController`、`@Service`、`@Component` 和 Bean 有什么关系？

#### 简洁回答

这些注解本质上都在告诉 Spring：“这个类交给你来管理”。区别只是语义层次不同：`@RestController` 主要用于控制层并表示返回 JSON，`@Service` 主要用于业务层，`@Component` 是更通用的组件标记。它们共同的结果都是让类变成 Spring Bean。

#### 好背版本

- 本质都和 Bean 注册有关
- `@RestController` 管控制层
- `@Service` 管业务层
- `@Component` 是通用版

### 22.3 高频问题：如果 Service 没加 `@Service` 会怎样？

#### 简洁回答

如果 Service 类没有加 `@Service`，Spring 容器就不会创建这个 Service Bean。这样 Controller 里通过 `@Autowired` 注入时就找不到对应对象，应用通常会在启动阶段直接报依赖注入失败，导致 Controller 和 Service 之间的调用链断掉。

#### 好背版本

- 不加 `@Service`
- Spring 不会创建 Service Bean
- `@Autowired` 注入失败
- 应用启动就可能报错

### 22.4 高频问题：为什么项目里 admin 和 user 下都能有同名 Controller？

#### 简洁回答

同名 Controller 在不同包下，Java 层面靠全限定类名区分，不会冲突；路由层面再通过 `/admin/**` 和 `/user/**` 的请求前缀隔开。真正需要注意的是 Spring Bean 命名冲突，所以像用户端 `DishController` 这类重名控制器，可以显式指定 Bean 名，比如 `@RestController("userDishController")`，从而避免和管理端默认 Bean 名撞上。

#### 好背版本

- Java 靠包名区分类
- 路由靠 `/admin` 和 `/user` 区分
- Bean 层如果重名，显式指定 Bean 名即可

## 23. Day8 下单与支付怎么说

### 23.3 高频问题：为什么不直接说“微信支付没做完”？

#### 简洁回答

因为这不是“没做完”，而是做到了当前资源条件下最合理的程度。我们没有企业商户资质，不代表支付模块就没有价值。真正重要的是，我已经理解并实现了真实支付的主干结构，知道支付请求怎么发起、回调为什么必须由后端处理、订单状态为什么不能只靠前端改，并且把自己系统内部能控制的业务闭环尽量跑通了。

#### 好背版本

- 不是没做
- 是把可控范围内的部分做实了
- 外部资质受限，不等于项目价值为零

### 23.4 高频问题：你是怎么在开发环境下验证支付链的？

#### 简洁回答

我的思路是保留真实支付架构，再增加开发态验证方案。也就是说，支付入口、支付成功逻辑、订单状态更新这些都按真实方式组织；但在拿不到真实商户环境时，通过模拟支付成功或手动触发支付成功逻辑，去验证订单是否能从待付款变成待接单、支付成功页和历史订单状态是否会变化。这样验证的是系统内部业务闭环，而不是简单伪造页面效果。

#### 好背版本

- 架构按真实支付来
- 验证用开发态模拟
- 重点看订单状态和页面效果有没有闭环

### 23.5 高频问题：如果以后拿到了真实商户环境，你的代码还能继续接吗？

#### 简洁回答

可以，这也是我为什么坚持保留真实支付主干的原因。只要后面补齐商户号、证书、APIv3 Key 和回调地址，支付入口就可以切到真实微信下单流程，而支付成功后的订单状态更新逻辑本身是不需要推倒重写的。

#### 好背版本

- 现在保留真实支付主干
- 以后只需要补商户环境
- 支付后的业务逻辑可以继续复用

### 23.6 一个适合面试的 Day8 总结说法

可以这样说：

- Day8 这一块我先把用户端地址簿、下单、取消订单这些订单主链真正做通了，再往支付链推进。对于微信支付，我没有简单说“因为资质不够就不做了”，而是按真实微信支付架构去设计支付入口、支付回调和支付成功后的订单状态流转。同时，考虑到个人开发环境缺少企业商户资质和证书，我又设计了开发态的验证方案，尽可能把支付后的业务闭环和前端体验跑通。这样既保留了未来接真实环境的能力，也能在当前条件下把项目做到尽可能接近真实生产场景。

### 23.7 高频问题：为什么提交订单不能简单理解成“插一条订单记录”？

#### 简洁回答

因为提交订单本质上是在把购物车里的临时数据转成正式订单数据。它至少包含四类动作：先根据登录态确定当前用户，再校验购物车和地址是否合法，然后写订单主表和订单明细表，最后清空购物车。所以它不是单表新增，而是一条完整的业务链。

#### 好背版本

- 先确定当前用户
- 再校验购物车和地址
- 再写订单主表和明细表
- 最后清空购物车
- 本质是把临时购物车数据转成正式订单数据

### 23.8 高频问题：为什么订单要拆成 `orders` 和 `order_detail` 两张表？

#### 简洁回答

因为订单主信息和商品明细天然不是同一种数据结构。订单号、用户、地址、状态、总金额这些是一张订单固定只有一份的数据，适合放在 `orders` 主表；而一张订单里买了什么、每样几份、什么口味，这部分条数是不固定的，天然是一对多关系，所以要单独放在 `order_detail` 里。拆开之后结构更清晰，也更符合后续详情、历史订单、再来一单这些查询和回填场景。

#### 好背版本

- `orders` 存固定的一份订单整体信息
- `order_detail` 存不固定的多条商品明细
- 一张订单对多条明细，天然就是一对多

### 23.9 高频问题：为什么订单里还要保存地址、手机号、收货人，而不是只存 `addressBookId`？

#### 简洁回答

因为地址簿会变化，但历史订单不能跟着变。订单里保存的是下单当时的收货信息快照，如果后面用户修改了地址簿，老订单依然应该保留下单时的地址、手机号和收货人。否则历史订单数据就会被污染。

#### 好背版本

- 地址簿会变
- 订单不能跟着变
- 订单要保留下单当时的收货信息快照

### 23.10 高频问题：为什么购物车当前更适合放 MySQL，而不是 Redis？

#### 简洁回答

因为购物车属于用户私有的强业务数据，不只是高频读结果，它后面还要参与正式下单，所以优先要保证持久化和数据一致性。像商品列表这种读多写少、丢了还能从数据库重建的数据更适合 Redis；购物车如果只放 Redis，会额外引入数据丢失风险和 Redis 与 MySQL 同步复杂度，对当前项目来说属于过度设计。

#### 好背版本

- 商品列表适合 Redis，因为高频读、可重建
- 购物车更像正式业务数据，优先放 MySQL
- 只放 Redis 会增加稳定性和一致性风险

### 23.11 高频问题：为什么支付要拆成 `payment()` 和 `paySuccess()` 两段？

#### 简洁回答

因为调起支付不等于支付成功。用户点击支付后，中间还可能出现取消支付、支付失败、网络超时、重复点击等情况，所以系统必须把“开始支付”和“确认支付成功后的状态更新”拆开。`payment()` 负责校验订单能不能支付、记录支付方式并返回支付参数；`paySuccess()` 才是真正把订单从待付款改成已支付后的统一状态流转入口。

#### 好背版本

- 调起支付不等于支付成功
- `payment()` 负责开始支付
- `paySuccess()` 负责支付成功后的状态更新
- 这样业务状态才不会乱

### 23.12 高频问题：什么叫幂等性？为什么支付场景特别需要它？

#### 简洁回答

幂等性指的是同一个操作执行一次和执行多次，最终结果应该一致，不应该因为重复执行产生额外副作用。支付场景特别容易出现前端重复点击、网络重试、第三方支付重复回调、后端补偿重放等情况，所以支付成功逻辑必须做幂等保护。比如当前项目里，如果订单已经是“已支付 + 待接单”，就直接返回，不再重复更新状态。

#### 好背版本

- 幂等性就是同一操作多次执行，结果仍一致
- 支付最怕重复点击、重复回调、网络重试
- 所以支付成功逻辑必须防重复处理

### 23.13 高频问题：真实微信支付里，为什么订单最终是否成功不能只信前端？

#### 简洁回答

因为前端不是最终可信方。前端可能被篡改、断网、关闭页面，或者只拿到了局部结果。真实微信支付里，更可靠的方式是以后端收到支付平台异步回调为准。也就是说，前端负责发起支付和拉起支付面板，后端则以后续回调通知来确认最终支付成功并更新订单状态。

#### 好背版本

- 前端只负责发起支付
- 前端不是最终可信方
- 真正可靠的是支付平台对后端的异步回调

### 23.14 高频问题：什么叫异步？什么叫回调接口？

#### 简洁回答

异步可以理解成“我先把事情发出去，不站在原地等最终结果，结果到了再处理”。回调接口则是“我先留一个通知入口，等对方处理完，再主动回来告诉我结果”。在微信支付里，用户发起支付后，微信不会把最终结果同步锁死在当前请求里，而是由微信服务器在支付完成后，主动请求我们后端预留的回调接口，把支付结果通知回来。

#### 好背版本

- 异步：先发出去，结果稍后处理
- 回调接口：提前留个入口，让对方处理完回来通知我
- 微信支付成功后，微信服务器会回调后端

### 23.15 高频问题：为什么支付链更适合用 `orderNumber/outTradeNo`，而不是 `orderId`？

#### 简洁回答

因为 `orderId` 更像系统内部数据库主键，只适合内部表关联；而 `orderNumber/outTradeNo` 是对外业务单号，适合传给第三方支付平台，也适合在回调时跨系统定位订单。微信并不知道你数据库里的自增主键是多少，它只认你下单时传给它的商户订单号。

#### 好背版本

- `orderId` 是内部主键
- `orderNumber/outTradeNo` 是对外业务单号
- 支付平台只认业务单号，不认数据库自增 id

### 23.16 高频问题：你项目里真实微信支付的主流程是什么？

#### 简洁回答

真实微信支付里，前端先把订单号交给后端 `payment()`，后端校验订单后，根据订单号、支付金额和当前用户的 `openid` 向微信下单，拿到前端拉起支付所需参数后再返回给小程序。前端调用 `uni.requestPayment(...)` 让用户确认支付。支付完成后，微信服务器通过异步回调通知我们的后端接口，后端根据回调里的 `out_trade_no` 找到订单，再统一执行 `paySuccess()` 更新订单状态。

#### 好背版本

- 后端先向微信下单
- 前端拉起微信支付面板
- 微信支付完成后回调后端
- 后端再更新订单状态

### 23.17 高频问题：真实商户环境拿不到时，你是怎么保证支付模块还有项目价值的？

#### 简洁回答

我的处理方式不是把支付整个跳过，而是保留真实支付架构的关键骨架：支付入口、支付成功状态更新、支付回调入口都按真实方案设计。同时，在当前开发环境下增加 mock 支付闭环，让系统内部的订单状态流转和前端页面效果可以先验证。这种方案保留了未来平滑切到真实支付的能力，也让当前项目具备可演示、可解释的工程价值。

#### 好背版本

- 真实支付主干保留
- 当前环境用 mock 闭环验证
- 以后拿到商户环境可平滑切真实支付

### 23.18 高频问题：Day8 你遇到过哪些最值得讲的问题？

#### 简洁回答

Day8 我遇到的不是单一代码 bug，而是一整串联调问题：比如 Redis 没启动导致依赖服务不可用、token 过期导致接口 401、后端没重启导致新接口 404、时间字段格式和前端消费方式不兼容、前端依赖缺失的 `/user/order/getEstimatedDeliveryTime`、以及微信开发者工具 `code:10` 最终定位到 AppID 混用和 secret 失效。这些问题让我学会了把联调问题分成环境问题、契约问题、运行时问题和平台配置问题来排查，而不是一上来就只盯代码。

#### 好背版本

- Day8 最大收获不只是写接口
- 还包括一整轮真实联调排错
- 学会先分问题类型，再逐层排查

## 24. Day10 WebSocket 实时提醒怎么说

### 24.1 高频问题：Day10 这一块你到底做了什么？

#### 简洁回答

Day10 我围绕订单域打通了一条实时提醒闭环。具体来说，用户在小程序里发起催单后，请求先进入后端订单业务层，后端会先校验当前用户、订单归属和订单状态，确认这次催单合法后，再组装一条 JSON 消息，并通过 WebSocket 广播给当前在线的管理端页面。管理端收到提醒后，不只是弹一个通知，还能继续查询订单详情并执行接单、派送、完成等处理动作。

#### 好背版本

- 用户端发起催单
- 后端先校验订单是否合法
- 再组装消息并通过 WebSocket 广播
- 管理端实时收到提醒
- 提醒后还能继续处理订单

### 24.2 高频问题：为什么这里要用 WebSocket，而不是普通 HTTP？

#### 简洁回答

因为这个场景需要服务端主动把消息推给管理端。如果只用普通 HTTP，管理端只能不停轮询后端问“有没有新提醒”，这样实时性差，请求也更浪费。WebSocket 建立长连接后，后端一旦有催单或来单消息，就可以直接推给当前在线的管理端页面。

#### 好背版本

- 这个场景要后端主动推消息
- 轮询也能做，但不够实时、还更浪费
- WebSocket 更适合做管理端实时提醒

### 24.3 高频问题：WebSocket 在你项目里的作用到底是什么？

#### 简洁回答

WebSocket 在我这个项目里，主要承担的是管理端实时提醒通道。管理端页面打开时会先建立 WebSocket 连接，后端把这条连接登记进在线连接表；用户催单后，后端把提醒消息广播给这些在线连接，于是管理端页面就能第一时间收到消息、弹提醒、播放提示音，并进入订单处理链。

#### 好背版本

- 页面先连 WebSocket
- 后端维护在线连接表
- 用户催单后广播提醒消息
- 管理端第一时间收到并继续处理订单

### 24.4 高频问题：WebSocket 底层是 TCP 还是 UDP？

#### 简洁回答

WebSocket 底层建立在 TCP 之上，不是 UDP。它的实时性主要来自长连接和服务端主动推送，而它的稳定性主要依赖 TCP 的可靠传输能力。

#### 好背版本

- WebSocket 用的是 TCP
- 实时感来自长连接和主动推送
- 稳定性主要靠 TCP

### 24.5 高频问题：`SESSION_MAP` 里保存的是什么？

#### 简洁回答

`SESSION_MAP` 存的不是管理员账号对象，而是 `sid -> Session` 的映射关系，也就是“客户端标识”对应的“WebSocket 连接对象”。后端后面广播消息时，真正依赖的是这些在线连接，而不是直接按账号对象推送。

#### 好背版本

- 不是存管理员账号
- 是存 `sid -> Session`
- 本质是在线连接表

### 24.6 高频问题：为什么 `sendToAllClient()` 发消息前还要检查连接状态？

#### 简洁回答

因为在线连接表里理论上保存的是当前可用连接，但实际网络环境里，某些连接可能已经断开、失效或者状态不同步。如果不先检查连接是否为空、是否还打开，就可能往一条已经失效的连接发消息，这样既没意义，也可能报错、浪费资源。所以广播前先校验连接状态，并顺手清理失效连接，会更稳。

#### 好背版本

- 先确认连接还活着
- 失效连接就清掉
- 避免无意义发送和广播报错

### 24.7 高频问题：为什么 `reminder()` 不是一上来就发 WebSocket？

#### 简洁回答

因为实时提醒也必须受业务规则约束。后端不能只因为前端点了催单按钮，就直接广播消息，而是要先确认当前用户是谁、订单是否存在、是否属于当前用户、当前状态是否允许催单。只有这些都通过，这次催单才是合法业务动作，后面才有资格被转换成一条实时提醒消息。

#### 好背版本

- 先判断这次催单合不合法
- 合法了才组装消息并广播
- 不是按钮一按就直接推送

### 24.8 高频问题：为什么 Day10 不能只做到“会弹提醒”？

#### 简洁回答

因为提醒本身不是业务终点，它只是订单处理链的入口。如果管理端只能看到提醒，却不能继续查看订单详情、执行接单、派送、完成等动作，那这条链最多只是“通知链”，还不是完整业务闭环。Day10 真正有价值的地方，是把“实时提醒”和“订单状态流转”接在了一起。

#### 好背版本

- 提醒不是终点
- 提醒后还得能处理订单
- 否则只是通知链，不是完整闭环

### 24.9 高频问题：为什么 `confirm()`、`delivery()`、`complete()` 都要先校验状态？

#### 简洁回答

因为订单状态流转必须受业务规则约束，不能任意跳状态。比如只有待接单的订单才能接单，只有已接单的订单才能进入派送中，只有派送中的订单才能完成。如果不做状态校验，就可能出现已取消订单还能派送、已完成订单再接单这类错误，整个订单链就会乱掉。

#### 好背版本

- 每个动作都只能发生在正确阶段
- 接单、派送、完成要一步一步走
- 不校验状态，订单流转就会乱

### 24.10 高频问题：Day10 这一块最值得讲的排障案例是什么？

#### 简洁回答

最值得讲的是：手工 `new WebSocket(...)` 能连通，但管理端页面自动连接却失败。这个现象说明后端 WebSocket 端点并不是完全坏的，问题更可能出在管理端前端自动连接逻辑。后来通过读取运行中的静态 bundle 和 sourcemap，最终定位到自动连接地址写错，修成根据当前页面 `location.host` 动态拼接后，管理端才真正恢复自动收提醒。同时浏览器缓存还会制造“明明改了、第一次打开还是旧效果”的假象，所以后来又沉淀出 `Ctrl + F5` 强刷这个重要经验。

#### 好背版本

- 手工连得通，不代表页面自动连接就对
- 最后定位到前端运行包里的 WebSocket 地址写错
- 修完后还要警惕浏览器缓存带来的假象

### 24.11 一个适合面试的 Day10 总结说法

可以这样说：

- Day10 这一块，我不是只接了一个 WebSocket，而是围绕订单域打通了一条实时提醒闭环。用户在小程序里发起催单后，后端会先校验当前用户身份、订单归属和订单状态，确认这次催单合法后，再组装成 JSON 消息，并通过 WebSocket 广播给当前在线的管理端页面。管理端收到提醒后，不只是弹一个通知，还能继续进入订单详情页并执行接单、派送、完成等处理动作。所以这一块最终形成的是“实时通知 + 订单状态流转”的完整业务闭环，而不是单纯的前端弹窗效果。
