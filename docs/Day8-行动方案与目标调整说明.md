# Day8 行动方案与目标调整说明

## 1. 为什么要调整 Day8 方案

Day8 原始主题是“下单与支付”，但在实际推进中我们确认了一个非常关键的现实边界：

- 课程允许我们重点理解真实微信支付流程
- 但个人开发环境通常不具备企业商户资质、真实证书和完整商户参数
- 因此“真实微信扣款成功”不应作为 Day8 的硬性完成标准

这不是知难而退，而是要在当前资源、项目结构和课程目标之间做更成熟的工程化取舍。

## 2. Day8 最新目标

Day8 的最新目标不是“强行打通真实扣款”，而是：

- 把用户端下单主链真正做通
- 把订单域后续核心能力尽量补齐
- 按真实微信支付架构保留支付主干设计
- 在拿不到真实商户资质时，用开发态模拟或替代验证手段，尽可能验证支付后的业务闭环

一句话版本：

- 在力所能及范围内，最大化接近真实支付项目的实现与展示效果，但不把外部商户环境作为必须打通的前提

## 3. Day8 已确定完成的部分

截至当前，已经完成并联调通过的内容有：

- 地址簿接口
- 提交订单主链
- 下单成功后购物车自动清空
- 待付款订单取消
- APIFox 用户端联调验证

这些内容都属于真实用户业务链的一部分，已经具备较强的项目展示价值。

## 4. Day8 后续的优先级顺序

后续不再按“先硬撞真实支付”推进，而是改为下面这个顺序：

1. 先补齐订单域接口与页面依赖
2. 每补一小块就立刻做 APIFox 或前端页面联调
3. 再补真实支付架构中的 `payment` 和 `paySuccess`
4. 最后增加开发态的模拟支付成功验证方式

优先级建议如下：

1. 订单详情
2. 历史订单
3. 再来一单
4. 支付接口主干
5. 支付成功回调主干
6. 开发态模拟支付闭环

## 5. 什么叫“最大化接近真实结果”

这里的“最大化接近真实”，具体不是指真正完成微信扣款，而是指：

- 下单后能生成待付款订单
- 前端能进入支付页
- 后端存在真实风格的支付入口
- 支付成功后存在统一的订单状态更新逻辑
- 订单详情、历史订单、成功页等位置能反映支付后的业务结果

也就是说，第三方支付平台本身可以受限，但我们自己系统内部的业务闭环要尽可能做实。

## 6. 什么不作为 Day8 的硬目标

以下内容不再作为 Day8 的硬性完成标准：

- 真实商户号下的微信扣款成功
- 企业资质相关材料的获取
- 课程外额外申请商户环境

原因很简单：

- 这些依赖外部资质和敏感证书
- 并不完全由当前项目代码能力决定
- 强行把它们当成当天必须完成的目标，会把项目推进带偏

## 7. 支付模块的最终落地思路

支付部分采用“双层目标”：

### 第一层：真实架构保留

- 保留 `PUT /user/order/payment`
- 保留支付成功回调入口
- 保留 `paySuccess(orderNumber)` 这类统一状态更新方法

这样未来只要补齐商户参数和证书，就有机会平滑切到真实环境。

### 第二层：开发态闭环验证

- 在当前个人开发环境下，不强行要求真实微信扣款
- 通过模拟支付成功或手动触发支付成功逻辑，验证支付后的订单状态变化
- 让前端页面也能看到“支付成功后”的业务效果

## 8. 面向简历和面试的价值

采用这个方案后，Day8 依然可以形成很强的项目表达：

- 我完成了用户端下单主链和订单域核心能力
- 我按真实微信支付架构设计了支付入口与支付回调链路
- 受个人开发环境缺少企业商户资质限制，未在本机完成真实扣款
- 但我通过开发态模拟和后端状态流转，验证了支付后的业务闭环

这个说法比“支付没做”更强，也比“硬说自己接通了真实微信支付”更稳。

## 9. 后续协作节奏不变

Day8 虽然目标调整了，但推进节奏不变：

- 一次只推进一小块
- 每做完一小块就立刻联调
- 联调以用户亲手在 APIFox 或页面中操作为主
- 当天代码和验证完成后，再进入复盘、源码讲解和话术沉淀

这条协作规则继续作为 Day8 的默认执行方式。
