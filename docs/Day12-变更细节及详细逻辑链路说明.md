## 1. Day12 这一阶段到底真正做了什么

如果只看课程标题，Day12 很容易被理解成：

- 工作台
- Excel 导出

但结合这次项目的真实推进过程，更准确的说法应该是：

- 把管理端首页需要的几组运营数据聚合成工作台看板接口
- 让工作台首页真正能展示“今日数据 + 订单总览 + 菜品总览 + 套餐总览”
- 把课程版项目里最后一个“文件下载型功能”补齐，完成运营数据报表导出

这次 Day12 真正完成并验证通过的内容包括：

- 工作台今日数据接口 `/admin/workspace/businessData`
- 订单总览接口 `/admin/workspace/overviewOrders`

- 套餐总览接口 `/admin/workspace/overviewSetmeals`

- Excel 文件下载与打开验证

一句话总结：

- Day12 真正补齐的是“管理端首页看板能力”，而 Excel 导出更多属于课程版完整性的收尾项。

## 3. Day12 的完整主链应该怎么理解

如果把这次 Day12 所有代码、接口和页面效果串成一条线，可以压缩成下面这 3 段：

### 3.1 首页看板入口：`WorkspaceController` 暴露工作台接口

- `WorkspaceController` 统一挂在 `/admin/workspace`
- 对外暴露了 4 个工作台接口
- Controller 只负责接请求、确定时间范围、调用 `workspaceService`

这里最重要的不是“多了几个 GET 接口”，而是：

- 管理端首页真正有了自己的数据入口层
- 前端工作台页面不再依赖散乱接口拼接，而是有了明确的数据来源

### 3.2 业务聚合层：`WorkspaceServiceImpl` 负责把多域数据加工成看板指标

- 工作台展示的并不是数据库原始字段
- 真正返回给前端的是经过业务口径加工后的结果，例如：
  - 营业额
  - 有效订单数
  - 订单完成率
  - 平均客单价
  - 新增用户数

所以 Day12 最值钱的部分，其实不在“导出 Excel”，而在于：

- 后端开始不只是提供原始数据
- 而是在提供“面向首页看板的业务指标”

### 3.3 文件下载层：`/admin/report/export` 负责导出运营数据报表

- 这条链本质是：
  - 查最近 30 天运营数据
  - 后端用 POI 生成 Excel
  - 通过响应流把文件下载给客户端

这部分功能真实、常见、课程里也该做，但如果从面试价值看：

- 它更适合作为“做过”的补全项
- 不适合作为简历主亮点

## 4. `workspace` 这块到底在做什么

Day12 最值得讲清楚的是 `workspace`，因为它比 `Excel 导出` 更有面试价值。

对应入口在：

- `com.sky.controller.admin.WorkspaceController`
- `com.sky.service.impl.WorkspaceServiceImpl`

它真正做的事不是：

- 把订单表、菜品表、套餐表原样查出来扔给前端

而是：

- 根据首页要展示什么，把多个业务域里的数据重新组织成“首页看板数据”

这就是工作台这块的真正含义。

## 5. `businessData` 为什么比看起来更重要

`GET /admin/workspace/businessData` 返回的是：

- `turnover`
- `validOrderCount`
- `orderCompletionRate`
- `unitPrice`
- `newUsers`

这里最值得记住的是：

- `turnover` 是已完成订单金额聚合结果
- `validOrderCount` 是已完成订单数量
- `orderCompletionRate` 不是数据库字段，而是后端自己算的
- `unitPrice` 也不是数据库字段，而是后端自己算的

这说明：

- 工作台展示的数据，并不是简单“查出来”
- 而是经过了后端业务指标加工

所以 `businessData` 真正练到的是：

- 聚合查询
- 指标口径设计
- 后端派生指标计算

## 6. `overviewOrders` 在做什么

`GET /admin/workspace/overviewOrders` 返回的是：

- 待接单数量
- 待派送数量
- 已完成数量
- 已取消数量
- 全部订单数量

这里值钱的地方不是 count 几次，而是：

- 首页要看的不是订单明细表
- 首页要看的是“今天订单状态分布”

也就是说：

- 后端不是给前端一堆订单列表让它自己算
- 而是直接给前端“看板需要的总览结果”

这是一种很典型的后台首页接口设计方式。

## 7. `overviewDishes` 和 `overviewSetmeals` 为什么虽然简单但合理

这两个接口分别返回：

- 已启售数量
- 已停售数量

它们从技术难度上看不复杂，但它们合理的地方在于：

- 首页工作台本来就不追求展示所有细节
- 它更关心的是“当前整体状态”

所以这两块接口虽然没有特别高的技术含量，但能说明：

- 你知道后台首页看板展示的是“总览”
- 而不是“把底表原样堆上去”

## 8. 为什么 `workspace` 有一定面试价值

如果从全集视角看，Day12 最值得保留到面试表达里的不是 `Excel 导出`，而是 `workspace`。

因为 `workspace` 至少能体现 4 个点：

- 后台首页不是简单 CRUD
- 页面展示口径和数据库结构不是一回事
- 有些指标需要后端派生计算
- 一个看板往往需要跨多个业务域聚合数据

所以 `workspace` 更适合作为：

- 项目能力的一部分

而 `Excel 导出` 更适合作为：

- 功能补全项

## 9. `Excel 导出` 这条链到底怎么理解

这一块虽然不适合当简历主卖点，但过程文档里还是要把它记清楚。

对应入口在：

- `com.sky.controller.admin.ReportController#export`
- `com.sky.service.impl.ReportServiceImpl#exportBusinessData`

这条链的本质不是“去操作用户电脑上的 Excel 软件”，而是：

- 后端查近 30 天运营数据
- 在服务器内存中动态生成一个 `.xlsx` 文件
- 再通过 HTTP 响应流把这个文件下载给客户端

也就是说：

- 后端负责生成文件
- 客户端负责接收和保存文件

## 10. 为什么企业里会有这种功能

Excel 导出虽然技术含金量不高，但在企业里非常常见。

常见场景包括：

- 导出订单
- 导出对账单
- 导出库存明细
- 导出日报、周报、月报
- 导出运营数据报表

原因很简单：

- 业务人员、运营、财务、管理层都很习惯用 Excel 看数据、发文件、做二次整理

所以这类功能业务上很真实，但面试上不一定值得大讲特讲。

## 11. 为什么企业里的大导出一般要异步

这次课程版项目里我们做的是同步导出，因为：

- 数据量小
- 目标是理解文件下载链路

但如果换成企业里的大导出场景，比如几十万条订单一起导：

- 一次 HTTP 请求会被长时间占住
- 数据库压力会变大
- Java 内存容易被大工作簿拖高
- 用户也会长时间等待

所以企业里更常见的是：

- 用户先创建导出任务
- 后端后台异步生成文件
- 文件生成后再给用户下载链接

这一点非常适合当作拓展理解，但不属于当前课程版 Day12 必须实现的范围。

## 13. Day12 最值得带走的工程认识

这次 Day12 里，最值钱的工程认识至少有 3 个。

### 13.1 首页看板接口通常是“聚合接口”，不是“底表接口”

一个成熟后台首页展示的数据，往往来自多个业务域：

- 订单
- 用户
- 菜品
- 套餐

所以首页接口更像“数据聚合器”，而不是某张表的直接查询接口。

### 13.2 派生指标应该由后端统一口径计算

像：

- 订单完成率
- 平均客单价

这种指标不应该交给前端临时各算各的，而更适合由后端统一算好后返回。

这样：

- 口径统一
- 页面更轻
- 也更符合真实项目里的职责分工

### 13.3 “业务上常见”不等于“简历上值得主打”

Excel 导出在企业里非常常见，也确实是一个真实需求。

但从面试价值来看，它更多是：

- 功能补全
- 课程版项目收尾

而不是：

- 最值得讲的项目核心卖点
