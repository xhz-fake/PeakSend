## 5. Day7 真实打通的链路

### 5.1 菜品缓存链

已经真实验证通过：

- 用户端携带 `authentication` 请求头访问 `/user/dish/list`
- JWT 拦截器解析 token 并识别当前用户
- 第一次按 `categoryId` 查菜品时回库
- 查询 `dish` 和 `dish_flavor`
- 返回结果自动写入 `dishCache`
- 第二次相同分类请求直接命中缓存
- 管理端变更菜品后清缓存
- 用户端再次查询时重新回库并重建缓存

## 6. Day7 必须继承的关键认识

### 6.1 Spring Cache 和 Redis 的关系

固定理解为：

- Spring Cache 是缓存抽象和规则声明层
- Redis 是底层真正存缓存数据的介质

### 6.2 当前缓存的粒度

固定理解为：

- 菜品缓存按 `categoryId` 缓存整份分类菜品列表
- 套餐缓存按 `categoryId` 缓存整份分类套餐列表

不要误讲成：

- 缓存的是单个菜品
- 缓存的是单个套餐对象

### 6.3 用户端展示范围

固定理解为：

- 用户端查询数据库时已经带了 `status = ENABLE`
- 所以只展示起售中的菜品和套餐
- 缓存里天然也只会出现起售中的数据

### 6.4 JWT 拦截和缓存是两层逻辑

必须区分：

- JWT 拦截器负责确认当前请求用户身份是否合法
- 缓存负责决定数据从 Redis 取还是从 MySQL 查

所以即使缓存命中：

- JWT 拦截器仍然要先执行

### 6.5 APIFox 双 token 规则

后续联调必须坚持：

- 管理端请求头名：`token`
- 用户端请求头名：`authentication`

变量分开存：

- `adminToken`
- `userToken`

不要再混成一个统一 `token`。

## 7. Day7 过程中踩到并必须保留的坑

### 7.1 Redis 服务不是 “PONG” 就算项目接通

必须记住：

- `redis-cli ping -> PONG` 只能说明 Redis 自己活着
- 是否真正对项目可用，还要看 Spring Boot 能否正常访问 Redis 相关接口

### 7.2 Redis 配置里有密码时，后端必须同步配置

这次真实踩到的问题是：

- Redis 开了 `requirepass`
- 但 Spring Boot 一开始没配 `spring.redis.password`
- 导致后端报 `NOAUTH Authentication required`

### 7.3 APIFox 变量作用域会影响联调结果

必须记住：

- `{{userToken}}` 发红，不一定是 token 失效
- 很可能是这个变量没有配置在当前接口所属模块里

### 7.4 变量名不等于请求头名

必须记住：

- `userToken` 和 `adminToken` 是 APIFox 变量名
- 后端真正识别的请求头名分别是：
  - `authentication`
  - `token`
