# Day15-变更细节及详细逻辑链路说明

## 1. Day15 这一阶段真正要解决的是什么

Day15 的问题，不再是“读请求太多，要不要缓存”。

它要解决的是另一类经典后端题：

- 有一个限量资源
- 很多人会同时来抢
- 库存不能超扣
- 同一个人不能重复成功
- 管理端还要能控制活动启停和查看结果

如果这种场景只靠数据库来硬扛，通常会有两个问题：

- 热点竞争都打到数据库，压力会很集中
- 多个校验拆在 Java 里做时，很容易出现并发窗口

所以 Day15 选择的路线不是：

- 在数据库里反复查、反复锁、反复判断

而是：

- 把热点竞争校验前移到 Redis
- 用 Lua 脚本把关键判断和库存扣减收成一次原子执行
- 再把最终结果持久化到 MySQL

一句话概括：

- Day15 的主线是“Redis 原子校验 + 数据库最终持久化 + 页面真实联调”

## 2. 为什么业务壳子选“限量套餐活动”

Day15 的候选壳子本来有两类：

- 限量优惠券领取
- 限量套餐活动

最终选择“限量套餐活动”，原因不是它名字更花，而是它和当前项目结合更自然。

因为当前项目已经有：

- 套餐数据
- 小程序商品展示链路
- 管理端运营视角

所以限量套餐活动更容易挂到现有系统上，形成真实入口，而不是新开一个和项目主线割裂的业务域。

最终落地后，这个选择也被证明是对的，因为我们真的补出了：

- 管理端活动管理页
- 小程序活动入口和活动页

也就是说，这个壳子没有停留在“接口演示”，而是真的并进了现有产品形态。

## 3. Day15 的数据模型是怎么设计的

这次新增了两张表。

### 3.1 活动表：`flash_sale_setmeal_activity`

这张表负责描述一个“限量套餐活动”本身。

它至少要回答这些问题：

- 这个活动对应哪个套餐
- 活动叫什么
- 套餐名称/价格/图片的展示快照是什么
- 现在总库存是多少
- 当前状态是启用还是停用
- 活动开始和结束时间是什么

这样设计的好处是：

- 活动自己就具备完整展示信息
- 抢购时不必每次都再去拼装一大堆套餐字段

### 3.2 抢购记录表：`flash_sale_setmeal_order`

这张表负责描述“谁抢到了什么”。

它至少要记录：

- 活动 id
- 用户 id
- 套餐 id
- 抢购单号
- 活动名/套餐名/价格/图片快照
- 抢购状态
- 创建时间

这里最关键的是两个唯一约束：

- `activity_id + user_id`
- `order_no`

其中：

- `activity_id + user_id` 是数据库层面对“一人一单”的兜底保障
- 即使 Redis 前置校验已经做了，数据库层仍然应该保留最终约束

## 4. Redis 里到底存了什么

Day15 不是把整条订单直接塞进 Redis。

Redis 只存最适合做热点竞争控制的那部分数据。

### 4.1 活动 Hash

Key 形态：

- `flashsale:activity:{activityId}`

里面存的是活动最关键的几个热点字段：

- `setmealId`
- `startTime`
- `endTime`
- `stock`
- `status`

为什么存 Hash？

因为这些字段天然属于同一个活动对象，而且抢购脚本需要一起读。

### 4.2 已抢购用户 Set

Key 形态：

- `flashsale:activity:{activityId}:users`

里面存的是已经成功抢到过该活动的用户 id。

为什么存 Set？

因为它最适合回答这个问题：

- 这个用户是不是已经抢过了

判断方式就是：

- `SISMEMBER` / Lua 里判断集合是否包含该用户

这样“一人一单”的资格校验就可以在 Redis 这一层直接完成。

## 5. 为什么必须用 Lua，而不是在 Java 里多调几次 Redis

这个问题是 Day15 的核心。

如果不用 Lua，而是在 Java 里按下面这种顺序做：

1. 查活动状态
2. 查活动时间
3. 查库存
4. 查用户是否已经抢过
5. 扣库存
6. 记录用户已抢

那么在并发场景下，这些动作之间就会有窗口期。

比如：

- 线程 A 查到库存还有 1
- 线程 B 也查到库存还有 1
- 两边都继续扣减

这样就可能出现超扣。

Lua 的价值就在于：

- 把这些关键判断和修改收成 Redis 内部一次脚本执行
- 对 Redis 来说，这次脚本执行是原子的
- 执行过程中不会被别的命令插进来打断

所以 Day15 真正要讲的不是“我会写 Lua”，而是：

- **我需要把高并发下的多段 Redis 校验收成一次原子执行**

## 6. 后端主链路是怎么走的

核心实现文件：

- [FlashSaleSetmealActivityServiceImpl.java](file:///D:/ProgramFiles/CodeProjects/PeakSend/peaksend-backend/sky-server/src/main/java/com/sky/service/impl/FlashSaleSetmealActivityServiceImpl.java)

可以把这条主链拆成四块来看。

### 6.1 管理端创建活动

管理端创建活动时，系统做的不是单纯插一条表记录。

它至少做了这些事：

1. 校验套餐是否存在
2. 校验库存是否合法
3. 校验状态是否合法
4. 校验时间区间是否合法
5. 生成活动记录并落库
6. 把活动热点字段预热到 Redis
7. 如果活动已存在成功用户，还会把用户集合一起预热

这里“预热到 Redis”很关键，因为后面的抢购链路不是临时查库现拼，而是直接打热点缓存。

### 6.2 用户端查询当前可抢活动

用户端并不是去查“所有活动”，而是查当前时间下可抢、可展示的活动。

它最终返回给小程序的是适合直接展示的活动列表，包括：

- 活动名
- 套餐名
- 价格
- 图片
- 库存
- 活动时间

所以小程序那一页能直接显示，不需要再额外拼很多次接口。

### 6.3 用户端点击抢购

这是 Day15 的主战场。

点击“立即抢购”后，后端大致按下面这条链走：

1. 拿到当前用户 id
2. 准备活动 Hash key 和用户 Set key
3. 调用 Lua 脚本做原子校验：
   - 活动是否存在
   - 是否已开始
   - 是否已结束
   - 是否启用
   - 库存是否足够
   - 用户是否已经抢过
4. 如果脚本返回成功：
   - Redis 里的库存已被扣减
   - Redis 里的用户集合已写入当前用户
5. 再进入数据库持久化：
   - 更新活动库存
   - 写入抢购记录
6. 组装返回值给前端：
   - 活动 id
   - 套餐 id
   - 抢购单号

### 6.4 持久化失败时为什么要回补 Redis

这次实现里还有一个很重要的细节：

如果 Lua 已经把 Redis 里的库存扣掉了，但后续数据库落库失败了，就不能直接算了。

否则会出现：

- Redis 看起来少了一份库存
- 但数据库里根本没有成功订单

这会让库存状态失真。

所以这次实现里做了回补动作：

- 持久化失败时，把 Redis 里的库存加回去
- 同时把用户从已抢购集合里移除

这一步是 Day15 很有价值的工程意识点，因为它说明我们没有把“Redis 成功”误当成“整条业务就真的成功”。

## 7. 一人一单为什么不是只靠一个地方做

这次“一人一单”实际上是双层保护。

### 7.1 Redis 前置校验

这是第一层，也是高并发主链最重要的一层。

它的作用是：

- 尽早把重复请求拦在热点竞争前面
- 避免无意义请求继续打数据库

### 7.2 数据库唯一约束兜底

这是第二层。

即使 Redis 理论上已经挡住了重复抢购，数据库层仍然保留：

- `uk_flash_sale_activity_user`

它的意义是：

- 防止极端情况下出现重复成功记录
- 给最终一致性再上一层保险

所以正确的工程理解不是：

- “我已经有 Redis 了，就不需要数据库约束”

而是：

- “Redis 负责前置拦截和高并发承压，数据库负责最终落库约束”

## 8. 删除限制为什么必须有

Day15 的管理端不是只有创建、启停，还补了删除。

但删除不是随便删。

规则是：

- 只有没有抢购记录的活动才允许删除

为什么？

因为一旦活动已经有用户抢购成功，数据库里就会有真实业务记录。

如果这时把活动主记录直接删掉，就会带来两个问题：

- 管理端审计视角会断裂
- 用户抢购记录和活动主数据之间的业务语义会被破坏

所以已有抢购记录的活动只能：

- 继续保留
- 允许启停
- 不允许物理删除

这条规则已经通过管理端页面真实验证过。

## 9. 前端为什么必须补，不补会有什么问题

这是 Day15 非常关键的一次经验。

如果只做到：

- 有后端接口
- 有 Redis Lua
- 有数据库表

然后就结束，其实还不够。

因为面试官或项目评估者很容易继续追问：

- 管理员怎么创建活动

如果这些问题回答成：

- “我用 curl 验证过”

那整个功能的真实感会明显下降。

所以这次最终补了两条前端链：

- 管理端活动管理页
- 小程序活动页

它们的价值，不只是“有页面好看”，而是让 Day15 从接口能力变成了真实产品能力。

## 10. 这次真实联调到底验证了哪些业务规则

这次不是只验证“抢购成功”。

真正闭环掉的规则包括：

### 10.1 创建活动可见

- 管理端页面创建活动成功
- 小程序页面能看到活动

### 10.2 抢购成功会联动库存和记录

- 第一次抢购成功
- 小程序库存从 `10 -> 9`
- 我的抢购记录出现订单号
- 管理端刷新后库存也变成 `9`

### 10.3 同一用户不可重复抢购

- 第二次点击后提示：
  - `同一用户不可重复抢购`

### 10.4 停用后不能继续抢

- 管理端点“停用”
- 小程序再次点击后提示：
  - `限量套餐活动未启用`

### 10.5 已有抢购记录的活动不能删除

- 管理端尝试删除
- 页面提示：
  - `该活动已有抢购记录，不允许删除`

### 10.6 重新启用后，仍然受一人一单约束

- 管理端重新启用
- 小程序仍然会因为已抢过而被拦截

这一组验证说明：

- 活动状态规则
- 一人一单规则
- 库存规则
- 删除规则

彼此之间没有互相冲掉。

## 11. Day15 最值得讲给面试官的点

### 11.1 为什么高并发资源竞争不能只靠数据库

可以这样答：

- 因为这种限量资源场景会在短时间内把大量请求压到同一条记录上，如果所有资格判断和库存扣减都放在数据库，数据库会承受很重的热点竞争压力，而且多段逻辑拆开做时还容易出现并发窗口。所以我把活动时间、状态、库存和用户资格这些高频判断前移到 Redis，用 Lua 脚本做原子校验，再把结果持久化到 MySQL。

### 11.2 为什么 Lua 比 Java 里多次调 Redis 更稳

可以这样答：

- 因为 Java 里多次调用 Redis 时，中间会有窗口期；而 Lua 脚本是在 Redis 内一次执行完关键校验和库存扣减，天然更适合这种需要原子性的热点竞争场景。

### 11.3 这个功能为什么更像真实项目，而不是练习题

可以这样答：

- 因为我最后不是只把接口跑通，而是把它真正接进了管理端和小程序。管理员可以在页面创建、启停、查看活动，用户可以在小程序里看到活动、点击抢购、查看抢购记录，而且库存、状态和删除限制都完成了前后端联动验证。

## 12. Day15 最值得反复记住的几句话

- Day14 解决的是“读多写少怎么缓存”，Day15 解决的是“热点资源怎么原子控制”。
- Lua 的价值不是脚本本身，而是把多段 Redis 校验收成一次原子执行。
- Redis 负责前置拦截和热点承压，数据库负责最终落库和唯一约束兜底。
- 页面真实点通之后，这个功能才真正从“接口能力”升级成“产品能力”。
