# 订单延迟关单量化留档

## 1. 这组数字对应什么能力

- 下单后发送 `RocketMQ` 延迟消息
- 到期后由消费端二次校验订单状态
- 仅对“待付款 + 未支付”的订单执行自动取消

## 2. 版本边界

- 当前稳定版本：`Day16`
- 对应链路：
  - `OrderServiceImpl.submitOrder(...)`
  - `RocketMqOrderDelayCloseMessagePublisher`
  - `OrderDelayCloseConsumer`
  - `OrderDelayCloseHandleService`
- 当前代表性样本：
  - `orderId=14`
  - `orderNumber=1786938624333`

## 3. 测量方法

- 真实提交一笔订单，拿到订单号与下单时间
- 通过后端日志确认：
  - 延迟消息发送成功
  - 消费者收到消息
  - 关单事务执行成功
- 再直接查询 MySQL：
  - 对比 `order_time` 与 `cancel_time`
  - 计算 `timestampdiff(second, order_time, cancel_time)`
- 最后核对订单状态与取消原因，确认不是“消息到了但状态没改”

## 4. 原始数据

代表性日志时间点：

- 发送订单延迟关单消息成功：`2026-08-17 11:50:24.432`
- 收到订单延迟关单消息：`2026-08-17 11:50:34.471`
- 延迟关单消费成功：`2026-08-17 11:50:34.486`

MySQL 对账结果：

- `order_time = 2026-08-17 11:50:24`
- `cancel_time = 2026-08-17 11:50:34`
- `delay_seconds = 10`
- `status = 6`
- `pay_status = 0`
- `cancel_reason = 支付超时，系统自动取消`

由此得到当前稳定版本下的代表性结果：

- 下单到自动关单：约 `10s`
- 延迟消息触发精度已达到秒级

## 5. 最终结论

- 当前 Day16 稳定版本已经形成“下单 -> 发送延迟消息 -> 到期消费 -> 状态二次校验 -> 自动取消”的完整闭环
- 在当前代表性样本中，自动关单触发耗时约 `10s`
- 由于消费端带有状态校验，这条链的关键价值不只是“会自动关单”，更是“重复消息或状态已变化时不会误取消”

## 6. 可写进简历/话术库的句子

- 基于 RocketMQ 延迟消息重构订单超时关单链路，下单后自动预约关单事件，代表性样本中关单触发耗时约 `10s`，并通过消费端状态二次校验避免误关单。
