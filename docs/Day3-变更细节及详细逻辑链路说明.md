# Day3-变更细节及详细逻辑链路说明

## 1. Day3 这一小阶段到底做了什么

Day3 当前先完成的，不是菜品接口，而是一个很关键的“代码整理升级”：

- 把公共字段自动填充做起来

说白了，就是把这些原来需要手动写的字段：

- `createTime`
- `updateTime`
- `createUser`
- `updateUser`

从员工模块、分类模块的 Service 里抽出来，改成统一自动处理。

## 2. 为什么要改这件事

因为我们前两天已经见过很多类似代码了。

每次新增数据时，常常都要写：

- 创建时间
- 更新时间
- 创建人
- 修改人

每次修改数据时，常常又要写：

- 更新时间
- 修改人

如果这些代码一直散落在每个 Service 里，会有 3 个明显问题：

1. 重复代码很多
2. 很容易漏写
3. 后面模块变多后会越来越乱

所以 Day3 第一刀不是继续堆新接口，而是：

- 先把重复逻辑集中收口

## 3. 这次新增了哪些关键文件

### 1）`AutoFill.java`

这个文件是一个自定义注解。

它的作用不是去执行逻辑，而是先打一个“标签”：

- 这个 Mapper 方法需要自动填充公共字段

同时它还会带一个值，用来说明：

- 这次操作是新增
- 还是修改

也就是：

- `OperationType.INSERT`
- `OperationType.UPDATE`

你可以把它理解成：

- 给方法贴一张便利贴
- 告诉系统“这个方法执行前，记得先帮我补字段”

### 2）`AutoFillAspect.java`

这个文件才是真正干活的地方。

它是一个 AOP 切面。

你先不用把 AOP 想得太复杂，可以先这么理解：

- 某些方法执行前
- 程序先偷偷插进来做一件统一的事情
- 做完后再继续执行原方法

这次它做的统一事情就是：

- 在 Mapper 的新增或修改方法执行前
- 自动给实体对象补时间和用户 id

## 4. 这次改了哪些旧文件

### 员工模块

- `EmployeeMapper`
- `EmployeeServiceImpl`

### 分类模块

- `CategoryMapper`
- `CategoryServiceImpl`

其中最关键的变化有两类。

第一类：在 Mapper 方法上打标记。

也就是：

- 新增方法打 `@AutoFill(OperationType.INSERT)`
- 修改方法打 `@AutoFill(OperationType.UPDATE)`

第二类：把 Service 里那些重复的手动赋值代码删掉。

比如以前常见的这些写法：

```java
employee.setCreateTime(LocalDateTime.now());
employee.setUpdateTime(LocalDateTime.now());
employee.setCreateUser(...);
employee.setUpdateUser(...);
```

现在不再由 Service 手动负责，而是交给切面统一处理。

## 5. 为什么注解打在 Mapper 上，而不是打在 Service 上

这是今天特别值得理解的点。

因为“自动填充公共字段”这件事，本质上最贴近的是：

- 数据即将写入数据库的那一刻

而真正执行“插入数据库 / 更新数据库”的地方，就是 Mapper。

所以把注解打在 Mapper 上，意思就是：

- 只要这个数据库方法要执行了
- 我就先补好字段

这样做有两个好处：

1. 离数据库写入更近，不容易漏
2. 不管是谁调用这个 Mapper，只要打了注解，都能统一生效

## 6. 这套机制完整是怎么跑起来的

你可以把整个过程看成下面这条链路。

### 第一步：前端发请求

比如你新增员工，或者修改分类。

前端把数据发到 Controller。

### 第二步：Controller 接住请求

Controller 负责：

- 接收参数
- 调 Service
- 返回结果

它本身不负责补公共字段。

### 第三步：Service 处理业务

Service 负责真正的业务逻辑。

比如：

- 新增员工时设置默认密码
- 新增分类时设置默认状态
- 做一些查重或业务判断

但这次之后，Service 不再负责手动写创建时间、更新时间、创建人、修改人。

### 第四步：调用 Mapper 方法

当 Service 调用 `insert()` 或 `update()` 时，因为这些 Mapper 方法上已经有了 `@AutoFill`，所以切面会先介入。

### 第五步：切面先执行

`AutoFillAspect` 会先做这几件事：

1. 拿到当前执行的是哪个方法
2. 读取这个方法上的 `@AutoFill`
3. 判断这次是新增还是修改
4. 拿到方法参数中的实体对象
5. 生成当前时间
6. 从 `BaseContext` 里拿当前登录人的 id
7. 通过反射调用实体对象的 setter 方法

如果是新增：

- 补 `createTime`
- 补 `createUser`
- 补 `updateTime`
- 补 `updateUser`

如果是修改：

- 补 `updateTime`
- 补 `updateUser`

### 第六步：Mapper 再去执行 SQL

等切面把实体对象补完后，Mapper 再按原计划执行插入或更新 SQL。

这时数据库里拿到的对象，已经带着完整的公共字段了。

## 7. `BaseContext` 在这里起了什么作用

这个点你一定要抓住。

我们现在不是写死一个用户 id，而是希望：

- 谁登录了系统
- 就记住谁在操作

项目里这个“当前登录人 id”的保存位置，就是 `BaseContext`。

你可以把它理解成：

- 每次请求进来后
- 当前线程口袋里会放一张小纸条
- 上面写着当前登录人的 id

后面走到切面时，就能把这张小纸条拿出来用。

所以 `createUser` 和 `updateUser` 才能自动写成当前登录人的 id。

## 8. 为什么这里用到了反射

因为切面面对的不是某一个固定实体。

今天可能是：

- `Employee`

明天可能是：

- `Category`
- `Dish`
- `Setmeal`

如果把代码写死成只处理某一个类，就没法通用了。

所以这里用了反射，按方法名动态去调用：

- `setCreateTime`
- `setUpdateTime`
- `setCreateUser`
- `setUpdateUser`

这样只要某个实体有这些 setter，这套逻辑就能复用。

你可以把反射先理解成：

- 程序运行时，临时决定“我要调用哪个方法”

## 9. Service 现在还负责什么，不负责什么

这也是今天很容易混淆的点。

### Service 现在还负责的

- 员工默认密码
- 员工账号查重
- 分类默认启用状态
- 各自业务自己的判断逻辑

### Service 现在不再负责的

- 手动写 `createTime`
- 手动写 `updateTime`
- 手动写 `createUser`
- 手动写 `updateUser`

这就是一次很典型的职责收缩：

- 让 Service 更专注于业务
- 让公共字段这种通用动作交给统一组件

## 16. 菜品管理为什么比前两天更重要

因为员工、分类更多还是单表 CRUD。

但菜品管理开始不一样了。

它背后至少涉及两张表：

- `dish`：菜品主表
- `dish_flavor`：菜品口味表

这就意味着你不能再把它理解成“前端发一份 JSON，数据库插一行就结束了”。

现在真正发生的是：

- 一道菜本身要存一条主记录
- 这道菜下面的多个口味也要分别存起来

这就是典型的一对多。

## 17. 新增菜品这条链路是怎么跑的

新增菜品时，前端发来的不只是菜品本身的数据，还会带一组口味列表。

执行过程可以理解成：

1. Controller 接住整份 `DishDTO`
2. Service 先把菜品主信息拷贝到 `Dish`
3. 调用 `DishMapper.insert()` 保存主表
4. 因为主表用了自增 id，所以插入成功后会拿到新的菜品 id
5. 再把这个菜品 id 塞给每一条口味
6. 最后批量插入 `dish_flavor`

所以你后来在数据库里看到的是：

- `dish` 表新增 1 条
- `dish_flavor` 表新增多条

这不是巧合，而是代码就是这样设计的。

## 18. 为什么这里必须上事务

菜品新增、修改、删除都不是“一条 SQL 就完事”的动作。

比如新增菜品时：

- 先插 `dish`
- 再插 `dish_flavor`

如果第一步成功了，第二步失败了，就会留下半截数据。

所以这里必须用事务去保证：

- 要么整套都成功
- 要么整套都失败

你可以先把事务理解成：

- 给一组数据库操作绑成同生共死的一包

## 19. 菜品分页查询到底做了什么

分页查询不是简单地把 `dish` 表全查出来。

真正返回给前端列表页的数据，还要尽量贴合页面展示需求。

所以我们在分页查询里做了两件事：

1. 按页查菜品
2. 顺手把分类名称也查出来

这就是为什么你在返回结果里看到的不只是：

- `id`
- `name`
- `price`

还额外看到了：

- `categoryName`

这说明这次查询不是只查了主表，而是做了关联查询。

## 20. 为什么删除菜品不能直接删

这是今天特别值钱的一个点。

删除在真实项目里，通常不是“看到按钮就删”。

而是要先判断这条数据当前允不允许删。

我们这次已经实际验证过第一条规则：

- 起售中的菜品不能删除

执行逻辑是：

1. 先根据 id 查出这道菜
2. 看它的 `status`
3. 如果还是起售状态，就直接拦住
4. 给前端返回错误信息

你也亲手测到了：

- 返回 `起售中的菜品不能删除`

这就说明我们的删除不再是“硬删数据库”，而是“先过业务规则，再决定能不能删”。

## 21. 为什么删除时还要删口味表

因为一道菜删掉了，它下面那几条口味就不应该继续孤零零留在数据库里。

所以当菜品允许删除时，真正执行的是：

- 删除 `dish`
- 删除对应的 `dish_flavor`

你已经在控制台里看到了：

- 主表删 1 条
- 子表删 2 条

这说明我们做的是联动删除，而不是只删了一半。

## 22. 修改菜品为什么不是直接 update 一下就完

因为菜品修改不只是改主表字段。

它还可能改口味。

比如你这次把旧口味：

- `温度`

改成了新口味：

- `分量`

这就意味着修改动作其实分成两块：

### 第一块：改主表

比如：

- 菜品名
- 价格
- 描述
- 状态

### 第二块：重建口味

现在这套实现用的是一个很常见、也很好理解的策略：

1. 先更新 `dish`
2. 再把这道菜旧的口味全删掉
3. 再把前端传来的新口味重新插入

你可以把它理解成：

- 不去做复杂的“逐条比对口味差异”
- 而是直接用“删旧建新”的方式保证最终结果正确

## 23. 为什么修改前一定要先查详情

编辑页面不是空白的。

当你点“修改菜品”时，前端要先知道这道菜原来长什么样。

所以编辑功能的标准流程永远都是：

1. 先 `GET /admin/dish/{id}`
2. 页面回显旧数据
3. 用户修改
4. 再 `PUT /admin/dish`

你已经实测过：

- 根据 id 查询菜品时，主表信息能查回来
- 对应口味数组也能一起查回来

这就说明编辑页面真正需要的“旧数据回显基础”已经具备了。

## 24. 今天非常值得记住的高价值问题

### 问题 1：为什么自动填充要放在 Mapper 前，而不是 Service 里？

因为公共字段本质上是“数据库写入前的统一动作”。

把它放在 Mapper 前，离数据库更近，不容易漏，而且所有模块都能复用。

### 问题 2：为什么菜品管理突然变复杂了？

因为从这里开始，你第一次真正碰到了多表业务。

不是一张表自己玩，而是：

- 主表负责主体信息
- 子表负责扩展信息

### 问题 3：为什么删除前还要拦一下？

因为后端不只是执行数据库命令，还要守住业务规则。

“能不能删”本身就是业务判断，不是数据库替你决定的。

### 问题 4：为什么修改口味时要删旧再插新？

因为这是一种实现成本低、逻辑清晰、很适合当前学习阶段的做法。

它不一定是世界上唯一方案，但对现在这个项目来说非常实用。

## 25. 今天已经暴露出的前后端联调问题

今天还暴露出了两个非常典型的联调问题：

### 1）前端并不是只依赖你已经做过的“主接口”

你在调菜品页面时，后端日志里出现了：

- `No mapping for GET /admin/category/list`
- `No mapping for POST /admin/common/upload`

这说明一个页面能不能正常用，往往不只依赖“新增菜品 / 修改菜品”这类主接口。

页面还常常依赖一些配套接口，比如：

- 查询分类下拉框
- 上传图片

所以以后做功能时，不能只盯住最显眼的那个接口，要把整个页面依赖链都看全。

### 2）页面现象不一定说明主业务错了

比如今天：

- 菜品详情查询本身是成功的
- 但页面还是出现图片灰色、上传失败

这时候不能直接怀疑“菜品查询写错了”。

而要学会拆开看：

- 查详情接口是否成功
- 分类下拉接口是否成功
- 上传接口是否存在
- 图片 URL 本身是不是脏数据

这就是更成熟的排错思路。

## 26. 关于今天图片灰色和上传失败，应该怎么理解

从后端日志来看，今天至少已经明确两件事：

### 第一件事：上传失败的直接原因，不是上传逻辑报异常，而是接口压根不存在

日志里已经明确写了：

- `No mapping for POST /admin/common/upload`

这说明前端发起了上传请求，但后端当时根本没有这个入口。

### 第二件事：编辑页还依赖分类列表接口

日志里还写了：

- `No mapping for GET /admin/category/list`

这说明前端在打开菜品编辑页时，不只是查了菜品详情，还想查分类列表去填充下拉框。

也就是说，页面是否正常，不取决于一个接口，而取决于整套接口链是否完整。

### 第三件事：图片灰色还可能和图片字段本身的数据质量有关

我们前面测试时，有些图片地址被带进了额外的反引号或空格。

这类“脏图片地址”会导致前端虽然拿到了字符串，但浏览器实际无法正确显示图片。

所以图片灰色的排查顺序应该是：

1. 先确认图片 URL 是否真的有效
2. 再确认页面是否能正确拿到这个 URL
3. 再确认上传接口是否能生成新的、干净的图片地址

## 29. 今天后面额外补上的前端依赖接口

在我们把菜品管理主链跑通后，前端页面联调时又暴露了两个很典型的问题：

- `GET /admin/category/list` 不存在
- `POST /admin/common/upload` 不存在

这两个问题特别值得记住，因为它们说明：

- 页面能不能正常工作，不只取决于“新增菜品 / 修改菜品”这种主接口
- 还取决于很多页面级依赖接口是否补齐

这次具体补上的内容有：

### 1）分类下拉框接口

接口：

- `GET /admin/category/list`

作用：

- 给前端菜品编辑页提供“菜品分类下拉框”数据

如果没有这条接口，页面虽然能打开，但分类选择框就会残缺。

### 2）通用上传接口

接口：

- `POST /admin/common/upload`

作用：

- 接收前端选中的图片文件
- 保存图片
- 返回图片访问地址

如果没有这条接口，前端点击上传时就会直接报 404。

## 30. 为什么我们最后改成了“本地图片上传”

原课程的思路更偏向：

- 上传到阿里云 OSS

但我们在当前阶段没有继续硬走这条路，而是改成了：

- 上传到本地目录

原因很简单：

1. 你当前最重要的是先把业务链和联调链跑通
2. 直接上 OSS 会把注意力拉去云产品配置，容易打断主线学习
3. 本地上传更适合现在这个项目阶段

所以这次我们把图片资源先放在：

- `PeakSend/uploads`

并且让后端第一次上传时自动创建这个目录。

## 31. 本地上传方案具体是怎么工作的

这次本地上传不是“手动把图片扔到某个文件夹”这么简单。

真正的过程是：

1. 前端把本地图片传给 `POST /admin/common/upload`
2. 后端收到文件后，自动生成一个随机文件名
3. 把图片保存到本地 `uploads` 目录
4. 再返回一个浏览器可访问的地址

比如会返回这种地址：

- `http://localhost:8080/uploads/xxxxxx.jpg`

然后前端再把这个地址塞到菜品表单里，最后和菜品其他信息一起提交保存。

所以数据库里 `dish.image` 存的不是“图片本体”，而是：

- 图片访问地址

这和企业里对象存储的思路其实是一致的，只不过现在先把存储位置从“云端”换成了“你本机磁盘”。

## 32. 企业里图片一般放在哪里

这个问题今天非常值得记下来。

一般企业里，图片通常不会直接塞进数据库字段本体里，也不适合长期放在应用服务器本地目录里。

更常见的做法是：

- 阿里云 OSS
- 腾讯云 COS
- 七牛云
- AWS S3
- 公司自建对象存储

数据库里真正保存的，往往只是：

- 图片 URL

所以今天我们做的“本地上传”可以理解成：

- 先用最简单的方式把链路跑通

以后如果要迁移到云端，思路也很清晰：

- 只要把上传接口内部逻辑从“保存到本地”换成“上传到 OSS”
- 然后返回云端 URL 即可

这说明今天的本地方案不是死路，而是一个很合理的过渡方案。

## 33. 我们今天第一次真正看到了前端是怎么来的

你之前一直在看数据库、后端、APIFox，这很正常。

但今天这个前端问题逼着我们第一次真正去理解：

- 现在跑在浏览器里的前端，到底是什么

这次我们确认到：

- 你现在跑的是一套已经打包完成的前端静态资源

它实际所在的位置是：

- `FrontRunEnv/nginx-1.20.2/html/sky`

里面主要有：

- `index.html`
- `css/*.css`
- `js/*.js`

也就是说，浏览器真正加载的是：

- 打包后的 HTML
- 打包后的 CSS
- 打包后的 JS

而不是你平常想象中那种零散的 Vue 源码文件直接在运行。

## 34. 为什么我还能定位到前端问题

因为这套打包产物还带了：

- `source map`

你可以先把它理解成：

- 打包后代码和原始源码之间的一张“对照表”

靠着这张对照表，我们最后成功定位到了：

- 菜品编辑页组件
- 图片上传组件
- 菜品接口定义文件

这一步非常值钱，因为它说明以后就算拿到的不是前端源码仓库，只要打包产物和 sourcemap 在，有时依然能做深入排查。

## 35. 那个“菜品名称输入不符”到底是怎么回事

这次最后一个很有价值的坑，就是前端页面明明看起来能输入名字，但点保存时却老提示：

- `菜品名称输入不符，请输入2-20个字符`

最后我们不是猜出来的，而是直接顺着 sourcemap 反查到了运行中的前端规则。

定位结果是：

- 菜品编辑页组件里写死了一条名字校验正则

原规则只允许：

- 中文
- 英文
- 数字

并且长度限制在 2 到 20。

它不允许：

- 连字符 `-`
- 空格

所以像你后来写的：

- `Day3修改测试菜品-已更新`

这种名字虽然人看起来很正常，但会被前端表单在浏览器里直接拦掉，导致请求根本发不到后端。

这就是为什么我们后来发现：

- 上传请求到了后端
- 但保存请求没到后端

## 36. 我们最后是怎么修掉这个前端问题的

这次不是改后端，而是直接改了当前正在运行的前端打包文件中的校验规则。

也就是说，我们不是“猜前端大概有问题”，而是：

1. 找到前端打包后的 JS 文件
2. 找到 sourcemap
3. 反查到原始页面组件
4. 定位到菜品名称校验正则
5. 把规则放宽，让它允许 `-`

你最后用：

- `测试菜-1`

成功保存并正常退出页面，这就说明：

- 前端表单校验问题也已经被真正处理掉了

## 37. 今天额外沉淀出的高价值问题

### 问题 1：页面报错时，到底是前端问题还是后端问题？

不要一看到页面红字就本能怀疑后端。

正确做法是先拆链路：

1. 请求到底有没有打到后端
2. 后端有没有对应接口
3. 后端接口是否真的执行成功
4. 如果请求根本没到后端，那就要去看前端校验或前端逻辑

今天“菜品名称输入不符”就是非常典型的前端校验拦截。

### 问题 2：为什么前端图片能预览，但点保存还是失败？

因为“本地预览”和“真正保存到后端”是两回事。

本地预览很多时候只是浏览器临时拿到你选中的文件做一个展示。

但真正保存还需要：

- 上传接口成功
- 图片地址写回表单
- 最终修改接口再把这个地址写入数据库

任何一环断掉，页面都可能出现“看起来有图，但数据库没更新”的情况。

### 问题 3：为什么先用 APIFox 绕过前端是一个好办法？

因为 APIFox 可以帮助我们快速回答一个关键问题：

- 是后端不行，还是前端页面逻辑有问题

今天我们就是靠 APIFox 先证明：

- 后端更新菜品没有问题
- 图片地址写数据库没有问题

然后才有底气回头去收拾前端页面。

### 问题 4：为什么先做本地上传再迁移 OSS 是合理的？

因为学习项目最怕一开始就被云配置卡死。

本地上传能让你先把业务链、图片链、数据库链和页面链全部跑通。

等这些主线稳定后，再迁移到 OSS，难度会小很多。

## 38. Day3 最终复盘结论

到 Day3 收尾时，你已经不是只会“跟着视频敲几个接口”了，而是真正完成了：

- 一次工程化重构：公共字段自动填充
- 一个带多表关系的后台模块：菜品管理
- 一次完整的前后端联调排错：分类下拉、图片上传、图片显示、前端表单校验

如果要用一句话总结今天的价值，那就是：

- Day3 让你第一次真正从“会写单个接口”走向“能打通一个完整页面背后的整条依赖链”

这一步非常重要。
