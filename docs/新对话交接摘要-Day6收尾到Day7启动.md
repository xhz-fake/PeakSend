## 7. Day6 过程中形成的关键工程结论

这些不是普通事实，而是后续新对话必须继承的“硬认识”。

### 7.1 登录链标准表述

用户端登录链的标准理解应固定为：

- 小程序先拿 `code`
- 后端用 `code + appid + secret` 向微信换 `openid`
- 后端用 `openid` 查本地 `user` 表
- 查不到则自动注册
- 后端把本地 `user.id` 放进 JWT
- 后续请求靠 token 识别当前用户

### 7.2 token 里放的是本地 user.id

必须明确：

- token 里保存的不是 `code`
- 也不是让前端随便传一个 `userId`
- 而是后端根据 `openid` 找到的本地 `user.id`

### 7.3 用户身份必须由后端确认

必须坚持：

- 不能相信前端直接传 `userId`
- 当前用户身份必须由后端基于 token 解析
- 再通过 `BaseContext` 在一次请求处理中共享

### 7.4 购物车判重维度

当前购物车判重的正确规则是：

- `user_id + dish_id/setmeal_id + dish_flavor`

不能退化成只按：

- `dishId`

否则规格菜会被错误合并。

## 8. Day6 中踩过的坑和必须保留的教训

### 8.1 不要混拷 dev 和 build 编译产物

这是一个已经被真实踩爆过的大坑。

错误做法：

- 把 `unpackage/dist/dev/mp-weixin` 和 `unpackage/dist/build/用户端小程序` 的文件混着覆盖

会导致：

- 模块编号不一致
- 小程序直接崩溃
- 报 `Cannot read property 'call' of undefined`

如果后续再遇到产物损坏，修复原则是：

- 要么重新完整编译
- 要么整套覆盖，不要零碎混拷

### 8.2 运行中的小程序不一定吃源码改动

已经验证过：

- 改源码 `utils/env.js`
- 不一定等于微信开发者工具当前运行产物立即生效

必须先分清：

- 你改的是源码
- 还是当前正在跑的编译产物

### 8.3 Day6 不能再越界到订单与支付

这是当前阶段最重要的边界约束之一。

明确规则：

- Day6 到此为止已经收口

## 11. 当前已经稳定下来的交互范式

这一部分是交接里最重要的内容之一。新对话如果不遵守，会立刻导致体验变差。

### 11.1 总体角色定位

AI 在这个项目里不是单纯代码生成器，而应同时扮演：

- 项目陪跑老师
- 代码搭子
- 联调助手
- 复盘教练

### 11.2 推进顺序

每个阶段的固定顺序应保持为：

1. 先确认当天目标和范围
2. 再拆业务链、接口、数据库和关键代码
3. 再编码或联调
4. 再验证页面、接口、日志
5. 最后形成文档沉淀

### 11.3 复盘方式的硬要求

用户已经明确偏好并多次纠偏，必须严格遵守：

- 先说今天复盘有哪些环节
- 先做成果盘点
- 再挑 1 到 2 个最值钱的源码点精读
- 精读必须贴小段真实源码
- 必须逐行解释，不要大段概括
- 一次只问 1 个很小的问题
- 让用户先复述
- 再针对性纠偏

必须避免的坏做法：

- 上来就大段总结
- 没贴真实源码就泛泛而谈
- 在用户基础概念没铺平时，连续追问抽象问题
- 一下子问多个问题

### 11.4 基础概念未铺平时的要求

用户已经明确表达过：

- 对 JWT、token、id、openid、code 这类概念，如果没有先扫盲，就很难进入代码精读

因此规则是：

- 一旦发现用户在基础概念上卡住
- 应先补“最小必要概念”
- 再继续源码复盘

### 11.5 语言与节奏

用户主要使用中文交流，喜欢：

- 真实
- 直接
- 不装腔
- 不偷懒
- 不空泛

如果进入复盘或教学模式：

- 优先用中文
- 多用“人话”
- 但必须保留真实代码、真实路径和真实链路
