# Day10-变更细节及详细逻辑链路说明

## 1. Day10 这一阶段到底真正做了什么

如果只看课程标题，Day10 很容易被理解成：

- 来单提醒
- 催单
- 定时任务

但结合这次项目的真实推进过程，更准确的说法应该是：

- 把用户端催单链真正接进后端业务
- 把 WebSocket 实时提醒链从“代码存在”推进到“真实可联调、可收到消息”
- 把管理端订单处理后端补齐，形成“提醒 -> 处理订单”的闭环

这次 Day10 真正完成并验证通过的内容包括：

- 用户端催单入口 `/user/order/reminder/{id}`
- 后端催单业务校验与消息组装
- WebSocket 基础配置注册
- WebSocket 服务端连接维护与广播
- 管理端手工 WebSocket 联调验证
- 管理端自动 WebSocket 连接问题定位与修复
- 管理端收到提醒、播放提示音、点击跳转订单页
- 管理端订单查询、详情、接单、拒单、取消、派送、完成等后端能力补齐

一句话总结：

- Day10 不只是“把 WebSocket 接进项目”，而是真正把“用户催单 -> 后端校验 -> 实时提醒 -> 管理端处理订单”做成了一条完整的跨端业务闭环。

## 3. Day10 的完整主链应该怎么理解

如果把这次 Day10 所有代码、日志和联调结果串成一条线，可以压缩成下面这 4 段：

### 3.1 用户动作入口：催单请求进入后端

- 用户在小程序订单详情页点击“催单”
- 前端请求打到 `/user/order/reminder/{id}`
- Controller 只负责接请求、取订单 id，并把真正业务交给 Service

这里最重要的不是“多了个接口”，而是：

- 用户侧第一次向后端明确发起了一个需要实时通知管理端的业务动作

### 3.2 业务校验：不是所有订单都能催单

- 后端先拿当前登录用户 id
- 再按订单 id 查订单
- 再校验订单是否存在
- 再校验订单是否属于当前用户
- 再校验订单当前状态是否允许催单

只有这些都通过，后端才会继续往下走。

所以 Day10 里非常重要的一点是：

- 实时提醒不是“用户一按按钮就直接广播”
- 而是先经过严格的业务合法性判断

### 3.3 实时通知：把业务动作转换成 WebSocket 消息

- 催单校验通过后，后端会组装一条 JSON 消息
- 消息里至少包含：

  - `type`
  - `orderId`
  - `content`
- 然后把这条消息交给 WebSocket 服务端广播给当前在线的管理端页面

这里最关键的变化是：

- 催单不再只是数据库里的一个静态状态
- 而是被转换成了一条能实时推到管理端的消息

### 3.4 管理端处理：提醒不是终点，而是订单处理入口

- 管理端页面提前建立 WebSocket 长连接
- 后端维护在线连接表
- 一旦用户催单，管理端就能实时收到提醒
- 管理员收到提醒后，不只是“看见一条消息”
- 还可以继续进入订单详情页，并执行接单、拒单、取消、派送、完成等动作

所以 Day10 最终完成的是：

- 通知链
- 处理链

而不是只做了前半条“提醒链”。

## 4. 用户端催单入口到底在做什么

用户端催单入口在：

- `com.sky.controller.user.OrderController#reminder`

这一段代码表面上很短，但它承担了非常明确的入口职责：

- 接收用户催单请求
- 从路径里拿到订单 id
- 记录日志，便于确认请求有没有真正打进后端
- 调用 `orderService.reminder(id)` 进入业务层

这里最值得记住的设计点是：

- Controller 不直接查订单
- 不直接组装消息
- 不直接操作 WebSocket

因为这些都属于业务层职责。

一句话：

- Controller 负责把“催单请求”正式送进后端业务链，而不负责自己实现这条业务链。

## 5. `OrderServiceImpl.reminder()` 到底在做什么

Day10 最值钱的源码点之一，就是：

- `com.sky.service.impl.OrderServiceImpl#reminder`

这段逻辑可以拆成前后两半理解。

### 5.1 前半段：校验这次催单是否合法

它主要做了这几件事：

- 从 `BaseContext` 里拿当前用户 id
- 通过订单 id 查订单
- 校验订单存在
- 校验订单归属
- 校验订单当前状态必须是 `TO_BE_CONFIRMED`

这说明催单不是一个“无条件允许”的动作，而是受业务规则约束的。

更通俗一点说：

- 不是你拿到一个订单 id 就能催
- 不是任何状态的订单都能催
- 后端必须先确认“这次催单在业务上站得住”

### 5.2 后半段：组装消息并交给 WebSocket

通过前半段校验后，后半段才开始做真正的实时通知：

- 创建 `JSONObject`
- 放入消息类型 `type`
- 放入 `orderId`
- 放入展示内容 `content`
- 调用 `webSocketServer.sendToAllClient(...)`

这里要特别记住：

- 业务层负责决定“这条消息该不该发、发什么内容”
- WebSocket 层负责决定“发给谁、怎么发”

这是一种很清晰的职责分工。

一句话：

- `reminder()` 的本质，是把一次合法的催单业务动作，转换成一条可广播的实时通知消息。

## 6. 为什么这里必须用 WebSocket

这个问题在 Day10 里非常值得单独讲。

### 6.1 如果只用普通 HTTP，会怎样

如果不用 WebSocket，管理端想知道有没有新催单，只能不断轮询后端，比如：

- 现在有没有新催单
- 过几秒再问一次
- 再过几秒再问一次

这种方式的问题很明显：

- 请求浪费
- 实时性差
- 页面逻辑更笨重
- 用户体验一般

### 6.2 WebSocket 解决了什么问题

WebSocket 的核心不是“换了一种请求方式”，而是：

- 让前后端先建立一条持续存在的长连接
- 后端一旦有消息，就能主动推给前端

所以在 Day10 里，WebSocket 解决的是：

- 管理端实时接收催单/来单提醒

### 6.3 WebSocket 底层到底是 TCP 还是 UDP

这也是面试里很容易追问的点。

结论是：

- WebSocket 底层建立在 `TCP` 之上，不是 `UDP`

它的实时感主要来自：

- 长连接
- 服务端主动推送

它的可靠性主要来自：

- TCP 的可靠传输
- 连接状态维护
- 应用层对失效连接的清理和日志记录

一句话：

- WebSocket 在 Day10 里不是为了炫技，而是为了让管理端能够实时收到后端主动推送的提醒消息。

## 7. `WebSocketConfiguration` 的作用到底是什么

对应代码在：

- `com.sky.config.WebSocketConfiguration`

这个类只有几行，但它的地位非常靠前。

它不是业务代码，它做的是：

- 把 `@ServerEndpoint` 标记的 WebSocket 端点正式注册进 Spring Boot 运行环境

如果没有它，后面的：

- `@ServerEndpoint("/ws/{sid}")`

很可能就不会按预期生效。

所以这类配置代码的价值不在于“长不长”，而在于：

- 它决定了 WebSocket 这套基础设施能不能真正站起来

一句话：

- `WebSocketConfiguration` 不是在处理订单业务，而是在完成 WebSocket 基础设施注册。

## 8. `WebSocketServer` 到底维护了什么

对应代码在：

- `com.sky.websocket.WebSocketServer`

这也是 Day10 最核心的源码之一。

### 8.1 `SESSION_MAP` 保存的是什么

最关键的一行是：

- `Map<String, Session> SESSION_MAP = new ConcurrentHashMap<>()`

这里保存的不是：

- 管理员账号对象
- 管理员线程
- 管理员服务实例

而是：

- `sid -> Session`

也就是：

- 客户端标识
- 对应的 WebSocket 连接对象

所以当前项目里所谓“在线的管理端客户端”，本质上就是：

- 当前打开着管理端页面，并且已经和后端建立了 WebSocket 长连接的那些前端页面

### 8.2 `onOpen()` 在做什么

当管理端页面成功建立 WebSocket 连接时：

- 后端自动执行 `onOpen()`
- 把当前这条连接登记进 `SESSION_MAP`
- 记录日志，告诉我们谁连上来了、当前在线几个

它的本质是：

- 维护在线连接表

### 8.3 `onClose()` 在做什么

当管理端页面关闭或连接断开时：

- 后端自动执行 `onClose()`
- 把断开的连接从 `SESSION_MAP` 里移除
- 避免死连接长期残留在在线表中

它的本质是：

- 保证在线连接表尽量准确

### 8.4 `onMessage()` 为什么现在不是主角

`onMessage()` 说明：

- WebSocket 是双向通信
- 前端也可以主动通过这条连接给后端发消息

但在当前 Day10 的主链里，最关键的是：

- 后端主动把催单消息推给前端

所以 `onMessage()` 当前更多承担的是：

- 调试入口
- 预留扩展点

而不是核心业务入口。

### 8.5 `sendToAllClient()` 在做什么

这是 Day10 里最关键的方法之一。

它的主要步骤是：

- 遍历 `SESSION_MAP`
- 逐个检查每条连接是否还有效
- 失效连接就顺手清理掉
- 有效连接就调用 `sendText(message)` 推送文本消息
- 某个客户端推送失败时，只记日志，不影响其他客户端继续接收

这说明作者考虑到的不只是“能发出去”，还包括：

- 连接有效性
- 群发过程中的局部失败
- 在线表的自清理

一句话：

- `WebSocketServer` 不是订单业务类，而是负责连接维护和消息广播的通信基础设施类。

## 9. 管理端为什么能实时收到催单提醒

这个问题非常值得单独沉淀，因为很多人会误以为：

- 用户一催单，管理端那边才临时去建立连接

实际上不是。

Day10 当前链路里更准确的说法是：

- 管理端页面一打开，就会先自动建立 WebSocket 连接
- 连接成功后，后端 `onOpen()` 把它记进 `SESSION_MAP`
- 所以后面催单发生时，后端已经知道当前有哪些管理端页面在线
- 再调用 `sendToAllClient()` 时，就能直接把消息推过去

也就是说：

- 管理端之所以能实时收到提醒，前提不是“催单发生”
- 而是“页面已经提前待命”

一句话：

- 管理端页面之所以能实时收到催单提醒，是因为它在页面打开时就已经完成了 WebSocket 连接建立和在线登记。

## 10. 为什么 Day10 不能只做到“提醒会弹”

这是 Day10 最容易被低估的点。

如果 Day10 只做到：

- 用户点催单
- 后端广播
- 管理端弹出提醒

那它顶多只是一个：

- 实时通知演示

但它还算不上一个完整的业务闭环。

真正完整的闭环应该是：

- 用户催单
- 管理端被提醒
- 管理端知道是哪张订单
- 管理端能继续查详情
- 管理端能继续接单、派送、完成

所以管理端订单接口在 Day10 里不是“顺手补的普通 CRUD”，而是：

- 把提醒真正接成订单处理链的关键支点

## 11. 管理端订单处理后端为什么也属于 Day10

对应入口在：

- `com.sky.controller.admin.OrderController`

这部分当前已经补上了：

- 条件查询
- 订单统计
- 订单详情
- 接单
- 拒单
- 取消
- 派送
- 完成

它们的价值不在于“接口数量多”，而在于：

- 管理端收到提醒后，终于有了继续处理订单的后端能力

特别是下面这条状态流转链，非常值得记：

- `TO_BE_CONFIRMED -> CONFIRMED`
- `CONFIRMED -> DELIVERY_IN_PROGRESS`
- `DELIVERY_IN_PROGRESS -> COMPLETED`

这说明管理端处理链不是一堆散接口，而是：

- 一条受状态约束的订单流转链

一句话：

- Day10 的后半段真正补的是“订单状态流转能力”，而不是表面上的几个按钮接口。

## 12. 为什么 `confirm()`、`delivery()`、`complete()` 都要先校验状态

这几个方法的结构非常像：

- 先查订单
- 先确认订单存在
- 再确认当前状态是否允许执行当前动作
- 最后才更新状态

这背后的核心思想不是“代码写法统一”，而是：

- 订单状态流转必须受业务规则约束

比如：

- 只有 `TO_BE_CONFIRMED` 才能接单
- 只有 `CONFIRMED` 才能派送
- 只有 `DELIVERY_IN_PROGRESS` 才能完成

不能出现：

- 待接单直接完成
- 已取消再派送
- 已完成再接单

所以这里虽然没有专门引入状态机框架，但业务本身已经具备很明显的状态机思维。

一句话：

- 管理端订单处理的真正价值，不是改字段，而是在受控前提下推进订单状态流转。

## 13. Day10 里最值得讲的真实踩坑

这次 Day10 最值钱的地方，不只是代码本身，还包括一轮非常真实的联调和排障。

### 13.1 手工 WebSocket 能通，但页面自动连接失败

现象是：

- 浏览器手工 `new WebSocket(...)` 能通
- 后端能收到连接
- 但管理端页面一打开却提示无法接收实时报警信息

这个现象特别重要，因为它说明：

- WebSocket 后端并不是完全坏的
- 问题更可能出在管理端前端自动连接那一段

### 13.2 当前仓库没有完整管理端前端源码

这导致一个现实问题：

- 不能像普通前端项目那样，直接改 `src/...`
- 只能从运行中的打包产物和 sourcemap 里反推逻辑

这个限制后来直接影响了排障方式。

### 13.3 最终定位到自动连接地址写错

通过读取运行中的静态文件和 sourcemap，最后确认：

- 管理端自动建立 WebSocket 连接时，地址拼接有问题
- 它没有正确跟随当前页面 `host`
- 导致自动连接走错地址

所以这次真正的根因不是：

- Java 后端代码没写

而是：

- 运行中的前端 bundle 连接地址写错了

### 13.4 直接改运行中的静态包，让自动连接恢复

因为没有源码工程，最终处理方式是：

- 直接 patch 运行中的 `app.*.js`
- 把 WebSocket 地址改成随 `location.host` 动态拼接

修完以后，管理端表现恢复为：

- 页面不再报错
- 能自动收到催单提醒
- 能播放声音
- 点击提醒能跳订单页

### 13.5 浏览器缓存会制造“明明改了还是旧效果”的错觉

这也是 Day10 非常值得反复沉淀的一点。

真实现象是：

- 磁盘上的 bundle 已经改了
- 但浏览器第一次打开管理端时仍然可能加载旧缓存
- 按一次 `Ctrl + F5` 强制刷新后，页面才恢复正常

这说明联调时一定要警惕：

- 代码问题
- 运行中静态资源问题
- 浏览器缓存问题

它们可能会制造非常像的表象。

一句话：

- Day10 这轮排障最值钱的收获之一，是学会把“后端逻辑问题”和“前端运行包/缓存问题”分开判断。

## 14. Day10 最值得带走的工程认识

这次 Day10 里，最值钱的工程认识至少有 4 个。

### 14.1 实时业务闭环最怕只看单点

只看下面任意一个点都不够：

- 接口 200
- WebSocket 能连
- 控制台没报错
- 页面弹了一次消息

真正有意义的是：

- 从用户动作开始
- 一直看到管理端能继续处理订单

### 14.2 基础设施代码不长，但地位很前

像 `WebSocketConfiguration` 这种类，虽然代码很短，但如果没有它：

- 整条 WebSocket 通道可能就站不起来

所以不能只按代码行数判断价值。

### 14.3 “提醒到了”不等于“业务闭环完成了”

真正完整的业务链应该是：

- 提醒到了
- 管理端知道是哪张单
- 管理端能继续处理

不然它只是一条通知链，不是一条处理链。

### 14.4 前端静态资源和缓存问题，足以误导整个排障方向

这次 Day10 很典型的一点就是：

- Java 后端已经没问题了
- 但前端运行包和缓存仍然能制造“系统还是坏的”假象

所以联调排障不能只盯着后端代码。

## 15. Day10 最适合面试前背诵的一段话

可以这样说：

- Day10 这一块，我不是只接了一个 WebSocket，而是围绕订单域打通了一条实时提醒闭环。用户在小程序里发起催单后，请求会先进入后端订单业务层，后端会先校验当前用户身份、订单归属和订单状态，确认这次催单合法后，再组装成一条 JSON 提醒消息。然后我通过 WebSocket 维护管理端在线连接表，把消息广播给当前在线的管理端页面。管理端收到提醒后，不只是弹一个通知，还能继续查询订单详情并执行接单、派送、完成等处理动作，所以这一块最终形成的是“实时通知 + 订单状态流转”的完整业务闭环，而不是单纯的前端弹窗效果。

## 16. Day10 高频问题与好背回答

### 16.1 高频问题：为什么这里要用 WebSocket，而不是普通 HTTP？

#### 简洁回答

因为这个场景需要服务端主动推消息给管理端，如果只用普通 HTTP，管理端只能不断轮询后端，实时性差、请求浪费也更严重。WebSocket 建立长连接后，后端一旦有催单或来单消息，就可以直接推给在线管理端页面。

#### 好背版本

- 这个场景要服务端主动推消息
- 轮询也能做，但不够实时、也更浪费
- WebSocket 更适合做管理端提醒

### 16.2 高频问题：你项目里的 WebSocket 到底做了什么？

#### 简洁回答

我在项目里用 WebSocket 做的是管理端实时提醒。管理端页面打开时会先建立 WebSocket 连接，后端把这条连接登记进在线连接表。用户催单后，后端先完成业务校验，再组装消息并广播给所有在线管理端页面，管理端收到后会弹提醒并可继续进入订单处理。

#### 好背版本

- 页面先连 WebSocket
- 后端登记在线连接
- 催单后组装消息并广播
- 管理端实时收到提醒并继续处理订单

### 16.3 高频问题：WebSocket 底层是 TCP 还是 UDP？

#### 简洁回答

WebSocket 底层建立在 TCP 之上，不是 UDP。它的实时性主要来自长连接和服务端主动推送，可靠性主要来自 TCP 的可靠传输能力。

#### 好背版本

- WebSocket 用的是 TCP
- 实时感来自长连接和主动推送
- 稳定性主要靠 TCP

### 16.4 高频问题：`SESSION_MAP` 里存的到底是什么？

#### 简洁回答

`SESSION_MAP` 存的不是管理员账号对象，而是 `sid -> Session` 的映射关系，也就是“客户端标识”对应的“WebSocket 连接对象”。后端后面广播消息时，真正依赖的是这些在线连接。

#### 好背版本

- 不是存账号
- 是存 `sid -> Session`
- 本质是在线连接表

### 16.5 高频问题：为什么 `reminder()` 不是一上来就发 WebSocket？

#### 简洁回答

因为实时提醒也必须受业务规则约束。后端必须先确认当前用户是谁、这张订单是否存在、是否属于当前用户、当前状态是否允许催单，只有这些都合法，后面才有资格把它转换成一条提醒消息发出去。

#### 好背版本

- 先判断这次催单合不合法
- 合法了才组装消息
- 不是按钮一按就直接广播

### 16.6 高频问题：为什么 Day10 不能只做到“会弹提醒”？

#### 简洁回答

因为提醒本身不是业务终点，它只是订单处理的入口。如果管理端只能看到提醒，却不能继续查看订单详情、接单、派送、完成，那这条链最多只是通知链，还不是完整业务闭环。

#### 好背版本

- 提醒不是终点
- 提醒后还得能处理订单
- 否则只是通知链，不是闭环
