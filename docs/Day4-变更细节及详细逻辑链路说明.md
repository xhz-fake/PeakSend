Day4 当前主线是：

这一天我们不是只补了一个接口，而是把套餐模块最核心的一整条后台链路都真正做通了，包括：

- 新增套餐
- 套餐分页查询
- 套餐起售/停售
- 套餐删除
- 套餐详情查询
- 套餐修改

而且这次不是“代码写了但没测”，而是每一条都通过了：

- APIFox 接口联调

- 前端页面回显验证

## 2. 为什么 Day4 要从套餐管理开始

因为套餐模块本质上是 Day3 菜品模块的一次升级版练习。

它和菜品模块很像，但业务关系更复杂：

- 套餐自己有主表 `setmeal`
- 套餐和菜品之间还有关系表 `setmeal_dish`

所以它特别适合继续练这几个能力：

- 一对多/主表-关系表的联动保存
- 删除前业务校验
- 状态启停的业务规则
- 详情查询时的多表组装
- 修改时“删旧关系、插新关系”的事务更新

## 3. Day4 一开始遇到的第一个真实问题

最开始我们先测了套餐分页：

- `GET /admin/setmeal/page?page=1&pageSize=10`

结果接口返回成功，但列表是空的：

- `code = 1`
- `records = []`

这里非常重要的一点是：

- 它不是报错
- 也不是代码没写好
- 而是数据库里的 `setmeal` 表本来就没有数据

所以这次我们没有误判成“分页功能坏了”，而是先回到数据层确认：

- 当前套餐表为空

这一步其实很值得记住，因为它体现的是一种正确的排查顺序：

1. 先分清是报错还是正常空结果
2. 再判断是代码问题还是数据问题
3. 不要一看到空列表就下意识改 SQL

## 4. 套餐分页查询是怎么做起来的

套餐分页的整体结构和 Day3 菜品分页很像。

### Controller

入口在：

- `SetmealController.page()`

它负责：

- 接收分页参数
- 调用 `setmealService.pageQuery(...)`
- 把结果封装成 `Result<PageResult>`

### Service

分页核心在：

- `SetmealServiceImpl.pageQuery()`

这里延续了我们前面已经熟悉的分页套路：

- 先调用 `PageHelper.startPage(page, pageSize)`
- 再调用 Mapper 查询
- 最后把总数和记录列表封成 `PageResult`

### Mapper / SQL

分页 SQL 在：

- `SetmealMapper.xml`

这里用了：

- `left join category`

目的是把分类表里的名称也一起查出来，返回给前端展示：

- `categoryName`

同时这里也用了动态 SQL，根据有没有传条件，决定要不要拼接：

- 名称筛选
- 分类筛选
- 状态筛选

## 5. 新增套餐为什么是 Day4 第一个真正闭环

因为分页能不能查到数据，最终还是取决于库里有没有数据。

所以 Day4 的第一个最小闭环其实是：

- 先新增一条套餐
- 再回头验证分页

这条链路的实现逻辑是：

### 第一步：保存套餐主表

先把 `SetmealDTO` 拷贝成 `Setmeal`，然后插入：

- `setmeal`

这里如果前端没传状态，我们让它默认是：

- `0`，也就是停售

### 第二步：拿到套餐主键

因为 `setmeal_dish` 关系表里需要：

- `setmeal_id`

所以必须先插主表，拿到套餐 id。

### 第三步：保存套餐和菜品关系

从 `SetmealDTO` 里拿到：

- `setmealDishes`

然后给每一条关系数据补上：

- `setmealId`

最后批量插入：

- `setmeal_dish`

### 第四步：事务保证一致性

这个方法加了：

- `@Transactional`

原因很简单：

- 新增套餐不是只插一张表
- 而是主表 + 关系表联动

如果主表插成功了，关系表失败了，就会留下半截数据。

## 6. 套餐起售/停售为什么不是只改一个 status

表面看它只是改：

- `setmeal.status`

但真正业务上没那么简单。

我们这次专门先验证了一个失败场景：

- 套餐里如果包含停售菜品，就不能启售套餐

### 这条业务链是怎么走的

当请求：

- `POST /admin/setmeal/status/1?id=32`

进来时，后端不是直接 update，而是先做校验：

1. 先查这个套餐关联了哪些菜品
2. 再查这些菜品当前的状态
3. 只要有一道菜是停售
4. 就抛出业务异常，拒绝启售

也就是：

- `SetmealEnableFailedException`

返回信息是：

- `套餐内包含未启售菜品，无法启售`

### 这次为什么这个失败特别有价值

因为它不是接口报错，而是：

- 业务规则拦截成功

这说明我们已经开始从“会写 CRUD”进入到“会写业务校验”的阶段了。

### 后面又怎么成功启售的

我们先把关联菜品：

- `dishId = 71`

改成启售，再重新请求套餐启售，结果成功。

这就把整条链真正跑通了：

```text
先启售菜品
-> 再启售套餐
-> 套餐状态更新成功
```

## 7. Day4 中一个很真实的联调坑

这一段很值得单独记下来。

当时我们发现：

- 菜品状态怎么改都不对
- 前端和数据库看起来一直没变化

后面仔细排查才发现，问题根因根本不是后端代码，而是：

- APIFox 里复用了错误的请求模板

也就是本来应该调：

- `/admin/dish/status/{status}`

结果一直在错误地复用：

- `/admin/setmeal/status/{status}`

这次问题的意义不在于“路径写错了”这么简单，而在于你真正碰到了联调时很常见的一类坑：

- 你以为你在测 A 接口
- 其实请求打到了 B 接口

所以以后联调时，必须同时确认这四件事：

1. 请求方法是不是对的
2. 完整 URL 是不是对的
3. 路径参数是不是对的
4. 查询参数是不是对的

## 8. 套餐删除为什么要分两步测

我们这次删除不是上来就测成功，而是先故意测失败，再测成功。

### 第一步：先测“起售中的套餐不能删除”

当套餐处于起售状态时，请求：

- `DELETE /admin/setmeal?ids=32`

返回：

- `起售中的套餐不能删除`

这一步的意义是验证：

- 删除前的业务校验已经生效

### 第二步：先停售，再删除

接着我们先把套餐停售，再发删除请求，删除成功。

这样就把删除链真正跑成了：

```text
删除套餐
-> 先校验是否起售
-> 如果起售，拒绝删除
-> 如果停售，允许继续删除
-> 删除主表
-> 删除关系表
```

### 为什么删除时不能只删主表

因为套餐和菜品之间还有关系表：

- `setmeal_dish`

如果只删：

- `setmeal`

不删关系表，就会留下没有归属的关联数据，也就是脏数据/孤儿数据。

所以删除时必须联动处理：

- 删除套餐主表
- 删除套餐和菜品关系表

## 9. 套餐详情查询为什么不是单表查询

这条链是后面“套餐修改”的基础。

请求是：

- `GET /admin/setmeal/{id}`

比如：

- `GET /admin/setmeal/33`

### 它到底做了什么

不是只查：

- `setmeal`

而是分两段查：

1. 先查套餐主表信息
2. 再查这个套餐关联的菜品列表

最后把两部分组装成一个完整的：

- `SetmealVO`

里面既有：

- 套餐名称
- 价格
- 描述
- 分类名

也有：

- `setmealDishes`

这一步其实特别重要，因为它体现了一个很典型的 VO 思路：

- VO 不是照着数据库主表一比一返回
- 而是把前端真正要显示的数据组织好后再返回

## 10. 套餐修改为什么和菜品修改很像

这次套餐修改本质上复用了 Day3 菜品修改的思路。

### 修改链路

请求：

- `PUT /admin/setmeal`

时，后端做的是三步：

1. 更新套餐主表 `setmeal`
2. 删除这个套餐原来的全部关系数据 `setmeal_dish`
3. 插入前端这次传来的新关系数据

### 为什么不逐条比对旧关系和新关系

因为前端传来的菜品关系，可能同时包含：

- 某些菜删掉了
- 某些菜新增了
- 某些菜份数变了
- 顺序也可能变了

如果后端逐条算差异，逻辑会明显复杂很多。

在当前这个场景下，关系数据量不大，所以采用：

- 先删旧关系
- 再插新关系

是更简单、更稳、更容易维护的方式。

### 这次修改成功说明了什么

我们最终验证到：

- 套餐主表名称从旧值变成了 `Day4修改后套餐`
- 价格也更新成功
- 描述更新成功
- 关系表里的 `copies` 从 `1` 变成了 `2`
- 前端界面名称和状态也同步正确

这就说明：

- 主表更新成功
- 关系表重建成功
- 前端回显链也正常

## 12. Day4 当前最值得记住的几条业务规则

如果现在只抓套餐管理最核心的规则，先记这几条：

- 套餐新增不是单表保存，而是主表 + 关系表一起保存
- 套餐启售前，必须先校验关联菜品是否都已启售
- 起售中的套餐不能删除
- 套餐删除时必须同时删除关系表数据
- 套餐详情查询要返回主表信息和关联菜品列表
- 套餐修改采用“更新主表 + 删旧关系 + 插新关系”的事务方案
