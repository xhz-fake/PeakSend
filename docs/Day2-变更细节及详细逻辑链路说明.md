## 2. 今天第一步到底做了什么

我们刚才做的，不是什么很玄的东西，本质上就是：

- 让后端能够返回“员工列表”
- 并且支持“第几页、每页显示几条、按名字搜索”

你可以把它理解成后台管理页面里的“员工列表页”。

比如页面上会有这些需求：

- 我想看所有员工
- 我只想看第一页
- 一页只显示 10 条
- 我想搜索名字里带“张”的员工

为了实现这个页面，后端就必须提供一个接口。

## 3. 这个接口是干什么的

接口地址：

`GET /admin/employee/page`

它的作用非常简单：

- 从数据库里查员工
- 按页返回
- 可以按姓名做模糊搜索

你可以把它理解成：

- 数据库里可能有很多员工
- 后端不能一次性全扔给前端
- 所以要“分批次”返回

这就是“分页查询”。

## 4. 分页查询，用大白话怎么理解

假设数据库里有 100 个员工。

如果一次性全返回：

- 页面很乱
- 网络浪费
- 用户也看不过来

所以通常会这样做：

- 第 1 页显示 10 个
- 第 2 页显示 10 个
- 第 3 页显示 10 个

这就叫分页。

这里有两个最重要的参数：

- `page`：第几页
- `pageSize`：一页显示几条

比如：

- `page=1&pageSize=10`

意思就是：

- 我要第 1 页
- 每页 10 条数据

## 5. 我刚才具体改了哪些地方

我这次一共改了 5 个位置：

- `EmployeeController`
- `EmployeeService`
- `EmployeeServiceImpl`
- `EmployeeMapper`
- `EmployeeMapper.xml`

你现在不用一下子记住每个类的代码，只先记它们的职责：

- `Controller`：接收前端请求
- `Service`：写业务逻辑
- `Mapper`：访问数据库
- `Mapper.xml`：写 SQL 查询语句

## 6. 这条功能链路怎么走

你先用最简单的方式理解：

### 第一步：前端或 APIFox 发请求

比如发：

`/admin/employee/page?page=1&pageSize=10`

意思是：

- 我要员工列表
- 第 1 页
- 每页 10 条

### 第二步：Controller 接住请求

`EmployeeController` 负责接请求。

它做的事情很简单：

- 接收参数
- 调用 Service
- 把结果返回给前端

### 第三步：Service 处理业务

`EmployeeServiceImpl` 负责真正的分页逻辑。

它做的事情是：

- 告诉程序“我要分页了”
- 再去调用数据库查询
- 最后把查到的结果整理后返回

### 第四步：Mapper 去查数据库

`EmployeeMapper` 和 `EmployeeMapper.xml` 负责真正执行 SQL。

它会去 `employee` 表里查数据。

如果你传了名字，比如：

- `name=管理员`

那它就会查：

- 名字里包含“管理员”的员工

如果你没传名字，就查全部员工。

### 第五步：把结果返回给前端

最后后端会返回两类信息：

- 一共有多少条数据
- 当前这一页的数据有哪些

这就是为什么返回结果里会有：

- `total`
- `records`

## 7. 你现在不用理解太深，但至少先记住这 4 句话

- 列表页通常都需要分页接口
- 分页最核心的两个参数是 `page` 和 `pageSize`
- Controller 接请求，Service 处理业务，Mapper 查数据库
- 返回给前端时，通常不只给“数据列表”，还要给“总条数”

## 11. Day2 当前新增的第二个功能

在员工分页查询之后，我们又补了第二个功能：

- 启用 / 禁用员工账号

这个功能本质上很简单，你可以把它理解成：

- 让某个员工“可以登录”
- 或者让某个员工“暂时不能登录”

项目里靠的是数据库中的 `status` 字段来控制：

- `1`：启用
- `0`：禁用

## 12. 这个功能是怎么工作的

接口地址：

`POST /admin/employee/status/{status}?id=员工id`

比如：

- 启用 id 为 2 的员工：
  - `/admin/employee/status/1?id=2`
- 禁用 id 为 2 的员工：
  - `/admin/employee/status/0?id=2`

它的执行过程很直接：

1. 前端或 APIFox 把员工 id 和目标状态发给后端
2. Controller 接住这两个参数
3. Service 组装出一个员工对象，只给它塞入：
   - id
   - status
   - updateTime
   - updateUser
4. Mapper 根据 id 去更新数据库中这条员工记录
5. 更新完成后返回成功结果

## 13. 你现在可以怎么理解“启用 / 禁用”

不要把它想复杂。

它本质上不是“删除员工”，也不是“修改很多字段”，而只是：

- 把数据库里这个员工的 `status` 从 1 改成 0
- 或者从 0 改成 1

所以这类功能的本质就是：

- 找到一条记录
- 改一个状态值

这是后台管理系统里非常常见的功能形式。

## 14. Day2 当前新增的第三个功能

在“员工分页查询”和“启用 / 禁用员工账号”之后，我们又补了第三个功能：

- 根据 id 查询员工详情

这个功能通常用于什么场景？

- 当你在前端页面点击“编辑员工”按钮时
- 页面要先把这个员工原来的信息查出来
- 然后再回显到表单中

所以这个接口本质上就是：

- 通过员工 id
- 查出这一个人的详细信息

## 15. 这个功能是怎么工作的

接口地址：

`GET /admin/employee/{id}`

比如：

- 查询 id 为 2 的员工：
  - `/admin/employee/2`

执行过程依旧很简单：

1. 前端或 APIFox 把员工 id 发给后端
2. Controller 接住这个 id
3. Service 去调用 Mapper 查询数据库
4. Mapper 按 id 查 `employee` 表
5. 查到后返回这条员工数据
6. 为了安全起见，后端把密码字段处理成 `****`
7. 最后返回给前端

## 16. 你现在可以怎么理解“根据 id 查询详情”

你可以把它理解成：

- 分页查询：查“很多人”
- 根据 id 查询：查“某一个人”

这两个接口配合起来，就能支持后台页面的“列表”和“编辑弹窗”。

## 17. Day2 当前新增的第四个功能

在“分页查询”、“启用禁用”、“根据 id 查详情”之后，我们又补了第四个功能：

- 编辑员工信息

这个功能你可以理解成：

- 先通过 id 查出这个员工原来的信息
- 用户在页面上改完内容
- 再提交给后端
- 后端把数据库中这条员工记录更新掉

## 18. 这个功能是怎么工作的

接口地址：

`PUT /admin/employee`

请求体是一个 JSON，对应的是员工的新信息。

比如你要把 id 为 2 的员工名字改一下，就会发类似这样的数据：

```json
{
  "id": 2,
  "username": "gege",
  "name": "鸽哥2号",
  "phone": "13345454545",
  "sex": "1",
  "idNumber": "666666666666666666"
}
```

执行过程如下：

1. 前端或 APIFox 把员工的新信息发给后端
2. Controller 用 `@RequestBody` 接住这份 JSON
3. Service 把 DTO 拷贝成 Employee 实体
4. Service 补上更新时间和更新人
5. Mapper 根据 id 去更新数据库中的这条记录
6. 更新完成后返回成功结果

## 19. 你现在可以怎么理解“修改员工信息”

你可以把这一步理解成：

- “根据 id 查询详情”是为了先把旧数据拿出来
- “编辑员工信息”是把改完后的新数据再提交回去

所以这两个接口是一前一后的关系：

- 先查
- 再改

这就是后台“编辑功能”的标准套路。

## 20. Day2 已经从员工管理切到分类管理

员工管理这一段完成后，我们开始进入分类管理。

分类管理你可以先理解成：

- 给菜品分组
- 给套餐分组

比如：

- 酒水饮料
- 传统主食
- 人气套餐

这些都属于“分类”。

所以分类虽然简单，但它是后面菜品管理和套餐管理的基础。

## 21. Day2 当前新增的第五个功能

分类管理我们先从最简单的一步开始：

- 新增分类

这个功能和“新增员工”很像，本质上都是：

- 前端填表单
- 后端接收数据
- 保存进数据库

## 22. 新增分类是怎么工作的

接口地址：

`POST /admin/category`

请求体是一个 JSON，里面最关键的是：

- `name`：分类名称
- `type`：分类类型
- `sort`：排序

比如：

```json
{
  "type": 1,
  "name": "招牌小炒",
  "sort": 15
}
```

这里的 `type` 含义是：

- `1`：菜品分类
- `2`：套餐分类

## 23. 这条链路怎么理解

你可以先把它理解成下面这 5 步：

1. 前端或 APIFox 发来新增分类请求
2. Controller 接住这份分类数据
3. Service 把 DTO 转成 Category 实体
4. Service 自动补上默认启用状态、创建时间、更新时间、创建人、修改人
5. Mapper 把这条分类数据插入数据库

## 24. 你可以先记住的重点

- 分类和员工一样，也是一张表对应一个管理模块
- “新增分类”本质上就是向 `category` 表插入一条记录
- 前端并不会把所有数据库字段都传给后端，很多字段需要后端自己补

## 25. Day2 当前新增的第六个功能

在“新增分类”之后，我们继续补了：

- 分类分页查询

这个功能和员工分页查询几乎是同一套套路，只是查的表从 `employee` 变成了 `category`。

接口地址：

`GET /admin/category/page`

常用参数：

- `page`：第几页
- `pageSize`：每页几条
- `name`：按分类名搜索
- `type`：按分类类型筛选

你已经通过 APIFox 验证过：

- 能查到刚新增的分类
- 返回结构里有 `total`
- 返回结构里有 `records`

## 26. Day2 当前新增的第七个功能

在分类分页查询之后，我们补了：

- 启用 / 禁用分类

这个功能和员工启用禁用是同一个模型。

接口地址：

`POST /admin/category/status/{status}?id=分类id`

比如：

- 禁用 id 为 23 的分类：
  - `/admin/category/status/0?id=23`
- 启用 id 为 23 的分类：
  - `/admin/category/status/1?id=23`

本质上就是：

- 找到这条分类
- 把它的 `status` 改成 `0` 或 `1`

## 27. Day2 当前新增的第八个功能

在启用禁用分类之后，我们补了：

- 修改分类

接口地址：

`PUT /admin/category`

这一步和修改员工信息的套路也是完全一样的：

1. 前端把修改后的分类数据发给后端
2. Controller 接住 JSON
3. Service 把 DTO 转成 Category 实体
4. Service 补上更新时间和修改人
5. Mapper 根据 id 更新数据库

你已经验证过：

- 分类名称已经成功修改
- 排序也已经成功修改

## 28. Day2 当前新增的第九个功能

分类管理最后一步，我们补了：

接口地址：

`DELETE /admin/category?id=分类id`

你已经验证过：

- 删除请求返回成功
- 再查分页时，这条分类已经不存在

所以到这里，分类管理的基础 CRUD 已经全部跑通。

## 30. Day2 真正训练到的核心后端套路

今天最重要的不是“做了几个接口”，而是你已经重复练熟了一套非常关键的后台模块开发模式：

1. 先明确一个页面或一个业务动作到底需要什么接口
2. 再设计请求方式、路径和参数
3. Controller 接收请求
4. Service 组织业务逻辑
5. Mapper / XML 执行数据库操作
6. 用 APIFox 调试接口
7. 再通过前端页面或分页接口确认数据库变化

这就是以后做绝大多数中后台 CRUD 模块时的通用套路。

## 31. Day2 你现在已经该能讲清楚的内容
