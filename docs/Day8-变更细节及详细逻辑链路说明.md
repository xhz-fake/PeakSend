## 3. Day8 的完整主链应该怎么理解

如果把这次 Day8 所有代码和联调结果串成一条线，可以压缩成下面这 4 段：

### 3.1 地址来源：AddressBook

- 下单页先查当前用户默认地址
- 默认地址来自地址簿模块，而不是订单模块自己生成
- 下单时前端提交的 `addressBookId`，本质上就是从地址簿里选出来的地址标识

### 3.2 订单生成：Order

- 后端根据当前登录用户、购物车和地址信息生成订单
- 订单主表保存固定的一份订单整体信息
- 订单明细表保存这张订单里买了什么
- 下单成功后清空购物车

### 3.3 支付调起：Payment

- 前端把订单号交给后端 `payment()`
- 后端先校验订单是否允许支付
- 然后返回支付参数
- 这一步只代表“开始支付”，不等于“已经支付成功”

### 3.4 支付成功：paySuccess

- 真实支付里，支付平台回调后端
- 当前开发环境里，用 `mockPaySuccess()` 模拟“支付成功确认”
- 最终都统一走 `paySuccess()` 更新订单状态

所以 Day8 的主线不是“一个接口解决所有事”，而是：

- 地址前置
- 下单生成
- 支付调起
- 支付成功确认
- 订单状态流转

## 4. AddressBook 模块在 Day8 里到底值不值得讲

值得讲，但它在 Day8 里更像：

- 订单主链的上游依赖

它不是今天最有区分度的主角，但它决定了订单主链能不能顺利往下走。

### 4.1 它解决了什么问题

- 当前用户有哪些地址
- 默认地址是哪一条
- 用户新增地址时默认地址怎么确定
- 切换默认地址时怎么保证只有一条默认记录

### 4.2 为什么默认地址查询必须带当前用户

默认地址不是全局概念，而是“某个用户自己的默认地址”。

所以查询默认地址时，必须同时满足：

- `userId = 当前用户`
- `isDefault = 1`

不能只查 `isDefault = 1`，否则理论上有可能拿到别人的默认地址。

### 4.3 为什么设置默认地址要先清旧默认

一个用户在任意时刻只能有一条默认地址。

所以在切换默认地址时，必须：

- 先把当前用户所有地址的默认标记清掉
- 再把目标地址设成默认

而且这两步必须放进事务里，不然就可能出现：

- 旧默认被清掉了
- 新默认还没设置成功
- 最后用户一条默认地址都没有

### 4.4 AddressBook 和订单主链的关系

地址簿并不是和订单平行的无关模块，而是订单主链的前置输入。

可以这样理解：

- AddressBook 决定地址从哪里来
- Order 决定地址怎么参与生成正式订单

## 5. 提交订单主链到底在做什么

提交订单这件事的本质，不是“插一条订单记录”，而是：

- 把购物车里的临时数据转成正式订单数据

### 5.1 为什么一上来先拿当前用户

下单用户身份不应该由前端自己传 `userId` 决定，而应该由后端根据登录态拿当前用户。

这说明：

- 订单归属以后端为准
- 不能信前端自己报身份

### 5.2 为什么先查购物车

因为订单不是凭空生成的，订单里的商品最初就来自购物车。

如果购物车为空还允许下单，就会出现：

- 订单主表有数据
- 订单明细为空
- 生成一张没有任何商品的空订单

### 5.3 为什么再查地址

前端传来的只是 `addressBookId`，后端不能只看这个 id 存在，还要进一步校验：

- 地址是否存在
- 地址是否属于当前登录用户

这一步本质上既是在做业务校验，也是在做越权防护。

### 5.4 为什么订单主信息由后端组装

前端传来的 `OrdersSubmitDTO` 不是完整订单，它只包含用户可填写的那部分参数，比如：

- 地址 id
- 支付方式
- 备注
- 预计送达时间

但真正完整的订单对象，还必须由后端补齐：

- 当前用户 id
- 订单号
- 状态
- 支付状态
- 下单时间
- 收货信息快照

所以：

- 前端传的是“下单参数”
- 后端组装的是“完整订单”

### 5.5 为什么订单要拆成 `orders` 和 `order_detail`

这是 Day8 最容易被忽略、但最值得讲透的建模点。

订单主信息，比如：

- 订单号
- 用户
- 地址
- 时间
- 总金额
- 状态

这些是一张订单固定只有一份的数据。

但一张订单里买了什么商品、每样买几份、什么口味，这部分是：

- 数量不固定
- 一张订单可能有 1 条，也可能有很多条

所以天然应该拆成：

- `orders`：固定的一份订单整体信息
- `order_detail`：不固定的多份商品明细

一句话：

- `orders` 解决“这是一张什么订单”
- `order_detail` 解决“这张订单里到底买了什么”

### 5.6 为什么订单里要存地址快照，而不是只存 `addressBookId`

因为地址簿是会变化的。

如果订单里只保存一个 `addressBookId`，那用户后面修改地址簿时，老订单的地址信息也可能跟着变。

这显然不合理。

所以订单里必须固化下单当时的：

- 收货地址
- 手机号
- 收货人

这就是订单快照思想。

### 5.7 为什么下单成功后要清空购物车

购物车是“待下单的临时区”，订单是“已经正式生成的结果区”。

一旦购物车里的数据已经成功转成订单，就应该清空。否则会出现：

- 用户回到购物车，旧商品还在
- 再点一次，可能重复下单
- 业务状态混乱

所以：

- 购物车是临时态
- 订单是正式态

## 6. 为什么购物车当前更适合放 MySQL，而不是 Redis

这个问题很容易在面试里被追问。

### 6.1 商品列表为什么适合 Redis

商品列表这类数据通常具有这些特点：

- 高频读
- 重复读
- 丢了还能从数据库重建
- 读多写少

所以很适合放 Redis 做缓存。

### 6.2 购物车为什么当前更适合 MySQL

购物车属于：

- 用户私有数据
- 会频繁增删改
- 后面还要参与正式下单
- 需要更稳定的持久化存储

如果当前项目把购物车只放 Redis，会带来：

- 数据稳定性风险
- 数据丢失风险
- Redis 和 MySQL 同步复杂度上升

而当前项目的并发量和复杂度，还没高到必须用 Redis 取代 MySQL 存购物车。

所以更合理的取舍是：

- 商品列表这类高频读结果放 Redis
- 购物车这类强业务数据先稳稳存 MySQL

## 7. 支付链为什么要拆成多段

支付这一块最核心的工程理解是：

- 调起支付不等于支付成功

### 7.1 为什么 `payment()` 不等于支付成功

用户点击支付后，中间还可能发生：

- 用户取消
- 支付失败
- 网络断开
- 重复点击

所以在真实系统里，支付至少要拆成两段：

- 调起支付
- 确认支付成功

### 7.2 `payment()` 做了什么

`payment()` 的职责是：

- 校验订单能不能支付
- 记录支付方式
- 返回支付参数

它的职责不是直接把订单改成已支付。

### 7.3 为什么当前 mock 模式也不直接改状态

即使当前是 mock 支付，我们也希望保留真实支付的结构。

所以当前做法不是：

- 一点支付按钮直接改状态

而是：

- `payment()` 先返回 mock 支付参数
- 前端确认后，再走 `mockPaySuccess()`
- 最终统一进入 `paySuccess()`

这说明我们 mock 的只是“外部支付成功通知”这一跳，而不是把整个支付架构做假。

## 8. 真实微信支付的主逻辑到底是什么

这部分在 Day8 必须知道主干，但不用展开到微信官方文档级别。

真实微信支付链可以快速概括成：

1. 用户点击支付
2. 前端调用后端 `payment()`
3. 后端根据订单号和用户 `openid` 向微信下单
4. 微信返回前端拉起支付所需参数
5. 前端调用 `uni.requestPayment(...)`
6. 用户在微信支付面板里确认
7. 微信服务器异步通知后端支付结果
8. 后端根据 `out_trade_no` 执行 `paySuccess()`
9. 订单从待付款流转到待接单

这里最值得记住的是三个词：

- `openid`
- `outTradeNo/orderNumber`
- 异步回调

### 8.1 什么叫异步

异步可以粗暴理解成：

- 我先把事情发出去，不站在原地等最终结果，结果到了再处理

### 8.2 什么叫回调接口

回调接口可以理解成：

- 我先留给对方一个通知入口，等对方处理完，再主动回来告诉我结果

在微信支付里：

- 对方是微信服务器
- 回调接口就是我们留给微信的支付结果通知入口

### 8.3 为什么支付成功不能只信前端

因为前端并不是最终可信方。前端可能：

- 被篡改
- 断网
- 关闭页面
- 提前显示成功页

所以真实支付里，更可靠的是：

- 以后端收到支付平台回调为准

## 9. 为什么 `mockPaySuccess()` 要复用 `paySuccess()`

这也是一个很值钱的工程点。

如果 `mockPaySuccess()` 自己再写一套状态更新逻辑，就会出现：

- 真实支付成功一套逻辑
- mock 支付成功另一套逻辑
- 后面修改时很容易两边分叉

所以更合理的做法是：

- mock 只是模拟入口
- 支付成功后的真正状态流转统一收口到 `paySuccess()`

一句话：

- mock 可以模拟入口，但不能复制一套独立的支付成功业务逻辑

## 10. 为什么支付成功处理一定要考虑幂等

幂等是 Day8 非常值得沉淀的高频考点。

### 10.1 什么叫幂等

幂等可以简单理解成：

- 同一个操作执行一次和执行多次，最终结果都应该一致，不应该重复产生副作用

### 10.2 为什么支付场景特别需要幂等

支付链里很容易出现重复触发：

- 前端重复点击
- 网络重试
- 第三方支付重复回调
- 后端补偿任务重放

如果没有幂等保护，后面一旦接上库存、消息、积分、通知等逻辑，就可能出现：

- 重复扣库存
- 重复记账
- 重复发券

### 10.3 我们当前代码里哪里体现了幂等

在支付成功逻辑里，如果当前订单已经是：

- 已支付
- 待接单

就直接返回，不重复执行后续更新。

这就是支付成功处理里的基础幂等保护。

## 11. 为什么支付链更适合用 `orderNumber/outTradeNo`

支付不只是系统内部自己处理，还要和第三方支付平台对接。

### 11.1 `orderId` 是什么

- 数据库内部主键
- 更适合系统内部表关联

### 11.2 `orderNumber/outTradeNo` 是什么

- 对外业务单号
- 更适合传给支付平台
- 更适合回调后定位订单

第三方支付平台并不知道你数据库里的 `orderId = 6` 是什么意思，它只认你传过去的商户订单号。

所以：

- 系统内关联常用 `orderId`
- 支付链、回调链更适合用 `orderNumber/outTradeNo`

## 12. Day8 最值得讲的踩坑与解决过程

这次 Day8 不是单纯“写完代码就过”，而是经历了一轮非常真实的联调和排错。

最值得沉淀的问题包括：

- Redis 没启动，导致后端依赖服务不可用
- `token` 过期，导致用户端接口 `401`
- 后端没重启，导致新接口实际是 `404`
- 时间字段格式与前端消费方式不兼容
- 前端状态映射错误，导致已取消显示成已完成
- `deliveryFee` 缺失，导致页面显示 `undefined`
- 改了 uni-app 源码但没重新编译，导致修复看起来没生效
- 旧 `/deep/` 语法导致 `HBuilderX` 编译失败
- 前端依赖缺失的 `/user/order/getEstimatedDeliveryTime`
- 微信开发者工具 `code:10`，最终定位到 AppID 混用和 secret 失效

这些问题说明：

- 联调失败不一定先怪代码逻辑
- 要先区分环境问题、契约问题、运行时问题、平台配置问题和工程取舍问题
