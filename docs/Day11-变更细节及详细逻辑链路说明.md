## 3. Day11 的完整主链应该怎么理解

如果把这次 Day11 所有代码、接口和页面表现串成一条线，可以压缩成下面这 4 段：

### 3.1 入口层：`ReportController` 暴露 4 个统计接口

- `ReportController` 统一挂在 `/admin/report`
- 4 个接口都接收 `begin` 和 `end`
- Controller 只负责接参数、打印日志、调用 `reportService`

这里最重要的不是“接口数量多”，而是：

- 报表层的外部契约已经统一下来
- 对前端来说，Day11 形成了一组完整、稳定的统计入口

### 3.2 业务层：`ReportServiceImpl` 负责按报表口径组装数据

- 这里不是简单把 SQL 查出来就返回
- 真正的工作是：
  - 拆时间区间
  - 逐天统计
  - 计算派生指标
  - 拼装图表数据结构

所以 Day11 最值钱的点不在 Controller，而在 Service。

### 3.3 持久层：`OrdersMapper` 和 `UserMapper` 提供底层聚合能力

- `countByMap()` 负责按动态条件统计数量
- `sumByMap()` 负责按动态条件统计营业额
- `getSalesTop10()` 负责联表聚合 Top10 销量

Mapper 层提供的是“原材料”，而不是最终图表结果。

### 3.4 展示层：前端图表页真正把数据渲染出来

- 营业额、用户、订单趋势图能够正常显示
- Top10 柱状图能够正常显示
- 这说明 Day11 最终不是“接口 200”，而是“页面看见图”

所以 Day11 最终完成的是：

- 聚合查询链
- 图表数据组装链
- 页面展示链

而不只是前半条“查库链”。

## 5. 为什么 Day11 的难点不在 Controller

`ReportController` 代码其实非常轻：

- 接 `begin/end`
- 调用 Service
- 返回 `Result.success(...)`

它不负责：

- 一天一天拆时间区间
- 计算完成率
- 区分新增用户和累计用户
- 组装 `nameList/numberList`

所以 Day11 的难点根本不在“写出 4 个接口方法”，而在于：

- 怎么按业务口径把基础查询结果加工成前端图表真正要吃的数据结构

## 6. 为什么 Day11 的难点也不只是 SQL

Mapper 层当然重要，但它只解决“查什么”的问题。

例如：

- `sumByMap()` 负责 `sum(amount)`
- `countByMap()` 负责 `count(id)`
- `getSalesTop10()` 负责 `group by + sum + order by + limit 10`

但它们都不负责：

- 逐天循环
- 派生指标计算
- 多条统计结果拼装成一个 VO
- 前端图表字段格式转换

这说明 Day11 的真正难点是：

- SQL 负责拿基础统计结果
- Service 负责把这些结果变成图表接口

## 7. 前三个统计接口为什么骨架都很像

下面这 3 个接口：

- 营业额统计
- 用户统计
- 订单统计

表面上统计对象不同，但它们有同一套骨架：

- 拿到 `begin` 和 `end`
- 用 `LocalDate current = begin` 从开始日期往后推
- 用 `while (!current.isAfter(end))` 一天一天循环
- 把一天转换成完整时间区间
- 调用 Mapper 统计当天结果
- 把当天结果塞进列表
- 最后把列表拼成逗号分隔字符串返回前端

所以前三个接口最值钱的认识是：

- 它们不是 3 套完全不同的实现
- 而是同一套“按天拆区间 -> 每天统计 -> 拼图表”的模板

## 8. 为什么必须把“一天”转换成完整时间区间

这一点在 Day11 非常关键。

用户输入的 `begin/end` 是日期，比如：

- `2026-06-02`

但数据库里的 `orders.order_time` 和 `user.create_time` 存的是带时分秒的 `LocalDateTime`，例如：

- `2026-06-02 09:12:35`
- `2026-06-02 18:47:09`

所以后端不能直接拿“某一天”去做精确过滤，而必须把一天翻译成：

- 开始时刻：`2026-06-02 00:00:00`
- 结束时刻：`2026-06-02 23:59:59.999999999`

也就是说：

- 报表里所谓“统计某一天”
- 到数据库层面，实际就是“统计某个完整时间区间”

## 9. `turnoverStatistics` 到底在做什么

营业额统计接口的本质是：

- 把 `begin ~ end` 拆成一天一天
- 每一天只统计已完成订单的营业额
- 把每天结果拼成 `dateList + turnoverList`

这里最值得记住的两个点是：

- 营业额的口径是 `Orders.COMPLETED`
- 某一天没有完成订单时，`sum(amount)` 返回的是 `null`，而不是 `0`

所以代码里必须做兜底：

- `turnover == null ? 0.0 : turnover`

这说明 Day11 里不仅要会查，还要处理“无数据时图表如何稳定展示”的细节。

## 10. `userStatistics` 到底在做什么

用户统计接口每天都要查两种口径：

- 当天新增用户数
- 截止当天的累计用户总数

所以它不是“一天只查一次”，而是：

- 先带 `begin + end` 查当天新增
- 再去掉 `begin`，只保留 `end`，查截止当天累计

这里最值得带走的认识是：

- 同一个 Mapper 统计方法，只要条件不同，就能对应不同报表口径
- Day11 里很多难点不是“不会 count”，而是“知道这次 count 的业务口径是什么”

## 11. `ordersStatistics` 到底在做什么

订单统计接口每天也要查两类数据：

- 当天总订单数
- 当天有效订单数

在当前项目里，“有效订单”的口径就是：

- `status = Orders.COMPLETED`

除此之外，它还要在整个时间段维度上计算：

- `totalOrderCount`
- `validOrderCount`
- `orderCompletionRate`

其中完成率不是数据库直接返回的字段，而是 Service 层自己算出来的：

- `有效订单数 / 总订单数`

所以 Day11 在这里再次体现出一个非常清晰的分层：

- Mapper 负责基础计数
- Service 负责业务指标加工

## 12. 为什么 `top10` 是另一种打法

前 3 个接口要的是“趋势图”：

- 哪一天是多少
- 所以必须一天一天拆

但 Top10 要的是：

- 整个时间段里
- 哪些商品累计卖得最多
- 取前 10 名

它要的是“排行结果”，不是“每日趋势结果”。

所以 Top10 不需要按天循环，而是：

- 直接把整个区间转成一个完整时间范围
- 一次性联表聚合

SQL 的核心动作是：

- `left join orders`
- `where o.status = 5`
- `group by od.name`
- `sum(od.number)`
- `order by number desc`
- `limit 0,10`

所以 `top10` 的难点在于：

- 联表聚合
- 排名
- 结果转换成 `nameList/numberList`

## 14. Day11 最值得讲的真实调试点

这次 Day11 除了写接口，也踩了几类非常真实的联调问题。

### 14.1 Redis 没启动会制造“是不是报表代码炸了”的错觉

真实现象是：

- 后端报 `RedisConnectionFailureException`

但根因不是报表 SQL 炸了，而是：

- 前端或项目其他链路触发了依赖 Redis 的接口

这次最值钱的认识之一是：

- 联调时不能看到报错就直接归因给当前新功能
- 必须先确认它到底是不是当前链路上的故障

### 14.2 401 不一定是接口逻辑错了，也可能只是 token 过期

这次接口调试中还出现过：

- 请求已经打到 `JwtTokenAdminInterceptor`
- 但最后返回 401

最终定位不是报表业务逻辑错，而是：

- 使用了过期 token

这再次说明：

- 联调排错要先分清是“认证层问题”还是“业务层问题”

### 14.3 Druid 丢弃长时间空闲连接，不等于报表功能失败

在 Top10 联调时，后端打印了：

- `discard long time none received connection`

但这后面 SQL 依然正常执行，接口结果也成功返回，前端图表也正常显示。

所以更准确的判断是：

- 这是连接池在清理过久未使用的旧连接
- 不是当前报表功能失败

这类日志在联调里很容易误导排障方向，所以必须学会区分：

- 环境层提示
- 功能性故障

## 15. Day11 最值得带走的工程认识

这次 Day11 里，最值钱的工程认识至少有 4 个。

### 15.1 报表接口的难点通常不在 Controller

Controller 很多时候只是入口壳子，真正复杂的是：

- 报表口径
- 时间范围
- 派生指标
- 图表结构

### 15.2 统计查询和图表接口是两回事

会写 `count/sum/group by` 不等于会做报表接口。

报表接口还要解决：

- 怎么按业务口径组织统计
- 怎么把结果变成前端能直接消费的结构

### 15.3 先把趋势类接口做成模板，后面会越来越顺

营业额、用户、订单这 3 个接口虽然统计对象不同，但模板几乎一致。

所以这一天的核心不是死记 3 套代码，而是吃透：

- “按天拆区间 -> 每天统计 -> 拼图表”

### 15.4 联调时要把“环境问题”和“功能问题”分开判断

Redis 未启动、token 过期、连接池清理旧连接，这些都可能在 Day11 调试阶段出现。

但它们不一定意味着：

- 新写的报表代码有 bug

学会先分层，再定位，比直接盯着一段 SQL 更重要。
