# PeakSend 升级版项目行动规划（Day13 起草版）

## 1. 这份文档是干什么的

这不是最终敲定版，也不是为了把技术名词先堆满。

它的作用是：

- 在 `Day12` 原项目收官之前，先把升级版项目的大方向定下来
- 防止后续切换对话、切换阶段时，项目升级路线重新变散
- 让我们从现在开始就知道：后面不是“随便加点新技术”，而是按阶段把 `PeakSend` 从课程项目演进成更适合求职展示的扩展版项目

一句话概括：

- 原项目解决“把业务做通”
- 升级版项目解决“把它做得更像公司里的系统”

## 2. 为什么我们需要升级版项目

当前这份 `PeakSend` 已经具备很强的业务骨架：

- 管理端和用户端两条业务线都已经存在
- 订单、支付、历史订单、催单、工作台、报表等核心模块已经逐步补齐
- 项目中已经出现了 `Redis`、`WebSocket`、定时任务、统计报表等较有价值的技术点

但如果目标从“完成课程项目”升级为“拿它去冲中小厂实习”，只停在这里还不够。

原因不是这份项目没价值，而是：

- 当前技术画像仍偏单体课程项目
- 工程化、部署、服务拆分、异步消息、可观测性这些求职高频能力还没有真正长出来
- 后面如果再单独做一份新的业务项目，投入会很大，且容易和现在已有成果割裂

因此，更合理的路线不是重开一个新业务，而是：

- 以 `PeakSend` 为主战项目
- 在保留现有业务骨架的前提下，继续做工程化升级和架构演进

## 3. 升级版项目的总目标

升级版 `PeakSend` 的目标不是炫技，而是最终形成一份你能稳定讲清楚的项目：

- 既有真实业务链路
- 又有分阶段引入的新技术栈
- 每一层升级都能解释“为什么要加”
- 每一阶段做完后都能运行、能验证、能复盘、能用于面试表达

最终希望把它升级成一份这样的项目：

- 一个可运行、可部署的商配平台
- 一个带缓存、异步通知、延迟任务、服务拆分的后端项目
- 一个可以和你的底层 `RPC` 项目形成互补的简历主项目

## 4. 升级版项目的边界与原则

后面的升级，必须遵守下面几条原则。

### 4.1 不为技术而技术

后面加每个技术，都要能回答：

- 它解决当前项目的什么问题
- 为什么适合加在 `PeakSend`
- 如果不加，会有什么痛点

如果一个技术点只是“听起来高级”，但和当前业务没有自然联系，就不优先加。

### 4.2 一次只打一小仗

后面不能一句“开始上微服务”就大跃进。

必须改成：

- 先做一个最小闭环
- 跑通
- 验证
- 复盘
- 再进入下一阶段

### 4.3 每一阶段都要有可交付结果

每一阶段结束后，至少要留下：

- 能运行的代码
- 能复现的验证步骤
- 能讲清的主链
- 能复习的文档

### 4.4 前端源码缺失时，先保证后端主链，但最终要回到真实页面验证

当前项目管理端前端源码不完整，这确实是一个现实边界。

因此后续升级时默认采用下面的推进策略：

- 优先做后端服务、缓存、MQ、Docker、网关、注册中心、链路追踪等主能力，先把核心业务主链打通
- 在前端源码不完整、工具链受限时，允许先通过接口、日志、数据库、脚本、Swagger、APIFox 完成第一轮验证
- 但如果某个功能最终要被称为“已真实交付”，仍然要补到真实页面入口上，至少完成一次管理端或用户端的可点击联调
- 因此前端不是永远可以跳过，而是可以在实现顺序上后置；最终仍要回到“页面可见、可点、状态一致”的交付标准

### 4.5 先让项目更稳，再让项目更大

因此路线顺序会固定为：

1. 先工程化和部署能力
2. 再缓存与异步解耦
3. 再服务拆分
4. 最后再做监控、链路追踪、部署流程

## 5. 我们当前站在什么位置

如果把当前项目看作“课程版 `PeakSend`”，我们现在大致已经完成了：

- 单体项目基础结构
- 管理端与用户端主要业务链
- 下单、支付主干、历史订单、再来一单
- WebSocket 催单提醒
- 订单处理、工作台、统计报表等主体能力

也就是说，当前版本已经比较接近：

- 业务基本成型
- 工程能力和架构能力还没系统升级

所以后续升级，不是从零开始，而是从一个已经有业务主干的项目继续向上长。

## 6. 升级版总体路线图

升级版暂定分成四个大版本：

- `V1`：Docker + Redis 缓存工程化
- `V2`：Redis 高并发资源竞争 + RocketMQ 削峰异步
- `V3`：Spring Cloud Alibaba 最小微服务骨架
- `V4`：日志链路、可观测性、量化指标与最终表达

如果进一步映射到天数，可以先按 `Day13` 到 `Day20` 这样规划。

## 7. Day13 ~ Day20 阶段规划

下面这部分不是死板日历，而是“默认推进顺序”。

如果实际实现中某一阶段跨度大，也允许拆成两天或更多天，但顺序尽量不乱。

### Day13：Docker 化基础环境与一键启动

目标：

- 把当前项目从“本机手动拼环境”升级成“可通过容器统一拉起核心环境”
- 降低后续继续扩展时的环境成本和迁移成本

核心要做的事：

- 明确当前项目运行依赖：

  - MySQL
  - Redis
  - Nginx
  - 后端服务
- 为这些依赖补齐容器化方案
- 提供 `docker-compose.yml`
- 整理环境变量和端口说明
- 形成一份最小启动说明文档

预期达到的效果：

- 后面别人拿到项目后，不必再到处手动配环境
- 至少能通过较固定的步骤拉起 MySQL、Redis、Nginx 等核心基础设施
- 项目具备“工程交付感”

重点验证：

- 容器启动后数据库可连接
- Redis 可连接
- Nginx 可以正常转发
- 后端能连上容器里的依赖并启动

这一天的求职价值：

- 你可以明确讲“我把项目从本机开发态，推进成了可容器化部署的版本”

### Day14：Redis 缓存工程化专题

目标：

- 把项目里原本分散、半成型的 Redis 能力升级成一个可讲清楚的缓存工程化专题
- 不只停留在“项目里有 Redis”，而是能明确体现热点读优化、缓存一致性、穿透/雪崩基础防护与运行态验证

核心要做的事：

- 盘点当前项目中已有的 Redis 用法与缓存注解分布，先识别“已经做了什么”和“还缺什么”
- 补齐最适合教学式推进的两个基础闭环：
  - 用户端分类列表缓存
  - 管理端分类变更后的缓存失效
- 继续升级现有缓存能力：
  - 统一缓存 key 命名规则
  - 引入统一 TTL 设计
  - 通过分档 TTL 形成第一版错峰过期
  - 为典型查询补第一版空值缓存/穿透防护
  - 梳理 Redis 异常时的兜底策略
- 补一个真正能出量化数据的热点查询缓存：
  - 报表类热点查询结果缓存
- 完成一轮可复用的验证模板：
  - Redis key / TTL
  - Controller 日志
  - SQL 是否消失
  - 接口耗时对比

预期达到的效果：

- 项目不再只是“用过 Redis”
- 而是能清楚讲出：
  - 哪些接口适合缓存
  - 缓存 key 为什么这样设计
  - 为什么管理端写操作后要删缓存
  - TTL / 穿透 / 雪崩 / 兜底分别解决什么问题
  - 为什么判断缓存命中不能只看耗时
- 至少产出一组可验证、可量化的缓存优化证据

重点验证：

- 首次读走数据库，二次读命中缓存
- 管理端写操作后缓存失效，用户端重新回库
- Redis 中能够观察到对应 key 与 TTL
- Redis 异常时系统至少能保持核心链路不直接 500
- 报表热点接口在缓存前后具备可对比的响应时间和数据库查询量变化
- 至少拿到一组：
  - 接口响应时间对比
  - MySQL Questions 增量对比

这一天的求职价值：

- 你可以正式讲：
  - 热点接口缓存
  - 缓存与数据库一致性
  - 缓存穿透 / 雪崩的第一版应对
  - 为什么这一天已经开始体现后端高频读优化与工程化设计能力

### Day15：Redis 高并发资源竞争专题

目标：

- 不重复堆更多缓存接口，而是补一个更能代表 Redis 深度的高并发资源竞争场景
- 让项目的 Redis 能力从“缓存优化”继续下探到“原子性、并发控制、削峰前置准备”

候选业务壳子：

- 限量套餐活动
- 限量优惠券领取

默认推荐：

- 优先选“限量套餐活动”
- 原因不是它听起来更高级，而是它更符合当前项目的真实边界：
  - 现有后端已经具备套餐、购物车、下单主链
  - 现有小程序与管理端前端并没有优惠券现成页面和交互锚点
  - 限量套餐活动更容易同时挂到管理端和小程序现有产品形态上，既能完成 Redis 高并发资源竞争专题，也更适合做真实页面联调

核心要做的事：

- 设计一个限量资源模型：
  - 总库存/总名额
  - 活动开始与结束时间
  - 用户领取资格
- 使用 Redis 预热库存/名额
- 使用 Lua 脚本完成原子校验：
  - 是否到活动时间
  - 是否还有库存
  - 是否已经领取过
- 落地“一人一单 / 一人一券”约束
- 给后续 MQ 异步落库预留消息化边界

预期达到的效果：

- 项目不再只有“缓存 Redis”
- 而是开始具备“高并发资源竞争下的 Redis 原子控制”这一层能力

重点验证：

- 并发请求下库存不会被超扣
- 同一用户重复抢购不会成功
- Lua 原子脚本能在一次执行中完成核心校验
- 至少留下一组并发请求前后库存、成功数、失败数的对照数据
- 第一轮可先通过接口、日志与数据库验证核心链路；最终收口时补真实页面联调，确认管理端创建/启停与小程序抢购主链都能实际使用

这一天的求职价值：

- 你可以正式讲：
  - 为什么高并发资源竞争不能只靠数据库行锁硬扛
  - 为什么要把热点竞争校验前移到 Redis
  - 为什么 Lua 比“多次 Redis 调用拼在 Java 里”更稳

### Day16：RocketMQ 削峰异步化 + 延迟关单

目标：

- 把 Day15 的高并发资源竞争场景和订单域经典异步场景一起接到 MQ 上
- 用尽量少的天数同时拿下“削峰异步”与“超时关闭”两个高价值后端题

核心要做的事：

- 引入 `RocketMQ`
- 为 Day15 资源竞争场景补消息投递与异步落库
- 为订单域接入延迟消息，实现超时未支付自动关单
- 明确：
  - 谁负责生产消息
  - 谁负责消费消息
  - 消费端如何做幂等
  - 订单状态如何做二次校验避免误关单

预期达到的效果：

- 项目第一次具备“Redis 前置拦截 + MQ 异步削峰 + DB 最终落库”的组合链路
- MQ 的价值不再停留在“会收发消息”，而是能明确体现：
  - 主链路减负
  - 峰值削峰
  - 交易时效处理

重点验证：

- 并发领取/抢购请求可以先快速返回，再异步持久化
- 延迟关单链路正常生效
- 已支付订单不会被误取消
- 关键消息场景具备幂等保护

这一天的求职价值：

- 你可以同时讲：
  - 为什么引入 MQ
  - 为什么同步链路不能什么都自己做
  - 超时关单为什么是交易类项目里的经典题

Day16 当前完成情况（更新于 2026-08-17）：

- 已完成 RocketMQ Docker 环境接入与后端业务配置
- 已完成限量套餐抢购链异步化：
  - Redis Lua 抢资格
  - RocketMQ 发送抢购落库消息
  - 消费端异步扣活动库存并插抢购记录
- 已完成订单延迟关单链：
  - 下单后发送延迟关单消息
  - 到期后二次校验订单状态
  - 仅对仍为待付款订单执行自动取消
- 已完成两条链的真实联调验证：
  - 抢购异步落库链已拿到 Redis / MySQL / 日志三侧闭环证据
  - 延迟关单链已拿到订单状态自动从待付款变为已取消的真实证据
- 已补齐当前阶段的代表性量化结果：
  - 抢购异步落库链：发送消息 -> 消费收到约 `7ms`，发送消息 -> MySQL 落库成功约 `20ms`
  - 延迟关单链：`order_time -> cancel_time` 约 `10s`
- 已补齐重启场景下的运行态验证：
  - nginx 曾因持有旧 backend IP 出现 `502`，重启后恢复正常转发
  - Redis 活动缓存重启后丢失，但请求可触发 `ensureActivityCacheLoaded(activityId)` 自动回源重建
- 联调阶段曾两次出现“offset 前进但业务未真正落库”的问题，现已通过“listener 只接消息、事务逻辑下沉到独立 Service”的方式修复
- 当前 Day16 可视为：
  - **实现完成**
  - **真实验证完成**
  - **文档与话术已同步到当前状态**
  - **当前处于提交前复查阶段**

### Day17：Spring Cloud Alibaba 基础设施进场

目标：

- 开始从单体工程视角切换到微服务演进视角
- 但明确控制范围，只做“最小可讲骨架”，不把战线拉太宽

核心要做的事：

- 引入 `Nacos`
- 引入 `Gateway`
- 建立最小的微服务骨架
- 梳理哪些公共代码仍应放在公共模块
- 梳理注册发现、网关入口和 Docker 服务名通信的基本组织方式

预期达到的效果：

- 项目第一次具备：
  - 服务注册发现
  - 网关统一入口
  - 外部入口与内部路由分层

重点验证：

- 至少两个服务可以被注册到 `Nacos`
- `Gateway` 可以正确转发请求
- 外部访问 `http://localhost:8081/api/...` 可以真正穿过 `nginx -> gateway -> backend`

当前同步到真实代码状态后的口径：

- Day17 当前已完成的是：
  - `Nacos` 注册发现
  - `Gateway` 独立入口
  - `nginx -> gateway -> backend` 的最小链路贯通
- Day17 当前**还没有**真正把 `Nacos` 配置中心接进来
- 所以后续文档、话术和量化都必须按“注册发现 + 网关”口径记录，不能把配置中心提前写成已完成

这一天的求职价值：

- 你能讲“为什么微服务不能只理解成把包拆散，而要先建设基础设施”

### Day18：最小核心服务拆分 + OpenFeign 调用治理

目标：

- 迈出真正的服务拆分第一步
- 但不追求拆得多，只追求“拆得有边界、拆得能跑通、拆完能讲”

建议优先拆分的服务：

- `gateway-service`
- `order-service`
- `product-service`

按需保留的附加服务：

- `notify-service`

拆分思路：

- `order-service` 负责订单主链、状态流转、支付后状态变更
- `product-service` 负责菜品、套餐、分类、店铺营业态等商品域能力
- `notify-service` 如果保留，则负责 WebSocket 推送和消息消费
- 通过 `OpenFeign` 打通第一批必要的跨服务调用

预期达到的效果：

- 业务边界不再只停留在包结构层面，而是真正形成跨服务调用关系
- 微服务不只是“目录拆开”，而是已经具备最小可运行的服务协作能力

重点验证：

- 下单或查询链路至少能跨两个服务完成
- 服务间调用结果可通过日志和接口验证
- 不追求一天拆四个服务，只要求两到三个核心服务边界清晰

这一天的求职价值：

- 你可以开始真正讲“为什么这样拆，而不是那样拆”
- 也能避免把时间浪费在过宽的服务拆分和重复搬代码上

当前落地进展（Day18 第一阶段）：

- 已新增独立 `product-service` 模块，作为 Day18 第一刀的最小商品服务
- 已在 `sky-server` 接入 `OpenFeign`
- 已把购物车加购链路中“按 id 查询商品信息”的动作改成：
  - `sky-server` 借助 `Feign` 调用 `product-service`
- 已补齐 `Dockerfile.product` 与 `docker-compose.yml` 中的 `product-service` 编排
- 已完成后端全模块构建通过
- 已补完运行态接口验证：
  - `gateway -> sky-server -> product-service`
  - `nginx -> gateway -> sky-server -> product-service`

当前阶段结论：

- Day18 没有偏离“最小核心服务拆分 + OpenFeign 调用治理”的路线
- 只是没有一上来硬拆高耦合的 `order-service`
- 而是先按“最小可跑”原则，优先拆出了边界更清晰、风险更可控的 `product-service`

### Day19：日志链路、traceId 与可观测性补强

目标：

- 在服务变多后补上真正能提升工程表达质量的问题定位能力
- 让项目从“能拆能跑”升级成“出现问题时能定位”

核心要做的事：

## 13. 升级版项目量化指标体系 & 简历表达库

> 本节目的：解决升级版规划中"只写了做什么，没写优化了多少"的问题，让每一项升级在简历和面试里都能讲出**动作 → 措施 → 指标 → 结果**的完整链条。

### 13.1 先讲清楚：三种量化类型，别瞎编数字

写简历和面试时，数字分三类，**A 类必须真跑工具测了再写，B/C 类做工程对比推导后就可以写，但都要保留验证记录（截图/日志/对比表）防追问**。

| 类型 | 含义 | 举例 | 面试时怎么答"你怎么测的" |
|---|---|---|---|
| **A 类：真实可压测量化** | 必须用工具（JMeter/APIFOX压测、Redis INFO、日志统计）实际跑出数据后才能写到简历上 | 缓存命中率 85%+、接口 P95 从 320ms 降到 78ms | "我用 APIFOX / JMeter 连续压了 5 轮，每轮 1000 次请求，去掉首尾冷启动后取平均值；Redis 命中率用 `INFO stats` 里的 `keyspace_hits/(hits+misses)` 看的。" |
| **B 类：工程维度量化** | 不需要压测，只要对比前后代码/配置/流程/脚本，就能客观算出来 | 部署步骤从 23 步压到 4 步、重复 SQL 代码删了 420 行、手动配置项从 17 个减到 5 个 | "我统计了原先手工部署文档的步骤清单和新的 docker-compose up 一行拉起对比；代码重复行数是统计原 ReportService 5 个按天循环方法的共用逻辑抽出来之后删掉的行数。" |
| **C 类：定性转半定量** | 逻辑上必然成立、无法精确算但可以用"发生概率/覆盖范围/及时性级别"表达 | 把"人工巡检几乎必定漏单"优化为"MQ 消费失败告警 1 分钟内可感知；压测 5000 单未出现误关单" | "我做了 3 轮故障注入：故意停消费者、故意写错SQL、重复投递，每轮都验证幂等和告警；5000 条延迟消息里没有出现一笔已支付订单被误关。" |

### 13.2 比类型更重要的一条原则：不是按“天”量化，而是按“最终能力块”量化

这里必须先纠正一个很容易把人带偏的误区：

- 不是做完每一天都必须量化
- 也不是某一天做了一个技术点，就一定要立刻测一轮数字

正确做法是：

- 先判断这个能力是不是后续还会继续被同一路线改造
- 再判断它当前是不是已经进入“阶段终态”或“最终载体”
- 只有当它短期内不会再被同路线推翻时，才值得投入时间做量化

换句话说：

- 如果今天做的只是一个过渡版本，明天同一路线还会继续升级
- 那就不急着测“整车速度”
- 应该等这条能力线的最终稳定版本出来后再测

因此后面所有量化都遵守下面这条总原则：

1. **独立能力线，且后面不会被同路线替换**
   - 可以在当前阶段直接量化
   - 例如：Docker 工程交付、Redis 热点读缓存
2. **同一路线后面还会继续升级**
   - 先不急着测整链最终数字
   - 只保留必要的功能验证证据
   - 等最终稳定版本再测
3. **前一阶段的技术点仍然是后一阶段最终方案的一部分**
   - 不必回到老版本重测
   - 直接在当前最终代码上测这部分能力

最典型的例子就是：

- Day15 的 Redis + Lua 抢资格，不需要为了“补 Day15 量化”而回退到 Day15 老代码去测
- 因为 Day16 仍然保留了这部分能力，只是把后半段从同步落库升级成了 MQ 异步落库
- 所以 Day15 这条能力线真正该用于简历的数字，应优先从 Day16 的最终代码上拿

一句话记住：

- **量化归属可以按 Day 讲，但量化数据要优先取自最终稳定版本。**

#### ▶ Day16：RocketMQ 削峰异步化 + 延迟消息实现超时自动关单（A 类 + C 类）

> Day16 从量化视角看，是当前单体交易链的**最终稳定载体**。
> 也就是说：
> - Day15 的 Redis 高并发资格控制能力，到了 Day16 才真正接上 MQ 异步化后的完整交易后半段
> - 抢购链的最终性能、最终一致性和削峰收益，应以 Day16 当前代码为准
> - 延迟关单也是 Day16 才首次具备最终业务形态，因此必须在 Day16 做正式量化

| 量化维度 | 测量方法 | 合理数值区间 | 简历句式 |
|---|---|---|---|
| **高峰请求主链响应时间变化** | 对 Day15 领取/抢购接口压测，对比“同步直落 DB”和“发 MQ 后异步落库”两种方案 | avg 80~180ms → 20~50ms，P95 下降 40%+ | **"在高并发领取/抢购链路上引入 RocketMQ 做异步落库和削峰，主链路从'同步校验+写库'收敛为'Redis 校验+发消息'，峰值接口响应时间下降约 50%。"** |
| **消息投递/消费成功率** | 发 5000 条业务消息，统计生产成功数、消费成功数、死信数 | 投递成功率 99.9%+；消费成功率 99.5%+ | **"通过发送确认、消费重试和幂等设计，在 5000 条级消息压测下实现 99.9%+ 的消息投递成功率和 99.5%+ 的消费成功率。"** |
| **关单及时性**（对比：Spring Task 每分钟扫一次表 vs MQ 16 级延迟消息） | 创建 100 笔待付款订单，不支付。记录：从"订单创建时间+15分钟"那一刻 → 实际被置为 CANCELLED 的时间差 | 定时任务平均延迟 0~60s（扫表间隔）→ MQ 延迟消息平均延迟 < 3s | **"基于 RocketMQ 延迟消息重做超时关单链路，对比原轮询方案，将 15 分钟未支付订单的关单执行精度从分钟级提升到秒级，平均偏差从 30s 以上压到 3s 以内。"** |
| **误关单率**（压测必做） | 5000 单压测：其中随机 50% 在最后 1 秒完成支付。统计支付成功但仍然被取消的订单数 | 目标：5000 单误关单 = 0 | **"设计了'消费时二次校验订单状态'的兜底逻辑，在 5000 单的并发压测 + 最后秒级支付的边界场景下，已支付订单被误关单的比例为 0。"** |
| **数据库轮询压力下降**（对比旧实现） | MySQL `show global status like 'Handler_read%'`：对比 1 小时内，定时任务每分钟扫 `WHERE status=1 AND order_time < NOW()-15m` 的扫描行数 vs MQ 延迟消息的 DB 访问次数 | 定时任务每小时扫 60 次 × N 行 → MQ 只在到期时执行 1 次按主键 UPDATE | **"关单链路从'全表定时扫描'改为'到期精准触发'，DB 在关单场景的无效扫描量下降 99%，峰值时段订单表不会被定时任务周期性打穿。"** |
| **可配置性**（B 类） | 对比：原先改关单超时需要改代码重编译 vs 现在只需改 Topic 延迟级别或配置文件 | 改生效时间：原先 10 分钟 → 现在 1 分钟 | **"关单超时时间、重试次数、告警阈值统一抽配置化管理，调整运营策略无需改代码重新发布。"** |

Day16 建议分成两层执行：

- **必测项**
  - Redis + Lua 原子性与防超卖一致性
  - 抢购链同步 vs 异步的主链 RT 对比
  - 延迟关单偏差
  - 已支付订单不会被误取消
- **增强项**
  - 5000 条级消息成功率
  - 更大样本的误关单压测
  - 与旧定时扫描方案的 DB 压力差异

也就是说，Day16 不要求你一次把所有大样本极限压测全部做完，但至少要先拿到一轮**可写进简历的核心数字**。

### 13.7 面试官追问数字来源的"标准防守答法"

以后面试官只要一问"你这个 70% 的优化率是怎么算出来的？"，你就按这个三段式答，**别只说"我测的"**：

```
"我是用「先基线、后优化、再对比」的方式测的：
 ① 先把代码切回优化前版本，用 APIFOX / JMeter 跑 5 轮稳定基线，记录平均 rt、p95、mysql questions 增量；
 ② 再切到优化后代码，保证数据量和请求量完全一致，跑同样 5 轮，去首尾取中间值；
 ③ 两者做差，再结合 Redis INFO 和慢查询日志交叉验证，最终得出这个数字。
另外我还留了当时的压测报告和对比截图/日志，面试现场其实我也可以当场给你看当时的对比记录。"
```

### 13.9 本节结论

- 升级版最大的求职风险不是"做不出来"，而是**做出来了但说不清"优化了多少"**。
- 从现在开始，不再机械要求“每天都量化”，而改成：**每条能力线进入阶段终态时，必须补一轮正式量化；其余过渡阶段只做功能验证和必要留痕。**
- 后续执行时，优先遵守这条节奏：
  1. 先判断今天做的东西是不是最终稳定版本；
  2. 如果是，就按上面对应阶段的必测项拿正式数字；
  3. 如果不是，就先保留功能验证证据，等最终版本再测；
  4. 把最终可写进简历的对比结果存到 `docs/upgrade-metrics/` 下，按能力线而不是按日期留档；
  5. 再从"简历句式"里抄一版你当天真正能说出口的 30 秒表达，补进对应话术文档。
- 只要按这个规则执行，后面就不会再出现两种典型问题：
  - 对过渡版本过早量化，浪费时间
  - 功能做完了，却忘记在最终版本上拿简历数字
