# PeakSend 升级版项目行动规划（Day13 起草版）

## 1. 这份文档是干什么的

这不是最终敲定版，也不是为了把技术名词先堆满。

它的作用是：

- 在 `Day12` 原项目收官之前，先把升级版项目的大方向定下来
- 防止后续切换对话、切换阶段时，项目升级路线重新变散
- 让我们从现在开始就知道：后面不是“随便加点新技术”，而是按阶段把 `PeakSend` 从课程项目演进成更适合求职展示的扩展版项目

一句话概括：

- 原项目解决“把业务做通”
- 升级版项目解决“把它做得更像公司里的系统”

## 2. 为什么我们需要升级版项目

当前这份 `PeakSend` 已经具备很强的业务骨架：

- 管理端和用户端两条业务线都已经存在
- 订单、支付、历史订单、催单、工作台、报表等核心模块已经逐步补齐
- 项目中已经出现了 `Redis`、`WebSocket`、定时任务、统计报表等较有价值的技术点

但如果目标从“完成课程项目”升级为“拿它去冲中小厂实习”，只停在这里还不够。

原因不是这份项目没价值，而是：

- 当前技术画像仍偏单体课程项目
- 工程化、部署、服务拆分、异步消息、可观测性这些求职高频能力还没有真正长出来
- 后面如果再单独做一份新的业务项目，投入会很大，且容易和现在已有成果割裂

因此，更合理的路线不是重开一个新业务，而是：

- 以 `PeakSend` 为主战项目
- 在保留现有业务骨架的前提下，继续做工程化升级和架构演进

## 3. 升级版项目的总目标

升级版 `PeakSend` 的目标不是炫技，而是最终形成一份你能稳定讲清楚的项目：

- 既有真实业务链路
- 又有分阶段引入的新技术栈
- 每一层升级都能解释“为什么要加”
- 每一阶段做完后都能运行、能验证、能复盘、能用于面试表达

最终希望把它升级成一份这样的项目：

- 一个可运行、可部署的商配平台
- 一个带缓存、异步通知、延迟任务、服务拆分的后端项目
- 一个可以和你的底层 `RPC` 项目形成互补的简历主项目

## 4. 升级版项目的边界与原则

后面的升级，必须遵守下面几条原则。

### 4.1 不为技术而技术

后面加每个技术，都要能回答：

- 它解决当前项目的什么问题
- 为什么适合加在 `PeakSend`
- 如果不加，会有什么痛点

如果一个技术点只是“听起来高级”，但和当前业务没有自然联系，就不优先加。

### 4.2 一次只打一小仗

后面不能一句“开始上微服务”就大跃进。

必须改成：

- 先做一个最小闭环
- 跑通
- 验证
- 复盘
- 再进入下一阶段

### 4.3 每一阶段都要有可交付结果

每一阶段结束后，至少要留下：

- 能运行的代码
- 能复现的验证步骤
- 能讲清的主链
- 能复习的文档

### 4.4 前端源码缺失时，优先升级后端和系统层

当前项目管理端前端源码不完整，这是一个现实边界。

因此后续升级时默认采用下面的推进策略：

- 优先做后端服务、缓存、MQ、Docker、网关、注册中心、链路追踪等不依赖前端源码的能力
- 验证方式以接口、日志、数据库、脚本、Swagger、APIFox 为主
- 如果后面某个阶段确实需要新的页面演示，再考虑单独补一个极简演示页，而不是强行深改现有打包前端

### 4.5 先让项目更稳，再让项目更大

因此路线顺序会固定为：

1. 先工程化和部署能力
2. 再缓存与异步解耦
3. 再服务拆分
4. 最后再做监控、链路追踪、部署流程

## 5. 我们当前站在什么位置

如果把当前项目看作“课程版 `PeakSend`”，我们现在大致已经完成了：

- 单体项目基础结构
- 管理端与用户端主要业务链
- 下单、支付主干、历史订单、再来一单
- WebSocket 催单提醒
- 订单处理、工作台、统计报表等主体能力

也就是说，当前版本已经比较接近：

- 业务基本成型
- 工程能力和架构能力还没系统升级

所以后续升级，不是从零开始，而是从一个已经有业务主干的项目继续向上长。

## 6. 升级版总体路线图

升级版暂定分成四个大版本：

- `V1`：Docker + Redis 缓存工程化
- `V2`：Redis 高并发资源竞争 + RocketMQ 削峰异步
- `V3`：Spring Cloud Alibaba 最小微服务骨架
- `V4`：日志链路、可观测性、量化指标与最终表达

如果进一步映射到天数，可以先按 `Day13` 到 `Day20` 这样规划。

## 7. Day13 ~ Day20 阶段规划

下面这部分不是死板日历，而是“默认推进顺序”。

如果实际实现中某一阶段跨度大，也允许拆成两天或更多天，但顺序尽量不乱。

### Day13：Docker 化基础环境与一键启动

目标：

- 把当前项目从“本机手动拼环境”升级成“可通过容器统一拉起核心环境”
- 降低后续继续扩展时的环境成本和迁移成本

核心要做的事：

- 明确当前项目运行依赖：

  - MySQL
  - Redis
  - Nginx
  - 后端服务
- 为这些依赖补齐容器化方案
- 提供 `docker-compose.yml`
- 整理环境变量和端口说明
- 形成一份最小启动说明文档

预期达到的效果：

- 后面别人拿到项目后，不必再到处手动配环境
- 至少能通过较固定的步骤拉起 MySQL、Redis、Nginx 等核心基础设施
- 项目具备“工程交付感”

重点验证：

- 容器启动后数据库可连接
- Redis 可连接
- Nginx 可以正常转发
- 后端能连上容器里的依赖并启动

这一天的求职价值：

- 你可以明确讲“我把项目从本机开发态，推进成了可容器化部署的版本”

### Day14：Redis 缓存工程化专题

目标：

- 把项目里原本分散、半成型的 Redis 能力升级成一个可讲清楚的缓存工程化专题
- 不只停留在“项目里有 Redis”，而是能明确体现热点读优化、缓存一致性、穿透/雪崩基础防护与运行态验证

核心要做的事：

- 盘点当前项目中已有的 Redis 用法与缓存注解分布，先识别“已经做了什么”和“还缺什么”
- 补齐最适合教学式推进的两个基础闭环：
  - 用户端分类列表缓存
  - 管理端分类变更后的缓存失效
- 继续升级现有缓存能力：
  - 统一缓存 key 命名规则
  - 引入统一 TTL 设计
  - 通过分档 TTL 形成第一版错峰过期
  - 为典型查询补第一版空值缓存/穿透防护
  - 梳理 Redis 异常时的兜底策略
- 补一个真正能出量化数据的热点查询缓存：
  - 报表类热点查询结果缓存
- 完成一轮可复用的验证模板：
  - Redis key / TTL
  - Controller 日志
  - SQL 是否消失
  - 接口耗时对比

预期达到的效果：

- 项目不再只是“用过 Redis”
- 而是能清楚讲出：
  - 哪些接口适合缓存
  - 缓存 key 为什么这样设计
  - 为什么管理端写操作后要删缓存
  - TTL / 穿透 / 雪崩 / 兜底分别解决什么问题
  - 为什么判断缓存命中不能只看耗时
- 至少产出一组可验证、可量化的缓存优化证据

重点验证：

- 首次读走数据库，二次读命中缓存
- 管理端写操作后缓存失效，用户端重新回库
- Redis 中能够观察到对应 key 与 TTL
- Redis 异常时系统至少能保持核心链路不直接 500
- 报表热点接口在缓存前后具备可对比的响应时间和数据库查询量变化
- 至少拿到一组：
  - 接口响应时间对比
  - MySQL Questions 增量对比

这一天的求职价值：

- 你可以正式讲：
  - 热点接口缓存
  - 缓存与数据库一致性
  - 缓存穿透 / 雪崩的第一版应对
  - 为什么这一天已经开始体现后端高频读优化与工程化设计能力

### Day15：Redis 高并发资源竞争专题

目标：

- 不重复堆更多缓存接口，而是补一个更能代表 Redis 深度的高并发资源竞争场景
- 让项目的 Redis 能力从“缓存优化”继续下探到“原子性、并发控制、削峰前置准备”

候选业务壳子：

- 限量套餐活动
- 限量优惠券领取

默认推荐：

- 优先选“限量套餐活动”
- 原因不是它听起来更高级，而是它更符合当前项目的真实边界：
  - 现有后端已经具备套餐、购物车、下单主链
  - 现有小程序与管理端前端并没有优惠券现成页面和交互锚点
  - 限量套餐活动可以主要通过后端接口、APIFox、压测脚本完成验证，不把路线绑死在前端改造上

核心要做的事：

- 设计一个限量资源模型：
  - 总库存/总名额
  - 活动开始与结束时间
  - 用户领取资格
- 使用 Redis 预热库存/名额
- 使用 Lua 脚本完成原子校验：
  - 是否到活动时间
  - 是否还有库存
  - 是否已经领取过
- 落地“一人一单 / 一人一券”约束
- 给后续 MQ 异步落库预留消息化边界

预期达到的效果：

- 项目不再只有“缓存 Redis”
- 而是开始具备“高并发资源竞争下的 Redis 原子控制”这一层能力

重点验证：

- 并发请求下库存不会被超扣
- 同一用户重复抢购不会成功
- Lua 原子脚本能在一次执行中完成核心校验
- 至少留下一组并发请求前后库存、成功数、失败数的对照数据
- 允许在没有新增前端页面的情况下，仅通过接口与日志完成闭环验证

这一天的求职价值：

- 你可以正式讲：
  - 为什么高并发资源竞争不能只靠数据库行锁硬扛
  - 为什么要把热点竞争校验前移到 Redis
  - 为什么 Lua 比“多次 Redis 调用拼在 Java 里”更稳

### Day16：RocketMQ 削峰异步化 + 延迟关单

目标：

- 把 Day15 的高并发资源竞争场景和订单域经典异步场景一起接到 MQ 上
- 用尽量少的天数同时拿下“削峰异步”与“超时关闭”两个高价值后端题

核心要做的事：

- 引入 `RocketMQ`
- 为 Day15 资源竞争场景补消息投递与异步落库
- 为订单域接入延迟消息，实现超时未支付自动关单
- 明确：
  - 谁负责生产消息
  - 谁负责消费消息
  - 消费端如何做幂等
  - 订单状态如何做二次校验避免误关单

预期达到的效果：

- 项目第一次具备“Redis 前置拦截 + MQ 异步削峰 + DB 最终落库”的组合链路
- MQ 的价值不再停留在“会收发消息”，而是能明确体现：
  - 主链路减负
  - 峰值削峰
  - 交易时效处理

重点验证：

- 并发领取/抢购请求可以先快速返回，再异步持久化
- 延迟关单链路正常生效
- 已支付订单不会被误取消
- 关键消息场景具备幂等保护

这一天的求职价值：

- 你可以同时讲：
  - 为什么引入 MQ
  - 为什么同步链路不能什么都自己做
  - 超时关单为什么是交易类项目里的经典题

### Day17：Spring Cloud Alibaba 基础设施进场

目标：

- 开始从单体工程视角切换到微服务演进视角
- 但明确控制范围，只做“最小可讲骨架”，不把战线拉太宽

核心要做的事：

- 引入 `Nacos`
- 引入 `Gateway`
- 建立最小的微服务骨架
- 梳理哪些公共代码仍应放在公共模块
- 梳理配置中心和注册中心的基本组织方式

预期达到的效果：

- 项目第一次具备：
  - 服务注册发现
  - 配置集中管理
  - 网关统一入口

重点验证：

- 至少两个服务可以被注册到 `Nacos`
- `Gateway` 可以正确转发请求
- 配置可以从配置中心读取

这一天的求职价值：

- 你能讲“为什么微服务不能只理解成把包拆散，而要先建设基础设施”

### Day18：最小核心服务拆分 + OpenFeign 调用治理

目标：

- 迈出真正的服务拆分第一步
- 但不追求拆得多，只追求“拆得有边界、拆得能跑通、拆完能讲”

建议优先拆分的服务：

- `gateway-service`
- `order-service`
- `product-service`

按需保留的附加服务：

- `notify-service`

拆分思路：

- `order-service` 负责订单主链、状态流转、支付后状态变更
- `product-service` 负责菜品、套餐、分类、店铺营业态等商品域能力
- `notify-service` 如果保留，则负责 WebSocket 推送和消息消费
- 通过 `OpenFeign` 打通第一批必要的跨服务调用

预期达到的效果：

- 业务边界不再只停留在包结构层面，而是真正形成跨服务调用关系
- 微服务不只是“目录拆开”，而是已经具备最小可运行的服务协作能力

重点验证：

- 下单或查询链路至少能跨两个服务完成
- 服务间调用结果可通过日志和接口验证
- 不追求一天拆四个服务，只要求两到三个核心服务边界清晰

这一天的求职价值：

- 你可以开始真正讲“为什么这样拆，而不是那样拆”
- 也能避免把时间浪费在过宽的服务拆分和重复搬代码上

### Day19：日志链路、traceId 与可观测性补强

目标：

- 在服务变多后补上真正能提升工程表达质量的问题定位能力
- 让项目从“能拆能跑”升级成“出现问题时能定位”

核心要做的事：

- 统一日志格式
- 为请求生成并透传 `traceId`
- 补齐 `Gateway`、服务间调用、MQ 消费侧的链路标识
- 梳理统一问题定位手册

预期达到的效果：

- 出现问题时，不再只能依赖单机本地日志定位
- 多服务请求能够串成一条链路

重点验证：

- 一次请求经过多个服务时，日志中能串起同一条链路
- MQ 生产和消费链中也能看到关联标识

这一天的求职价值：

- 你可以讲日志链路、traceId 透传、问题定位效率提升

- 给升级版项目做一个阶段性收口

核心要做的事：

预期达到的效果：

- 当前升级版不再只是“做过若干优化”
- 而是能形成：
  - 缓存优化专题
  - Redis 高并发专题

  - 可观测性专题

- 项目启动步骤清晰、部署步骤清晰
- 每个阶段至少有一组可复用的指标证据

  - 原版项目做了什么

这一天的求职价值：

- 你可以讲量化验证、阶段部署、项目演进路线和简历表达

## 8. 各阶段做完后应该留下什么

- 阶段文档

## 9. 为什么这个路线是可做的

你担心后面没有课程标准答案，也担心前端源码不完整。

这是合理的，但这条路线依然是可做的，原因在于：

- 后续最值钱的升级点，本来就主要发生在后端和系统层
- `Docker`、`Redis`、`RocketMQ`、`Nacos`、`Gateway`、`Feign`、日志链路追踪这些，都不依赖完整前端源码
- 它们的验证方式更适合用接口、日志、数据库和服务运行状态来完成

也就是说：

- 前面课程阶段更像“对照成熟项目补齐业务”
- 后面升级阶段更像“按真实工程思路继续演进”

推进方法会变，但并不意味着做不下去。

## 10. 这份规划当前不包含什么

为了控制边界，当前版本暂时不把下面这些列为优先主线：

- `Kubernetes`
- 复杂分布式事务全家桶
- 过重的领域建模改造

### 13.3 通用量化工具箱（你每做完一天就按这个清单跑一次）

| 要测什么 | 用什么工具/方法 | 具体命令 / 操作 |
|---|---|---|
| 接口响应时间 avg/p95/p99 | APIFOX 自动化测试 / JMeter Thread Group | 连续 1000 次请求，分冷启动 200 次 + 预热后 800 次，去掉首尾 |
| 数据库 QPS / 查询次数 | MySQL 全局状态 | `SHOW GLOBAL STATUS LIKE 'Questions';` 前后做差 |
| Redis 命中率 / 内存 | redis-cli | `INFO stats; INFO memory` → `hits/(hits+misses)` |
| MQ 投递/消费成功率 | RocketMQ Dashboard + 业务日志对账 | 数 Dashboard 里的 `生产总数 / 消费成功数 / 死信数`，或按订单号对日志 |
| 幂等验证 | 手动发重复消息 + 写脚本重投 10 次 | 检查 DB 最终状态只有 1 次副作用 |
| 缓存效果 | 双环境对比：一次关 Redis、一次开 Redis 跑同接口 | 取时间差和 MySQL Questions 差 |

### 13.4 简历数字安全区间（**非常重要：没测就别往上填**）

给你一份"就算你不做极限压测，按正常流程跑也不会离谱"的区间参考。**你测出来的数字落在这个区间里就可以放心写；如果比这个区间好很多，可以写得更猛；差很多就别吹、先排查实现。**

```
缓存命中率：        85% ~ 95%     ← 热点接口正常水平
热点接口 avg rt：  200~400ms → 30~80ms   ← 单体 + MySQL 常态
主业务接口 rt 下降：30% ~ 60%   ← 异步化正常收益
DB 查询量下降：    80% ~ 98%   ← 报表级缓存做了之后
部署步骤压缩：     15~30 步 → 3~6 步
关单偏差：         30s+ → <5s
误关单率：         5000 单 = 0
MQ 投递成功率：    99.5% ~ 99.99%
问题定位耗时：     15~30min → 2~5min
跨服务端到端成功率：99% ~ 99.8%
```

### 13.5 面试官追问数字来源的"标准防守答法"

以后面试官只要一问"你这个 70% 的优化率是怎么算出来的？"，你就按这个三段式答，**别只说"我测的"**：

```
"我是用「先基线、后优化、再对比」的方式测的：
 ① 先把代码切回优化前版本，用 APIFOX / JMeter 跑 5 轮稳定基线，记录平均 rt、p95、mysql questions 增量；
 ② 再切到优化后代码，保证数据量和请求量完全一致，跑同样 5 轮，去首尾取中间值；
 ③ 两者做差，再结合 Redis INFO 和慢查询日志交叉验证，最终得出这个数字。
另外我还留了当时的压测报告和对比截图/日志，面试现场其实我也可以当场给你看当时的对比记录。"
```

> 这句话只要你说出来，面试官 90% 不会再追问了。因为他知道你真测了，不是拍脑袋写。

### 13.7 本节结论

- 升级版最大的求职风险不是"做不出来"，而是**做出来了但说不清"优化了多少"**。
- 从今天起你每做完一天（Day13~Day20 任何一天），**必须额外做 3 件事只花 20 分钟**：
  1. 按上面给的量化维度，至少跑 1 组对比数据；
  2. 把对比结果存到 `docs/upgrade-metrics/` 下，按天命名为一张 Markdown 表 + 2~3 张截图；
  3. 从"简历句式"里抄一版你当天能说出口的 30 秒表达出来，放进对应项目话术文档。
- 只要你坚持这么做，最终升级版项目和原版项目最大的区别就不是"加了多少技术"，而是**每一项技术背后都有可验证、能讲清楚的指标**——这恰恰是区分"课程项目"和"能拿面试的项目"最关键的分界线。
