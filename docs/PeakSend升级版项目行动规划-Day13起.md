# PeakSend 升级版项目行动规划（Day13 起草版）

## 1. 这份文档是干什么的

这不是最终敲定版，也不是为了把技术名词先堆满。

它的作用是：

- 在 `Day12` 原项目收官之前，先把升级版项目的大方向定下来
- 防止后续切换对话、切换阶段时，项目升级路线重新变散
- 让我们从现在开始就知道：后面不是“随便加点新技术”，而是按阶段把 `PeakSend` 从课程项目演进成更适合求职展示的扩展版项目

一句话概括：

- 原项目解决“把业务做通”
- 升级版项目解决“把它做得更像公司里的系统”

## 2. 为什么我们需要升级版项目

当前这份 `PeakSend` 已经具备很强的业务骨架：

- 管理端和用户端两条业务线都已经存在
- 订单、支付、历史订单、催单、工作台、报表等核心模块已经逐步补齐
- 项目中已经出现了 `Redis`、`WebSocket`、定时任务、统计报表等较有价值的技术点

但如果目标从“完成课程项目”升级为“拿它去冲中小厂实习”，只停在这里还不够。

原因不是这份项目没价值，而是：

- 当前技术画像仍偏单体课程项目
- 工程化、部署、服务拆分、异步消息、可观测性这些求职高频能力还没有真正长出来
- 后面如果再单独做一份新的业务项目，投入会很大，且容易和现在已有成果割裂

因此，更合理的路线不是重开一个新业务，而是：

- 以 `PeakSend` 为主战项目
- 在保留现有业务骨架的前提下，继续做工程化升级和架构演进

## 3. 升级版项目的总目标

升级版 `PeakSend` 的目标不是炫技，而是最终形成一份你能稳定讲清楚的项目：

- 既有真实业务链路
- 又有分阶段引入的新技术栈
- 每一层升级都能解释“为什么要加”
- 每一阶段做完后都能运行、能验证、能复盘、能用于面试表达

最终希望把它升级成一份这样的项目：

- 一个可运行、可部署的商配平台
- 一个带缓存、异步通知、延迟任务、服务拆分的后端项目
- 一个可以和你的底层 `RPC` 项目形成互补的简历主项目

## 4. 升级版项目的边界与原则

后面的升级，必须遵守下面几条原则。

### 4.1 不为技术而技术

后面加每个技术，都要能回答：

- 它解决当前项目的什么问题
- 为什么适合加在 `PeakSend`
- 如果不加，会有什么痛点

如果一个技术点只是“听起来高级”，但和当前业务没有自然联系，就不优先加。

### 4.2 一次只打一小仗

后面不能一句“开始上微服务”就大跃进。

必须改成：

- 先做一个最小闭环
- 跑通
- 验证
- 复盘
- 再进入下一阶段

### 4.3 每一阶段都要有可交付结果

每一阶段结束后，至少要留下：

- 能运行的代码
- 能复现的验证步骤
- 能讲清的主链
- 能复习的文档

### 4.4 前端源码缺失时，优先升级后端和系统层

当前项目管理端前端源码不完整，这是一个现实边界。

因此后续升级时默认采用下面的推进策略：

- 优先做后端服务、缓存、MQ、Docker、网关、注册中心、链路追踪等不依赖前端源码的能力
- 验证方式以接口、日志、数据库、脚本、Swagger、APIFox 为主
- 如果后面某个阶段确实需要新的页面演示，再考虑单独补一个极简演示页，而不是强行深改现有打包前端

### 4.5 先让项目更稳，再让项目更大

因此路线顺序会固定为：

1. 先工程化和部署能力
2. 再缓存与异步解耦
3. 再服务拆分
4. 最后再做监控、链路追踪、部署流程

## 5. 我们当前站在什么位置

如果把当前项目看作“课程版 `PeakSend`”，我们现在大致已经完成了：

- 单体项目基础结构
- 管理端与用户端主要业务链
- 下单、支付主干、历史订单、再来一单
- WebSocket 催单提醒
- 订单处理、工作台、统计报表等主体能力

也就是说，当前版本已经比较接近：

- 业务基本成型
- 工程能力和架构能力还没系统升级

所以后续升级，不是从零开始，而是从一个已经有业务主干的项目继续向上长。

## 6. 升级版总体路线图

升级版暂定分成四个大版本：

- `V1`：Docker + Redis + 工程化强化
- `V2`：RocketMQ + 延迟关单 + 通知异步化
- `V3`：Spring Cloud Alibaba + 核心服务拆分
- `V4`：监控、日志、链路追踪、部署流程

如果进一步映射到天数，可以先按 `Day13` 到 `Day20` 这样规划。

## 7. Day13 ~ Day20 阶段规划

下面这部分不是死板日历，而是“默认推进顺序”。

如果实际实现中某一阶段跨度大，也允许拆成两天或更多天，但顺序尽量不乱。

### Day13：Docker 化基础环境与一键启动

目标：

- 把当前项目从“本机手动拼环境”升级成“可通过容器统一拉起核心环境”
- 降低后续继续扩展时的环境成本和迁移成本

核心要做的事：

- 明确当前项目运行依赖：

  - MySQL
  - Redis
  - Nginx
  - 后端服务
- 为这些依赖补齐容器化方案
- 提供 `docker-compose.yml`
- 整理环境变量和端口说明
- 形成一份最小启动说明文档

预期达到的效果：

- 后面别人拿到项目后，不必再到处手动配环境
- 至少能通过较固定的步骤拉起 MySQL、Redis、Nginx 等核心基础设施
- 项目具备“工程交付感”

重点验证：

- 容器启动后数据库可连接
- Redis 可连接
- Nginx 可以正常转发
- 后端能连上容器里的依赖并启动

这一天的求职价值：

- 你可以明确讲“我把项目从本机开发态，推进成了可容器化部署的版本”

### Day14：Redis 升级使用与工程化补强

目标：

- 不再把 `Redis` 只当成“项目里出现过”
- 而是把它变成可以真正讲出业务价值的核心中间件

核心要做的事：

- 盘点当前项目里适合上缓存或短期状态存储的地方
- 优先挑 2 到 3 个最有价值的场景落地，例如：
  - 店铺营业状态缓存
  - 菜品 / 套餐 / 分类的热点数据缓存
  - 购物车或短期业务状态缓存
  - 登录态相关辅助缓存
- 统一缓存 key 命名规则
- 明确缓存失效策略
- 明确写操作后缓存如何更新或删除

预期达到的效果：

- `Redis` 不再只是“课程里提过”
- 而是有真实业务落点、有更新策略、有排错思路

重点验证：

- 首次读走数据库，二次读命中缓存
- 数据更新后缓存同步更新或删除
- Redis 异常时系统是否仍能回退到数据库逻辑

这一天的求职价值：

- 你可以讲缓存穿透、缓存更新、热点数据、读写路径、缓存和数据库一致性的基础思路

### Day15：RocketMQ 基础接入与事件模型设计

目标：

- 为项目补上异步消息能力
- 先建立消息驱动思维，再做具体业务落地

核心要做的事：

- 引入 `RocketMQ`
- 明确项目中适合事件化的几个动作
- 设计第一版事件主题，例如：
  - `order-paid`
  - `order-reminder`
  - `order-completed`
- 明确：
  - 谁生产消息
  - 谁消费消息
  - 消息体中带什么字段
  - 如何保证消费幂等

预期达到的效果：

- 项目第一次具备“同步业务链 + 异步处理链”的双线结构
- 后面延迟消息、异步通知、统计解耦都有了基础

重点验证：

- 能成功发送消息
- 消费者能正确接收
- 消费逻辑执行结果能在日志、数据库或界面中看到

这一天的求职价值：

- 你可以开始正式讲“为什么引入 MQ，而不是所有逻辑都同步处理”

### Day16：延迟关单与订单时效处理

目标：

- 结合订单域做一个非常适合面试讲解的 MQ 场景：超时未支付自动关单

核心要做的事：

- 梳理当前订单支付主链
- 在订单创建或支付流程中加入延迟消息
- 到达超时时间后检查订单状态
- 若订单仍未支付，则自动取消
- 明确自动取消时对订单状态、支付状态、原因字段的更新策略

预期达到的效果：

- 项目具备一个真实、经典、容易讲的异步业务场景
- MQ 的价值不再停留在“会收发消息”

重点验证：

- 创建一笔待付款订单
- 不支付，等待超时时间
- 订单自动变为取消状态
- 已支付订单不会被误取消

这一天的求职价值：

- 这是电商、外卖、交易系统里非常经典的业务题，面试时很有价值

### Day17：通知链异步化与提醒解耦

目标：

- 把之前已经做过的 WebSocket 提醒链，从“直接调用”进一步升级成“异步通知链”

核心要做的事：

- 重新梳理当前来单提醒、催单提醒的触发点
- 让提醒消息先进入 MQ
- 再由通知消费者统一处理后续动作，例如：
  - 推 WebSocket
  - 记录通知日志
  - 为后续短信、站内信预留扩展点

预期达到的效果：

- 订单服务和通知服务的职责开始解耦
- 后面做服务拆分时更自然

重点验证：

- 用户下单或催单后，不再由订单服务直接承担全部通知职责
- 即使通知处理稍慢，主业务也不被阻塞

这一天的求职价值：

- 你可以讲“为什么要把通知能力独立出来”
- 也能把 `WebSocket` 和 `RocketMQ` 串成一条更完整的异步链路

### Day18：Spring Cloud Alibaba 基础设施进场

目标：

- 开始从单体工程视角，切换到微服务演进视角
- 但这一天先不急着大拆业务

核心要做的事：

- 引入 `Nacos`
- 引入 `Gateway`
- 建立最小的微服务骨架
- 梳理哪些公共代码仍应放在公共模块
- 梳理配置中心和注册中心的基本组织方式

预期达到的效果：

- 项目第一次具备：
  - 服务注册发现
  - 配置集中管理
  - 网关统一入口

重点验证：

- 至少两个服务可以被注册到 `Nacos`
- `Gateway` 可以正确转发请求
- 配置可以从配置中心读取

这一天的求职价值：

- 你能讲“为什么微服务不能只理解成把包拆散，而要先建设基础设施”

### Day19：核心服务拆分 + 服务调用治理

目标：

- 迈出真正的服务拆分第一步
- 在拆分时同步把最基本的服务调用能力补起来，避免只拆不通

建议优先拆分的服务：

- `gateway-service`
- `order-service`
- `product-service`
- `notify-service`

拆分思路：

- `order-service` 负责订单主链、状态流转、支付后状态变更
- `product-service` 负责菜品、套餐、分类、店铺营业态等商品域能力
- `notify-service` 负责 WebSocket 推送和消息消费
- 通过 `OpenFeign` 打通第一批必要的跨服务调用

预期达到的效果：

- 业务边界不再只停留在包结构层面，而是真正形成跨服务调用关系
- 微服务不只是“目录拆开”，而是已经具备最小可运行的服务协作能力

重点验证：

- 下单或催单链路至少能跨两个服务完成
- 服务间调用结果可通过日志和接口验证

这一天的求职价值：

- 你可以开始真正讲“为什么这样拆，而不是那样拆”

### Day20：日志链路、部署流程与最终表达收口

目标：

- 给升级版项目做一个阶段性收口
- 让它从“已经拆起来了”进一步变成“可以展示、可以讲解、可以继续迭代”的状态

核心要做的事：

- 统一日志格式
- 为请求生成并透传 `traceId`
- 接入日志收集或链路追踪方案
- 梳理统一启动流程与部署步骤
- 整理最终项目结构图、链路图、简历描述和面试高频问法

预期达到的效果：

- 出现问题时，不再只能依赖单机本地日志定位
- 项目具备阶段性的可观测性、可展示性和可表达性
- 当前升级版能够形成一套可继续往后迭代的稳定骨架

重点验证：

- 一次请求经过多个服务时，日志中能串起同一条链路
- 项目启动步骤清晰、部署步骤清晰
- 你可以独立讲出：
  - 原版项目做了什么
  - 升级版新增了什么
  - 为什么把路线压成 Day20 仍然成立
  - 哪些能力已经具备，哪些还可以继续向后扩展

这一天的求职价值：

- 你可以讲日志链路、服务协作、阶段部署、项目演进路线和简历表达

## 9. 为什么这个路线是可做的

你担心后面没有课程标准答案，也担心前端源码不完整。

这是合理的，但这条路线依然是可做的，原因在于：

- 后续最值钱的升级点，本来就主要发生在后端和系统层
- `Docker`、`Redis`、`RocketMQ`、`Nacos`、`Gateway`、`Feign`、日志链路追踪这些，都不依赖完整前端源码
- 它们的验证方式更适合用接口、日志、数据库和服务运行状态来完成

也就是说：

- 前面课程阶段更像“对照成熟项目补齐业务”
- 后面升级阶段更像“按真实工程思路继续演进”

推进方法会变，但并不意味着做不下去。

## 10. 这份规划当前不包含什么

为了控制边界，当前版本暂时不把下面这些列为优先主线：

- `Kubernetes`
- 复杂分布式事务全家桶
- 过重的领域建模改造
- 重新做一套大型前端工程
- 纯展示型但技术含量不高的小功能堆叠

这些东西不是永远不做，而是当前阶段投入产出比不高。

## 12. 当前阶段的结论

从现在开始，我们对 `PeakSend` 应该有两层明确认识：

### 第一层：原项目

- 目标是把课程版项目收官
- 强调业务主链、联调、复盘、文档沉淀

### 第二层：升级版项目

- 目标是把它演进成更适合实习求职展示的版本
- 强调工程化、异步化、服务拆分和可观测性

这两个目标不是互相冲突，而是前后衔接。

更准确地说：

- 原项目是地基
- 升级版是往上长出来的楼

后续只要我们继续坚持：

- 不乱加技术
- 一次只推进一个最小闭环
- 每阶段都要跑通、验证、复盘、沉淀

那么这份项目就有机会从一份课程项目，逐步长成一份更有竞争力的实习主项目。

## 13. 升级版项目量化指标体系 & 简历表达库

> 本节目的：解决升级版规划中"只写了做什么，没写优化了多少"的问题，让每一项升级在简历和面试里都能讲出**动作 → 措施 → 指标 → 结果**的完整链条。

### 13.1 先讲清楚：三种量化类型，别瞎编数字

写简历和面试时，数字分三类，**A 类必须真跑工具测了再写，B/C 类做工程对比推导后就可以写，但都要保留验证记录（截图/日志/对比表）防追问**。

| 类型 | 含义 | 举例 | 面试时怎么答"你怎么测的" |
|---|---|---|---|
| **A 类：真实可压测量化** | 必须用工具（JMeter/APIFOX压测、Redis INFO、日志统计）实际跑出数据后才能写到简历上 | 缓存命中率 85%+、接口 P95 从 320ms 降到 78ms | "我用 APIFOX / JMeter 连续压了 5 轮，每轮 1000 次请求，去掉首尾冷启动后取平均值；Redis 命中率用 `INFO stats` 里的 `keyspace_hits/(hits+misses)` 看的。" |

| **统一部署文档的完整度**（B 类） | 列清单：最终 README 里是否有：架构图、服务清单、端口清单、docker-compose 一键起/停、压测方法、验证步骤、常见排障清单 | ≥ 8 类文档齐全 | **"形成了一套完整的升级版项目交付包：含架构图、服务清单、一键启动脚本、压测记录、验证清单与问题定位手册，具备可复盘、可讲解、可继续演进的稳定骨架。"** |

### 13.4 简历数字安全区间（**非常重要：没测就别往上填**）

给你一份"就算你不做极限压测，按正常流程跑也不会离谱"的区间参考。**你测出来的数字落在这个区间里就可以放心写；如果比这个区间好很多，可以写得更猛；差很多就别吹、先排查实现。**


### 13.5 面试官追问数字来源的"标准防守答法"

以后面试官只要一问"你这个 70% 的优化率是怎么算出来的？"，你就按这个三段式答，**别只说"我测的"**：

```
"我是用「先基线、后优化、再对比」的方式测的：
 ① 先把代码切回优化前版本，用 APIFOX / JMeter 跑 5 轮稳定基线，记录平均 rt、p95、mysql questions 增量；
 ② 再切到优化后代码，保证数据量和请求量完全一致，跑同样 5 轮，去首尾取中间值；
 ③ 两者做差，再结合 Redis INFO 和慢查询日志交叉验证，最终得出这个数字。
另外我还留了当时的压测报告和对比截图/日志，面试现场其实我也可以当场给你看当时的对比记录。"
```

> 这句话只要你说出来，面试官 90% 不会再追问了。因为他知道你真测了，不是拍脑袋写。

### 13.7 本节结论

- 升级版最大的求职风险不是"做不出来"，而是**做出来了但说不清"优化了多少"**。
- 从今天起你每做完一天（Day13~Day20 任何一天），**必须额外做 3 件事只花 20 分钟**：
  1. 按上面给的量化维度，至少跑 1 组对比数据；
  2. 把对比结果存到 `docs/upgrade-metrics/` 下，按天命名为一张 Markdown 表 + 2~3 张截图；
  3. 从"简历句式"里抄一版你当天能说出口的 30 秒表达出来，放进对应项目话术文档。
- 只要你坚持这么做，最终升级版项目和原版项目最大的区别就不是"加了多少技术"，而是**每一项技术背后都有可验证、能讲清楚的指标**——这恰恰是区分"课程项目"和"能拿面试的项目"最关键的分界线。
